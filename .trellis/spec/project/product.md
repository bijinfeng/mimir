# mimir 产品需求文档

> 自托管的个人知识库：写 Markdown 笔记、收集外部资料、带引用地问 AI。
> 单用户，部署在自己的服务器上。

---

## 1. 非目标

明确不做的事。写下来是为了在功能诱惑面前有据可依。

| 不做 | 原因 |
|---|---|
| 多人协作、团队权限、审计日志 | 单用户自托管，这些是纯负担。WeKnora 的 RBAC 四层角色矩阵对一个人是负资产 |
| 公开发布 / 博客平台 | 偶尔想分享一篇时，导出 md 即可，不值得为它做一套发布流程 |
| 全功能任务管理 | 只做「笔记里的 `- [ ]` 能聚合出一个清单」这一层。不做看板、甘特、提醒 |
| 知识图谱可视化 | 好看，日常几乎不点。反链列表 + 相关笔记已经够用 |
| 外部插件市场 | 见 architecture.md 的插件章节。「插件架构」在本项目里指内部接缝，不是第三方生态 |
| 可切换的**数据库** / 向量引擎 | 数据库是**受控双实现**而非可切换产品（D-045）：服务器部署 = Postgres 17 + pgvector，本地开发与桌面端 = SQLite，由 `DATABASE_URL` 协议头决定——它是部署事实，不进设置页、没有界面开关、不做第三种后端。SQL 方言分支收敛在五个点名处（见 TECH §1）。**文件存储不在此列**——它有多实现（本地与 S3），且第二次实现不是为了兼容已有栈：远程部署的人本来就没有本地文件可开。见 D-031、D-038 |
| 排版级编辑器 | 不做 LaTeX 排版、不做协同编辑、不做块级拖拽 |
| **自建兼容 Word 的编辑器** | PDF 批注在 M2（那时它是「划线与注释」的一部分）。Office 的在线编辑**不做自建**——那等于从零写一个兼容 Word 的编辑器，而本项目的定位是知识库不是办公套件。但**借**一个是可以的：docx 的编辑由 vendored 的 GenOffice 引擎承担（D-049、`architecture.md` §15），因为它的补丁式保存做到了「改两个字不重排整篇 XML」。现实路径「下载 → 外部工具改 → 替换原件」仍然保留（`替换原件` 因此必须有） |
| **缩略图与网格视图** | 需要一条缩略图管线（图片解码 + PDF 首页渲染），而「文件名 + 格式 + 大小」已经足够认出是哪份文件 |
| **入库 OCR 与付费视觉 OCR 通道** | 不对上传或抓取的图片、扫描件自动识别，不把识别文字写入原件或知识库索引。用户于 2026-10-17 明确批准的例外是 **PDF 编辑器内、本地计算的临时 OCR**，仅供当前 PDF 复制与搜索；无需配置模型，不调用付费视觉服务。识别结果仅保留在当前编辑会话，允许选字复制与搜索；不写回 PDF 或知识库索引，关闭或刷新后清除 |
| **格式转换导出**（PDF → md、Word → PDF） | 导出回答的是「把我的东西拿走」，而不是「帮我转格式」。原件与提取的正文都给了，转换交给专业工具 |
| 用户管理（用户列表 / 角色 / 权限 / 改邮箱） | 单用户自托管。**改自己的名称与头像是「账号资料」，不在这一条里**——它没有引入第二个用户，也没有新增任何一处权限判断。改邮箱尤其不做：`OWNER_EMAIL` 是所有者账号的真相来源（D-020），改邮箱等于换账号 |

## 2. 三条核心洞见

这三条驱动了后面几乎所有设计。评审时可以问：某个功能是在服务哪一条？

### 2.1 知识库死于「收集摩擦」和「再也不看」

不是死于存不下。绝大多数个人知识库的生命周期是：兴致勃勃搭好 → 收集了一堆 → 再也没打开过。

**设计后果**：
- 收集入口的摩擦必须低于「先在浏览器收藏，之后再说」
- 检索质量是**核心功能**，不是附属特性。搜不到等于没存

### 2.2 闭环是五环，断一环整个就废

```
收集  →  整理  →  检索  →  使用  →  沉淀
```

原型阶段两次补洞都源于这个诊断：

| 断裂处 | 症状 | 修补 |
|---|---|---|
| 收集 | 界面上根本没有地方粘贴链接 | 抓取对话框（自动识别来源并提示该来源特有的坑） |
| 整理 | 只有「待整理」橙色徽标，没有任何整理动作，收件箱是死胡同 | 标签与目录随时可补（在头部的「⋯」菜单里，D-054 后不再有收件箱这个暂存区） |
| 沉淀 | 对话产出结论，但界面上无处可去 | AI 回答下的「存成笔记」，保留引用来源 |

### 2.3 「资料」与「笔记」行为不同，但不做浏览分类

| | 笔记 | 资料 |
|---|---|---|
| 来源 | 自己写 | 抓取（博客 / 公众号 / GitHub）或**上传文件** |
| 可编辑 | 是 | 否（只读） |
| 真相 | 文件 | **原件 + 派生正文**（抓取件：原始快照 + 派生正文） |
| 检索权重 | 高 | 正常 |

这些差异体现在**行为**上：笔记可编辑、抓取件只读；检索时自己的笔记加权。
它们**不体现在浏览分类上**（修订，D-047）：界面不按来源分组、不放来源
筛选与来源徽标——库就是**一个统一的文档集合**，组织靠目录、标签与搜索。
理由：按来源分类是「稍后读列表」的心智（我的笔记 / 收集的资料两个入口），
而知识库的浏览主角是库本身；「这是笔记还是资料」在打开详情的那一刻自然
可知（能不能编辑），不需要一枚常驻徽标提前替用户分类。

**上传的文件属于「资料」，但不是一种新的东西。** 它和抓取的资料共用同一条
`documents` 记录、同一套整理动作（标签 / 目录）、同一次检索，
区别只在原件的来源不同（本机 vs URL）。所以：

- **`kind` 是来源，不是格式。** 五种：笔记 / 网页 / 公众号 / GitHub / 文件。
  PDF、Word、Excel、图片这些是**格式**——格式决定预览方式
  （PDF 在线看、Word 提取正文），不决定它是不是知识
- 唯一的例外是 **`.md` 上传**：它变成**可编辑的笔记**。md 本来就是可编辑格式，
  做成只读副本会立刻产生两个真相（原件不再变、而正文可以改）

## 3. 内容来源与抓取方案

三类来源的难度差异极大，方案必须分开设计。

### 3.1 技术博客

**主路径：RSS / Atom 订阅。** 掘金、博客园、Medium、Substack、Hugo/Hexo 站点基本都有 feed。定时轮询、新文章自动入库，比爬首页稳得多，也不需要处理反爬。

**辅路径**：无 feed 的站点用「粘贴 URL → 服务端 Readability 提取正文」。

### 3.2 微信公众号

**这是最难的一类。** 现实约束：

| 约束 | 后果 |
|---|---|
| 服务端直接 GET 多数情况能拿到正文（在 `#js_content`），但近年加了环境校验，高频访问会撞墙 | 只能低频，且需要限速与退避 |
| 正文图片在 `mmbiz.qpic.cn`，下载必须带 `Referer: https://mp.weixin.qq.com/` | 不带就 403，文章变空壳 |
| RSSHub 的公众号路由维护成本高、易失效 | 不作为唯一方案 |
| 技术号经常把代码贴成**截图**，正文里根本没有代码文本 | 只能 OCR 或接受。摘要里要标注「该段为图片」 |
| 文章会被删除 | **全文快照 + 图片本地化是刚需**，不是可选项 |

**方案**：主路径是浏览器扩展（在用户的会话里抓，绕开反爬、拿到完整 DOM）；服务端抓取作为辅路径（低频、带 Referer、失败时提示「改用扩展」）。

### 3.3 GitHub

用 GitHub API（PAT 可把限额从 60 次/小时提到 5000 次/小时）：

- 取 repo 元数据 + README（raw）+ topics + license + releases + 最近提交时间
- AI 生成解读：解决什么问题 / 技术栈 / 适合什么场景 / 是否值得深入 / 与已有笔记的关联
- **Star 同步**：每天拉一次自己 star 的仓库，新的自动入库。对技术人这是最省力的知识来源
- 只抓 README 和 `docs/`，不克隆整个仓库

### 3.4 优先级

| 来源 | M0 | M1 | M2 |
|---|---|---|---|
| 手动新建笔记 | ✓ | | |
| 粘贴 URL（服务端抓取） | ✓ | | |
| GitHub API | ✓ | | |
| 公众号（服务端，低频） | ✓ | | |
| **文件上传（任意格式，原件 + 预览 + 下载）** | | **✓ 已落地** | |
| **文本 / HTML / Office / PDF 的正文提取（可搜）** | | **✓ 已落地** | |
| **RSS 订阅（手动触发轮询，界面在设置 › 订阅）** | | **✓ 已落地** | |
| 浏览器扩展 | | ✓ | |
| GitHub Star 同步 | | | ✓ |

## 4. 功能范围

### M0 —— 可用

目标：能真实地写笔记、收集资料、搜到东西。

- Docker Compose 骨架 + Postgres
- 单用户登录（首个注册者成为唯一用户，之后注册自动关闭）。首次建号时自动播种一个「开始使用」知识库 + 一篇产品说明（D-085）
- Markdown 笔记：所见即所得编辑，文件落盘为纯 md
- 笔记 CRUD + 标签
- 粘贴 URL 抓取（网页 / 公众号 / GitHub），直接入库
- 整理：建议标签、归目录
- 全文检索（中文分词，见 architecture.md）
- 库视图（卡片 / 列表）+ 目录树（侧边栏直接增删改移）+ 标签
- 全量导出（**含上传的原件**——对一份 PDF 来说原件才是内容）

**判据**：能连续用一周不觉得别扭。

### M1 —— 有用

目标：问它「我以前记过什么」，能给出准确且带引用的答案。

- **配置面**：模型按任务配置（对话 / 推理 / 摘要 / 向量化）；检索设置展示
  可理解的状态、测试入口与维护操作。普通用户界面不展示融合参数、分词器、
  数据库类型、文件路径、环境变量或其他实现细节。部署与诊断配置仍由现有
  服务端契约管理，见 architecture.md §7.5。
- **分块 + 向量化（pgvector / sqlite-vec）——已落地**（D-084）：`chunks` /
  `chunk_embeddings` 双方言表；写路径自动分块；嵌入失败不阻断写入，
  「待嵌入 N 段」在设置 › 检索如实显示，补嵌入分批可重入
- **混合检索：关键词 + 子串 + 向量，加权 RRF 融合——已落地**：检索单元
  下沉到分块；向量通道就绪时默认模式自动变 hybrid（由注册表推导）
- **带引用的知识库问答，引用指回分块的真实偏移——已落地**：相邻分块合并、
  每篇上限（默认 3）、引用的 `start/end` 是分块自身的区间（不再是猜的）
- **AI 自动摘要、标签建议——已落地**：摘要走 `summarize` 角色、不落库
  （现用现生成）；AI 标签与统计版建议标签并存（入口都在「⋯」菜单，AI 项
  标明会产生用量）
- **内联改写（选中一段 → 改写/翻译/精简/扩写）——已落地**：选区工具条
  直接替换选区（进 undo 栈，可撤销）
- **文件上传**（任意格式）：原件入库、列表、按格式预览、下载、替换原件、
  随导出打包带走。`parser` 接缝有 text / docx / xlsx / pptx / **pdf**（M1-E）
  五个实现，所以文本、HTML、Office 与 **PDF 的内容都可搜、可被 AI 引用**
  （PDF 复用仓库里已有的 pdf.js，不引入第二个解析器；扫描件没有文字层，
  入库提取如实提示没有文字层，不自动做 OCR；编辑器内临时 OCR 的批准范围见 §1）。.xlsx 与 .pptx 另有**预览与编辑**（网格 / 幻灯片；
  §5.12、TECH §15.7–15.9）
- **编辑**：Markdown、**.docx**（浏览器内编辑器，D-049）、**.xlsx**（改单元格，
  D-053）与 **.pptx**（改文字，D-052）都可改——三种 Office 格式的保存**都是
  补丁式**的（改一处不重排整篇 XML，见 `architecture.md` §15.9）。PDF 批注在 M2
- **RSS 订阅——已落地**（设置 › 订阅）：订阅时先拉一次（拉不通不落库）、
  更新按水位线增量入库、失败原因与上次成功时间分开显示；退订不删已收文章。
  轮询由用户点「更新」触发（M1 没有 jobs 层，TECH §4.10 的同一形态）
- **账号资料**：改名称、换头像（头像进 `data/avatars/`，**不进 vault、不进检索、不进导出包**——
  导出包回答的是「我的知识」，不是「我的账户」）
- **用量统计**：每次模型调用记账（token / 耗时 / 成败），设置页「统计」分区给出
  token 消耗热力图与按角色的用量表。表与采集点先落，界面后做（见 TECH §12.6）

**判据**：问「我以前关于 X 记过什么」，回答带引用且引用指对了原文位置。

M1 的推进拆成五段（顺序与依赖见 `architecture.md` §11）：

| 段 | 内容 | 为什么在这个位置 |
|---|---|---|
| A | 插件骨架：注册表 + 配置分层 + provider 角色化 | 后面每一步都要读写配置，而且向量通道要问 provider「有没有可用的 embed 模型」 |
| B | 分块与向量化 | 检索单元下沉是 C 的前提 |
| C | 混合检索 | 两条老通道改返回分块 id，加向量通道 |
| D | 带引用的问答、摘要、标签、内联改写 | 消费 C 的结果 |
| E | 文件上传、Office 与文本的正文提取、RSS | `parser` 接缝的新实现，独立推进。**全部已落地**（D-084）：上传与五类提取（文本 / HTML / Office×3 / PDF）、RSS 订阅（feeds 表 + 手动轮询 + 设置页界面） |

### M2 —— 好用

- 浏览器扩展（解决公众号、知乎、付费墙）
- GitHub Star 同步
- 划线与注释（读 PDF/网页时高亮 → 变成可检索的引用片段）
- 对话沉淀成笔记的完整形态（自动带引用来源）
- 移动端速记（窄屏独立设计，见下）

### M3 —— 长期

- 回顾机制：随机回顾、每日回顾、「一年前的今天」
- 关联推荐（自动发现未链接的提及）
- 多篇资料生成技术调研综述
- 模型侧成本优化（按内容哈希缓存、增量向量化）

## 5. 关键交互决策

这些是原型阶段逐条定下来的。每条都附了理由，因为「为什么不用另一种」比「用了哪种」更容易被遗忘。

### 5.1 布局：两栏 + 知识库页（修订，D-047 / D-079）

左导航 / 主区。主区有两种状态：

| 状态 | 何时 | 主区显示 |
|---|---|---|
| **浏览态** | URL 无 `id` | **知识库页**：知识库的名称 / 描述 / ID / 创建者，工具条（计数、卡片 / 列表、新建文件夹、新建文件、添加文档）+ 文件夹卡片与文件卡片。筛选靠左导航的 scope（知识库 / 标签） |
| **阅读态** | URL 有 `id` | 详情占满主区（阅读 / 编辑），顶部返回库 |

**没有「全部文档」页**（D-079，用户拍板）：内容都住在知识库里，`scope=all`
进入时直接落到第一个知识库（一个都没有时给创建引导）。「归属」这件事因此
重新成为内容的第一属性，而不是一个可选的整理动作。收集入口收进工具条的
「添加文档」下拉（上传文件 / 上传文件夹 / 网页抓取 / 直接编辑），搜索改从
命令面板（Ctrl K）进入。

否决史：「两栏 + 命令面板」曾因「不记得存过什么时连翻一翻都做不到」被否决
（那条理由是对的）——但解法不是把浏览面塞回一条 300px 的窄栏，而是让
**主区本身就是浏览面**。三栏的窄列表 + 详情是邮件客户端的 master-detail
心智，把库压成了配角；两栏库视图里，收集的东西才是主角（对齐 DEVONthink /
Eagle / Cubox 这类知识库应用的形态）。

代价：原来「左列表右详情」能边看边归类，现在要「点开 → 处理 → 返回」，多一次点击；
补偿是归类动作（标签 / 目录）都在详情头部的「⋯」菜单里，不依赖并排。
阅读态的左导航提供最近打开的笔记与当前笔记位置，允许直接切换；它不新增常驻的第三列。

### 5.2 左导航：会话优先

顶部是「新建对话」+ 会话历史，然后才是文档入口。

会话历史最多显示 12 条；当前会话在已取回列表的第 12 条之后时，显示前 11 条和当前项。
最近打开记录按账号保存至多 12 个 ID，导航展示其中至多 6 篇笔记。加载、真实空列表与暂时读取失败分别反馈；
403/404 项隐藏，401 沿用鉴权错误处理，其他失败允许重试，已成功读到的项目保留可用。
账号菜单在会话或部署模式读取失败时保留设置入口与重试；只有确认需要登录的模式显示邮箱和登出。
登出经过现有未保存内容确认，等待期间单次提交，失败在菜单内重试；窄屏 Drawer 与侧轨只保留一个账号菜单触发器。

**全部两栏。** 文档模式的主区在浏览态与阅读态之间切换：

| 模式 | 左栏 | 主区 |
|---|---|---|
| 对话 | 会话历史 + 知识库列表 | 对话（含可折叠的检索过程与引用） |
| 设置 | 同上 | 设置分区与表单 |
| 文档（浏览态） | 同上 | 知识库页：头部身份 + 文件夹 / 文件卡片 |
| 文档（阅读态） | 同上 | 阅读 / 编辑，顶部返回库 |

**设置页为什么也不该有中栏**：设置是「进入一个分区改完就走」的场景，而中栏
在那里只能显示文档列表——**与你在做的事完全无关，却占掉四分之一的宽度**。
它还会误导：那个列表看起来像设置的一部分。

设置页自己有一套分区导航（模型 / 检索 / 抓取 / 插件 / 统计 / 数据 / 外观 / 账号），
那才是它需要的那一栏；它是**横向**排在内容上方的——早期版本把它做成内容列里
的左侧竖栏，于是一页之内有了两条左栏（`.trellis/spec/project/decisions.md` D-025）。

「外观」是其中一个分区，也是唯一**不写进设置键表**的一项：它是纯客户端的
渲染偏好，存 `localStorage` 而不是数据库（`design.md` §11 的同一判断）。
代价是换设备要重选一次，这一点直接写在那个分区里，不假装它跟着账号走。

### 为什么删掉了对话模式的中栏

原型里它显示「本次引用」（一张张来源卡片）。当时的设计意图是
**「它读了什么」应该和「我有什么」一样可见**。这个意图是对的，但**放错了位置**：

1. **它与回答下方的引用块重复。** 每条 AI 回答下面已经是一列引用块，带类型徽标、
   标题、原文片段与命中通道。中栏那几张是它的副本，而且更差——少了与
   具体回答的对应关系，看不出「这个来源支撑的是哪句话」
2. **它有一半时间显示的是别的东西。** 新对话时中栏按当时的 §5.10 显示待整理收件箱；
   有会话时显示引用。同一栏位承担两种语义，用户每次都要重新判断「现在是什么」
3. **它是静态的。** 打开一个旧会话时显示的是那个会话的历史引用，
   而用户此刻想做的往往是「继续问」或「去看那篇文档」——两者都不需要这一栏

删掉换来的是：对话列更宽（问答是主场景，值得更多横向空间）、少一个要学的模式、
以及不再有「看起来像本次引用、实际是收件箱」这种误导（那正是删掉前的实际状态）。

**代价与补偿**：失去了「一次看到这次对话的全部来源」。这个需求由回答下的引用块
满足（滚动即可看到），并且引用块比中栏卡片多了「支撑哪句话」这层信息。
§5.10 那条「新对话的中栏不空着」改成在**对话空态里**列出待整理内容——
动机（「我刚收了几篇东西，想问问」）没有丢，只是换了承载它的地方。

### 5.3 树与标签并存，分工明确

- **知识库与文件夹**：一个文档只能在一个位置，管**归属**
- **标签**：一个文档可挂多个，管**横切**

两者走同一套过滤逻辑，只是筛选条件不同，避免变成两套代码。

目录是**实体**（D-068）；**侧栏只列顶层的知识库，平铺**（D-079），
子文件夹是知识库内部的结构，在知识库页里以文件夹卡片与「文档 / …」
面包屑呈现（新建、改名、删除都在知识库页的卡片上）。改名与移动对子树
生效，已归入的文档一起跟着走；删除只删结构，**里面的文档保留**、指派清空
——文档的删除有自己的确认流，不搭目录删除的便车。
递归列表中的文档显示相对目录归属，当前目录在面包屑中突出。移动文档后明确显示目标，
并提供一次撤销到原目录的操作。

知识库创建和编辑复用同一弹窗，字段为名称与可选描述；编辑支持只改描述、清空描述或同时改名，
不再提供图标选择，历史图标数据保留。失败保留完整草稿，成功后刷新知识库信息并返回操作入口。
知识库改名后同步当前 scope 的路径前缀，保留子目录后缀和已打开文档 ID，不因身份路径同步离开当前笔记。
目录更新与失败恢复的技术约定见[共享契约](../shared/contract/folder-update.md)。

### 5.4 编辑器：所见即所得，无源码模式

**已知性质：Tiptap 不是无损的，但是幂等的。**

```
输入      | 1 | 2 |
首次保存  | 1   | 2   |     会被整理成编辑器的规范形
之后每次  | 1   | 2   |     不再变化
```

正文、标题、列表、嵌套列表、代码块、引用、链接、行内代码往返逐字节一致；表格是唯一会被重排的结构。
新建笔记进入编辑页时聚焦正文，打开已有笔记时不抢走阅读焦点。

**边界**：可以作为唯一编辑器（不会逐次劣化）；**不要**用 Obsidian / VS Code 改同一批文件（两边规范形不同，来回改产生大量无意义 diff）。

### 5.5 AI 的两个入口：文档侧栏 + 主视图对话（修订，D-087）

**历史上删过 AI 侧栏**（「两边都不如」的判断见 DECISIONS 当时的记录）。
D-087 按使用反馈加回来了，但**只加在文档页**——实测校准了两类提问的真实场景：

- **读一篇文档时问它**——高频，且提问天然锚定这一篇。跳去主视图意味着
  离开正在读的内容，回个头还得再找回来。这类提问归**文档侧栏**：
  工具条「问 AI」在当前页右侧滑出对话，范围锁定这一篇；选中一段后
  内联工具条「就这段提问」同样在侧栏里预填发问。侧栏是**本文的阅读助手**
- **跨库提问 / 无特定文档**——归**主视图对话**，它有自己的页面、
  会话历史与全库范围

两个入口共享同一套对话体（流式、检索过程、引用卡、失败出路、存为笔记）。
文档侧栏锁定当前文档范围，输入区不显示“思考强度”，固定使用标准聊天模型；
主视图保留标准 / 深入切换。侧栏关闭时保持挂载：流式进行中收起再展开，
回答不丢。

「返回对话」入口保留：从对话点引用跳去文档后，文档顶部仍出现返回入口。

### 5.6 检索过程可见，默认折叠

AI 回答上方是一块「思考 2 轮 · 调用 3 次工具 (1.0s)」的折叠盒
（assistant-ui 官方 Reasoning 形态，D-099），展开后是逐步记录，每步带具体数字：

```
┌─ 🧠 思考 2 轮 · 调用 3 次工具 (1.0s) ⌄ ─┐
│    我先在知识库里找与「组件性能」相关的内容  │
│    用 jieba 切分查询词  组件 性能           │
│    词级召回 3 段 · 子串兜底 1 段            │
│    读取命中的文档并合并相邻分块  来自 2 个文档…│
│    确认没有遗漏，生成回答                    │
└────────────────────────────────────────┘
```

**这条对个人知识库比对企业的更重要**：AI 说「没找到」时，你能立刻分辨是**确实没存过**、还是**存了但分词没匹配上**、还是**检索范围设错了**。没有它，你只能怀疑自己记错了。

#### 过程可见的另一半：等待期就是过程行本尊

上面那条是**回答的依据**，但它要有内容，得等检索跑完（折叠标题里的耗时尤其要等整轮结束）。从按下发送到第一个 token 之间——检索要跑两个通道、模型还要建连接——界面上原本**什么都没有**，而这一段常常是整轮里最长的等待。

所以**检索过程行在等待期就活着**（D-098），一个表面贯穿整轮：

```
› 这篇讲了什么？用几句话概括。
  正在检索知识库 · 3s        ← 发送后立刻出现（检索结果未到）
  思考 1 轮 · 调用 1 次工具 · 7s   ← 检索一到就地展开，秒数在走
  这篇讲了什么？……            ← 正文一出收起成摘要行，秒数继续走
```

- 计时从按下发送起算。**它与服务端 trace 里的 `tookMs` 是两个钟**——客户端的
  钟只在活着的时候走，折叠摘要里永远是服务端记的整轮真实耗时
- 失败、报错、停止之后不显示「还在跑」：那时屏幕上该有的是失败卡片或
  「已停止生成」那一行
- **生成中输入框可打字，Enter 把追问排队**：本轮正常结束后自动发出；
  停止 / 失败则还给输入框（D-098）

### 5.7 对话沉淀成笔记

AI 回答下方有动作条（存成笔记 / 复制）。存下来的笔记**保留引用来源**，不是孤零零一段话。

这是闭环的最后一环。没有它，知识库只是「能问」，不会「越用越厚」。

**动作条只在「本轮真的有一条回答」时出现。** 停止生成、或流一开始就断掉的时候，服务端不会为这一轮写下助手消息，而「存成笔记」取的是**库里最后一条助手回答**——那会把**上一轮**的答案存下来，还提示「已存为笔记」。宁可少一个按钮，也不许它说谎。

### 5.8 失败路径：每类给不同的出路

| 失败 | 出路 | 说明里必须回答 |
|---|---|---|
| 额度用尽 | 改用别的模型 · 去充值 · 只看检索结果 | 这次花钱了吗 |
| 请求超时 | 重试 · 缩小到当前文档 · 拆成小问题 | 内容丢了吗 |
| 回答被截断 | 继续生成 · 只要结论 · 输出到笔记里继续写 | 能接着做吗 |
| 网络不可达 | 只用检索不调模型 · 重试 · 改用本地模型 | 还能做什么 |

统一给一个「重试」按钮等于把判断推回给用户，而用户此刻恰恰最缺判断依据。

「网络不可达」这条尤其重要：**离线不是全盘瘫痪**，检索在本地 Postgres、笔记在本地文件。明确告诉用户还能做什么。

#### 出路必须真的能走：不能走的标出来

这张表是**产品意图**，不是当前实现清单——四类里各有几条出路背后的能力（换模型、去充值、接着生成、只要结论、缩小到当前文档）在 M0 还不存在。它们**保留在卡片上**（直接删掉用户就找不到入口了，也就读不到「还有哪些可能」），但要**真的禁用**并用「暂不可用」说明状态，不在用户界面展示版本代号。

看着能点、点下去什么都不发生，比不显示更坏：用户会以为自己点错了，或者以为功能坏了。

**「只检索，不调模型」必须是真的。** 它的语义是「把原问题拿去检索，把命中的原文列出来，不调模型」——所以它是把**原问题**连同一次性的 `scope: 'search'` 发出去，而不是把「只检索，不调模型」**这句指令**当问题重发（后者会让检索拿指令去查词、模型照常被调用，点下去必然再失败一次）。

#### 请求根本没走完的时候

上面四类是**模型侧**的失败：请求跑完了、服务端给出了分类、库里也留了一条记录。另有一类是**请求就没走完**——建会话的接口失败，或者连接被切断、代理挂了。这两种从前**在界面上完全没有痕迹**（旧 SDK 不 reject，错误只躺在 `chat.error` 上）：用户按了发送，界面回到原样，像是没按过。现在它们落在**消息的错误状态**上（D-099：`incomplete / reason: error`，卡片由 `MessagePrimitive.Error` 渲染），这一类仍要有自己的外观。

它要有自己的一张卡：说「连接中断」+ 服务端/网络的原文 + 两条出路（重试 / 把问题放回输入框），并说明**这一轮没有生成回答，知识库里也不会多出一条记录**。

与四类失败**互斥**显示——服务端先发分类事件再发协议层的错误，所以同一件事会同时触发两条路径；那时只说一遍，说四类那张。

### 5.9 保存状态与未保存保护

编辑器底部状态行常驻保存入口及「正在保存… / 已保存 / 保存失败 · 点此重试」等反馈；格式工具栏不为保存按钮预留整列。

显式保存编辑器离开未保存内容时给**三个**选项：继续编辑 / 丢弃改动 / 保存并离开。
自动保存的 Markdown 笔记只给继续编辑 / 保存并离开：一旦自动保存完成，就不能把已落盘内容称作
「可丢弃的改动」。保存请求在途时等到结果明确，失败不放行。

**「保存并离开」在保存失败时不会放行**——放行了用户以为存上了，实际丢了，比不拦截更糟。

**这一层对所有可编辑的文档生效，不分格式。** 笔记与原件（docx / xlsx / pptx /
html / pdf）都能改，`lib/unsaved` 的脏标记与「立即保存」两个入口共用一份。
曾经只有笔记接上：状态行刚写着「已修改，未保存」，点「返回库」就直接走，
改动没了且没有任何提示——同一个动作两种结果，比两种都不拦更糟。

**「立即保存」的通道目前只在笔记上有**：`MarkdownEditor` 把 `saveNow` 交给宿主
（`onSaveHandle`），而 `packages/office` 的 `EditorProps` 没有对应的口子。所以原件的
「保存并离开」**不放行**（留在编辑态、改动还在），并指引用它状态行右端的
「保存到库」。补上那个口子之后，这一格应当改成真的先存再走。

### 5.10 其他

- **文档大纲**：右侧锚点导航，滚动联动高亮。**标题数 ≥ 2 才出现**——两段话的笔记不需要目录，常驻只是白占 200px。文件类文档不显示它（原件自带导航，见 §5.12）
- **标签与目录随时可补**：入口在文档头部右端的「⋯」菜单里（原本是「整理条」，D-054 收进菜单）。原先那条两段式的「收件箱 → 完成整理」流程已退役——新内容收进来直接可用，不需要第二个状态位
- **统一单行头部**：笔记、上传文件和只读资料共用 Markdown 笔记现有的简洁头部：左侧无边框的返回入口与紧凑标题，右侧为“问 AI”和更多操作。下载原件与笔记标题修改按文档能力显示。三栏布局中的工作区、文档和问 AI 侧栏头部高度及下边界对齐。头部、格式工具栏、内容区域保持原有顺序，正文与大纲列布局不变
- **快速切换与命令**：空的全局搜索展示账号最近至多 12 个 ID 中能读取的笔记（导航仍至多 6 篇），区分加载、空、部分失败和登录失效并可重试。去首尾空白后至少两个 JS 字符才检索文档，最多 500 字；命令按非空输入匹配。最多显示 6 处命中，同文档的不同片段分别保留服务端顺序、路径和定位信息，不压成一条。方向键与 Enter、鼠标遵守同一等待保护，组合输入确认前不检索或执行。
- **搜索动作交接**：新建、打开结果/最近笔记、返回库和带到新对话经过既有未保存保护；取消确认保留面板与原输入。新建确认后才单次发请求，成功后导航并聚焦正文；失败保留上下文。响应丢失不能承诺重试不会重复创建。AI 只有明确的“带到新对话”动作，沿当前 scope 预填、不自动发送，不自动附加当前文档。取消搜索回到可见入口，向编辑器或弹窗交接时由目标接收焦点。
- **双链**：Markdown 内链保存为 `[标题](/doc/<id>)`，文档 ID 是稳定目标。输入 `[[` 或使用链接工具可查找现存笔记并插入内链；正文链接可跳转，文档底部列出「来源」和「被引用」。不自动创建不存在的目标笔记

### 5.12 文件：两层可看，格式不是类型

上传的文件可以是任意格式，但它们共享同一条记录、同一套整理动作、同一次检索。
界面要回答的是「这个东西现在能看到多少」。

**直接看原件，没有层切换**（D-054：原先的 `正文 | 原件` 分段控件去掉了——
用户的原话是「不需要这个切换，直接就是原件」）。按「能不能真的看到东西」
分派：

| 情况 | 显示 | 为什么 |
|---|---|---|
| 有专用查看器（PDF / 图片 / 音视频 / Office） | 原件 | 那是文件本身的样子，也是编辑入口 |
| 没有查看器但提取出了正文（txt / csv / 旧版 doc） | 正文 | 文本文件的正文**就是**它的原样，别处看不到 |
| 两个都没有 | 说明卡片 + 下载 | 空白在那里等于说「这个文件是空的」 |

**提取结果没有消失**：它仍然可搜、可被 AI 引用。那才是它真正的用途——
「它讲了什么」这件事由**检索与问答**承担，不需要在详情里再占一层。

**提取失败或没有正文时必须说明原因，不能留白**（写在原件上方一行，
不挡路）。四种原因给用户的下一步完全不同：

```
这个格式还没有提取实现（如旧版 .doc）  → 「该格式的正文提取将在后续版本支持」
试过但失败了（编码不对/文件损坏） → 「提取失败：{具体原因}」
文件里没有文字（空文件/纯图片）  → 「文件里没有可提取的文字」
未知格式                      → 「原件已保存，可下载查看」
```

留白等于说「这篇没有内容」，而它其实有内容、只是还没提取——
与热力图把「用量未上报」画成斜纹而不是空底是同一条规矩。

**格式与大小是文件属性，不占用统一头部**：需要展示「PDF · 2.4 MB」时使用中性文字。
彩色徽标是**来源**的语义（笔记 / 网页 / 文件…），而格式是**属性**。
按「一格式一色」走下去，每加一种格式就要多一组色对——而格式是开放集合。

**筛选只按来源，不按格式**：胶囊固定六个（全部 / 笔记 / 网页 / 公众号 /
GitHub / 文件）。要按格式找用搜索或标签，不让筛选器随支持格式增长。

**GenOffice 支持的六种格式都有**（D-056 / D-057）：

| 格式 | 现在 | 之后 |
|---|---|---|
| `.md` | **上传即导入为笔记**，可编辑（正文进 vault，与手写笔记同一条路径） | — |
| `.html` | **源码 + 预览双栏**，改源码（CodeMirror），预览实时跟随（D-056） | 增量更新预览（现在每敲一个字整页重载）、点选改样式（上游 StylePanel 未接） |
| 纯文本 `.txt` 等 | 只读（正文就是它的原样） | — |
| `.docx` | **可编辑 + 完整分页视图**（块内断行、拆表、页眉脚、脚注；D-049、TECH §15.6） | 补页内分栏与更全的工具栏 |
| `.xlsx` | **网格预览 + 改单元格**（多表页签、合并单元格、行号栏；TECH §15.7） | 补行/列增删与公式重算 |
| `.pptx` | **幻灯片预览**（渲染成 SVG，文字可选中）+ **改文字与整段字形**（加粗/倾斜/下划线/删除线/上下标/字号/字体/颜色、查找替换；D-060、TECH §15.8–15.9）+ 左侧真实内容缩略图与新增、复制、删除、排序幻灯片 | 补元素位置（拖动改框）与段落格式（项目符号/行距/对齐） |
| PDF | **逐页渲染**（pdf.js）+ **页面级编辑**：旋转、新增、导入、复制、删除、调整页序（pdf-lib；D-057）；左侧显示真实内容缩略图 | **改文字**（PDF 的文字是内容流里的绘制指令，要 PDFium 的 7MB WASM）、M2 批注 |

PDF 与 PPTX 的缩略图均可点击跳页、拖动排序；页级复制、删除和键盘排序从缩略图右键菜单进入，菜单键或 Shift+F10 也可打开。最后一页不能删除，页操作后的主画布、页码和保存状态须立即同步。

**「替换原件」是编辑的现实路径**：下载 → 用外部工具改 → 传回。
没有它，用户只能删了重传——**而标签、目录、整理状态会全丢**。
替换时这些整理结果保留，正文与大小重算。

### 5.11 统计：热力图量的是 token，不是次数

格子记录的是**每次调用消耗的 token**（输入 + 输出），不是调用次数。

理由是这两件事不成比例：一次深度推理可能抵二十次摘要，而「我这个月花了多少」
比「我点了多少次」更常被问起。**代价必须写在明处**：它因此不再能回答
「我还在不在用」——那正是 §7 的成功判据。补法很便宜，tooltip 里同时给两个数：

```
9 月 23 日 · 12.3 万 token · 8 次调用
```

**颜色按 token，密度按次数。** 两个问题一次答完，不需要第二张图。

**格子有四个状态，不是一个色阶**：

| 状态 | 表现 | 为什么不能合并 |
|---|---|---|
| 无调用 | 空底 | — |
| 有调用、用量未上报 | 斜纹（**不是**空底） | 兼容端点不一定回传 usage。画成空等于说「我那天没用」，那是**静默的谎**——图在否认发生过的事 |
| 有用量 | 按分位着色 | — |
| 今天 | 进行中，图例注明「到今天此刻为止」 | 半天的数据看着像用量骤降 |

**分档按这一年的分位数，图例给出最深一档的真实区间**（如「最深一档 ≥ 12.3 万」）。
固定阈值在忙的月份全是最深色、闲的月份全是浅色，图就没信息了。
tooltip 里的真实数字才是可行动的那个——颜色只负责给出形状。

**范围固定一年，不做切换。** 第一版有 30 天 / 90 天 / 一年三档，
去掉了：概览那排（今日 / 本周 / 本月）已经回答了「最近怎么样」，
而这张图回答的是「这一年我在持续用吗」——它需要的正是一整年的形状。
顺带解决了一处解释成本：分位数是按范围算的，切范围会让同一个颜色
代表不同的数字，得在图例里额外声明一句。固定下来之后一档就是一个
确定的区间。

**补嵌入那天的尖峰不剔除。** 它比日常高一两个数量级，剔除能让曲线好看，
但会让「图表说 50 万、表格说 210 万」——这个项目最不能忍的就是两处各说各话。
尖峰照画，靠 tooltip 拆解来源（对话 / 摘要 / 嵌入）解释它。

**时区必须显式指定。** 容器默认跑 UTC，「昨晚 11 点」的消耗会算到前一天，
图整体左移一格且不报错。聚合按 `stats.timezone`（默认 `Asia/Shanghai`），
并在图旁标出当前时区。`at` 是 `timestamptz`，所以换时区只是换聚合方式，
历史数据自动跟着重算，不需要迁移。

### 5.13 生成可以随时停下

一轮提问要跑检索加模型，长的时候十几秒。**按钮上必须有一个「停」**：

- 生成中发送键换成**停止**（不是把输入区锁死：发送键此时本来就不该是「发送」，而 `disabled` 连焦点都拿不到，用户按不到 Esc、也看不到自己正在打的字）。输入框转**只读**，字还在、还能选中复制
- 输入框里的 **Esc 也能停**。中文输入法里 Esc 是取消候选词，所以判据要带上 `isComposing`（与 Enter 发送同一个判据）
- 停止后留一行「已停止生成 · 以上是已生成的部分」——半截回答留在屏幕上，用户需要知道它为什么停在这里
- **停止只 abort 本地请求**（SDK 不发任何服务端消息），半截回答**不保证落库**。所以界面不许诺「已保存」，这一轮也不再给动作条（见 §5.7）

### 5.14 消息区的滚动：贴底才跟随

会话是纵向的，回答是流式的。两条规则：

- **自己发出的新消息总是跳到底**（包括打开已有会话时跳一次）——那是用户做的一个明确动作，视线应该跟过去
- **流式内容只在贴底时跟随**（距底不到一行半）。向上读的时候，内容继续长不能把人拽回底部
- 离底时右下角出现一个「回到底部」小按钮，点它回到最新

不跟随的代价是多一次点击；跟随过头的代价是**用户永远读不了上面那句**——后者更贵。

### 5.15 桌面客户端：两种使用方式（修订，D-100）

桌面客户端支持**两种使用方式**，第一次启动时选一次，之后随时可在设置里换：

| 方式 | 数据在哪 | 登录 | 适合 |
|---|---|---|---|
| **本地使用** | 这台电脑（userData 下的 SQLite 与文件） | **不需要**——进入方式由客户端自己持有 | 一个人、一台机器；断网也完整可用 |
| **连接服务器** | 你自部署的 mimir 服务器 | 需要（与浏览器访问同一个账号） | 多台设备访问同一份知识库 |

**为什么本地模式不需要登录**：本机用户在第一次进入时自动建好（`local@mimir.local`），
客户端启动宿主时注入一把本机令牌，用户什么都不用填就进去了。这不是把服务
敞开——宿主只监听回环地址，令牌也不给浏览器里的网页。若从普通浏览器直接打开
那个本地端口，会看到一页说明并指回客户端，而不是一个永远填不对的密码框。

**切换的语义要说清（界面上也这么写）**：

- **不迁移数据**。本地与云端是两套独立的存储；「换成连接服务器」不会把本地
  数据传上去（那是同步，是另一个产品能力，见 §1 非目标）。
- **本地数据不会被删除**。切到云端后切回来，原来的东西还在。

**界面上的落点**：

- 首启的选择页：两个选项各写清「数据在哪、要不要登录、适合谁」，选云端时
  就地填地址并当场校验（连不上就说清原因，不写进配置）
- 设置 › 客户端：显示当前方式（本地模式下连数据目录一起显示——那是备份时
  该拷贝的路径），一个「更换使用方式…」回到选择页
- 本地模式下账号分区与左导航**不出现登出**（没有「登出之后去哪」），
  邮箱也不显示（本机用户没有可用的邮箱登录路径）

## 7. 成功判据

不自欺的判据只有一条：

> **连续用三个月，且第三个月打开的次数不低于第一个月。**

如果第一个月每天开、第三个月一周开一次，说明它退化成了收藏夹。届时要问的不是「怎么加功能」，而是「哪一环断了」。
