## Findings

### F13 — New note does not focus an editable field

- **Current path:** `packages/renderer/src/components/library/LibraryView.tsx:143-155` creates an empty note and navigates. The second creation path is `packages/renderer/src/routes/_app.tsx:322-335`. `DocumentPanel.tsx:763-790` mounts `NoteEditor` after a document query; `NoteEditor.tsx:163-178` mounts `@mimir/office` `MarkdownEditor`; `packages/office/src/editors/MarkdownEditor.tsx:315-347,512-516` creates Tiptap and `EditorContent` without a creation-specific focus request.
- **Smallest complete fix:** pass a one-shot focus intent from *both* create paths through navigation/app shell to the note editor, consume it only when the matching new document's Tiptap instance is ready, then focus the body (the audit's immediate typing case). Clear the intent after use. Never autofocus when opening an existing note or a search result, since that would steal reading/search focus. A title-first flow is another valid product choice, but it must be consistent across both entry points.
- **Dependency/decision:** The current URL has only scope/id (`_app.tsx:211-214`); a creation intent needs state outside persistent URL query or a clearly transient query value. Do not infer “new” merely from title `未命名笔记` or empty body.
- **Verify:** keyboard-create from library and Ctrl K; after editor is ready, `document.activeElement` is the contenteditable, immediate typing changes body and auto-saves once; opening existing and search-hit notes does not steal focus; remount/refresh does not replay focus.

### F14 — Document list disappears while editing

- **Current path:** `packages/renderer/src/routes/_app.docs.tsx` chooses `DocumentPanel` for a URL with id; `packages/renderer/src/routes/_app.tsx:211-214` navigates to that state. Sidebar `packages/renderer/src/components/nav/FolderSection.tsx:14-27` intentionally lists top-level knowledge bases only. `LibraryView.tsx:88-119,560-640` renders the browse list only in the library view.
- **Product conflict:** `.trellis/spec/project/product.md:220-242,248-255,297-301` explicitly chooses a two-column shell with full-main-area reading and rejects a persistent third-column document list. Thus adding a permanent file tree changes a recorded decision. The user's later “头部、工具栏和内容区域的三栏布局不能变” applies to the editor's three stacked regions/its body columns; do not silently replace the app shell.
- **Smallest aligned fix:** provide lightweight recent/open-note switching in the existing editor header or a compact popup, plus a clear current folder/breadcrumb cue, without a permanent side list. Make the active note identifiable when returning to the library. If tabs are chosen, define tab lifetime, close/reopen semantics, and unsaved guard behavior before coding. Full persistent tree/side list needs an explicit product decision and spec revision.
- **Verify:** open A, open B, return to A with keyboard and mouse without leaving the editor; current note and folder remain clear; no extra permanent column at 1280/880/600px; unsaved navigation still triggers the existing guard.

### F15 — Empty global search lacks recent documents

- **Current path:** `packages/renderer/src/components/CommandPalette.tsx:310-320` disables search for <2 chars; `:330-358` supplies only two commands plus search hits; `:465-489` documents that the old “最近打开” label was dead code. `packages/renderer/src/routes/_app.tsx:211-235` centralizes ordinary document/search navigation, but links/citations may have separate paths.
- **Smallest complete fix:** record a bounded, unique MRU list by document ID when a document is actually opened, then resolve live IDs/titles for the empty palette and render them after or before actions with the existing arrow-key selection model. Persist locally if “recently opened” should survive refresh; evict deleted/inaccessible IDs and deduplicate search-hit rows. Do not confuse server `updatedAt` (content modification) with opened order.
- **Product decision:** choose MRU lifetime/capacity and whether local-only storage is acceptable; product spec/design currently has no recent-doc contract. `.trellis/spec/project/product.md:220-242` supports quick switching without changing shell.
- **Verify:** A→B→A yields A,B in correct order when Ctrl K opens empty; arrows/Enter open selected item; refresh follows chosen persistence contract; deleted IDs disappear; empty-state actions and two-character search remain usable.

### F16 — Command palette covers too few commands and conflates no-match with AI question

- **Current path:** `CommandPalette.tsx:330-348` hardcodes only new-note and capture; `:350-358` merges commands/doc hits; `:386-404` executes highlighted item or routes no-match Enter to AI; `:495-520` says “没有匹配的文档” and still shows a “提问” action. `DocumentPanel.tsx:216-239,612-626` owns rename mutation and inline editable title. `packages/renderer/src/components/document/doc-menu.tsx:30-38` explicitly removed duplicate rename from the doc menu.
- **Smallest complete fix:** add context-sensitive command definitions for rename, move, find-in-note, and return to library, backed by callable app/document actions and disabled/unavailable states outside a note. Keep command result type separate from document hits and ask action. For a command-like query with no match, make Enter behavior explicit; best low-surprise approach is a separate, visibly selectable “提问 ‘…’” row instead of silently treating no match as a question. Avoid making keyboard rename depend on a DOM click of the pencil; expose a focused title edit action or controlled state at `DocumentPanel` boundary.
- **Decision:** product currently intentionally merges search, commands, and ask (`CommandPalette.tsx:14-20`); a new command mode/prefix is a product choice. The requested fix can preserve one input while making the action choice explicit. Rename command also deliberately conflicts with doc-menu uniqueness, so route it to the same inline edit behavior instead of adding a second rename form.
- **Verify:** command names match fuzzy/Chinese input, active document commands appear only in context, command Enter never sends an AI request, AI action is visibly selected before sending, Esc restores focus, and shortcuts shown remain accurate.

### F17 — No in-place note link discovery/completion

- **Current path:** `packages/renderer/src/editor/extensions.ts:19-44` has StarterKit Link but no wiki-link completion. `packages/office/src/editors/MarkdownEditor.tsx:871-955` link toolbar accepts only URL text and disables empty-selection linking. Backend `apps/server/src/services/links.ts:7-25,27-55` recognizes only Markdown `[title](/doc/<id>)` and stores outgoing links; `packages/renderer/src/components/document/DocumentFooter.tsx:17-65` displays backlinks. `NoteEditor.tsx:163-178` is the host adapter with access to API and document ID.
- **Smallest complete fix:** add a note-picker to the link toolbar that searches existing documents and inserts `[selected title](/doc/<stable-id>)` into the editor (including at a caret, not only a selection). Add `[[query` suggestion handling if the report's exact typing case is to be resolved; commit selection as the same ID-based Markdown link, not title-only syntax. Ensure clicking a rendered internal link navigates through app routing and unsaved guard; current Tiptap Link has `openOnClick: false` in `extensions.ts:25-30`, and no internal-link navigation handler was found in the inspected editor/body paths. Retain editable label after destination rename because ID is stable.
- **Dependencies:** A visual-only suggestion would leave backend backlink extraction empty. Link insertion must round-trip through Tiptap Markdown serialization and trigger `syncDocumentLinks`. A destination picker needs an API query; `api.search` is body-oriented and returns snippets, so title search/lookup behavior may need its own bounded query or client-visible note list. “Create missing note from [[…]]” is a separate choice; F17 can close with existing-note links first if scope explicitly says so.
- **Verify:** typing `[[mimir` yields matching candidate; keyboard selection inserts an ID link; save/reopen preserves it; source/backlink lists update; click follows link and Back/return restores prior document and position; nonexistent/deleted link target behavior is defined. Test Markdown parse/serialize, backend target extraction, and browser interaction.

### F18 — Folder position and move feedback are weak

- **Current path:** `LibraryView.tsx:322-338` intentionally holds the knowledge-base heading constant; `:459-507` shows a smaller `文档 / …` breadcrumb; `:584-640` lists folders and documents as peer rows with no document folder path. The API query is recursive: `apps/server/src/services/documents.ts:349-355` filters both exact folder and descendants, so flattening is not just CSS. `packages/shared/src/documents.ts:86-113` already gives each summary a `folder` value. `packages/renderer/src/components/document/doc-menu.tsx:110-141` moves documents by folder path; `DocumentPanel.tsx:230-239` performs the mutation but does not show a success/undo message.
- **Smallest complete fix:** display `doc.folder` relative to current knowledge-base/folder in list and card views, strengthen active breadcrumb/current folder typography, and show a move confirmation with destination. If undo is included as the audit recommends, capture the old folder and offer a short undo action that calls the same update API; ensure pending/failed states are represented. Keep recursive listing only if the path is visible; alternatively change list query to direct children, but that changes browsing semantics and may hide existing documents unexpectedly.
- **Product decision:** `.trellis/spec/project/product.md:297-301` deliberately keeps child folders in the library view rather than sidebar; F18 should improve orientation inside that model. Changing root heading to current folder conflicts with `LibraryView.tsx:322-327`'s documented knowledge-base identity distinction, so prefer strengthening breadcrumb/secondary heading unless spec is revised.
- **Verify:** root and multi-level folder views distinguish direct vs descendant documents, active location is obvious at 1280/880/600px, moving a note shows destination and immediate list result, undo restores original assignment if offered, keyboard breadcrumb works, no duplicate/confusing rows after move.

### F19 — Deletion text contradicts trash semantics

- **Current path:** `LibraryView.tsx:157-175` says `不可撤销：笔记会移入回收站，记录从库中移除。` Backend `apps/server/src/services/documents.ts:370-393` soft-deletes row and moves note file to `.trash`; `apps/server/src/lib/vault.ts:173-184` calls this recoverable. No in-app trash/restore route or component appeared in the inspected `apps/server/src/routes` / `packages/renderer/src` search. File upload deletion is different: `documents.ts:382-390` removes original upload content.
- **Smallest complete fix:** replace only the note copy with truthful, non-contradictory wording, e.g. “笔记将从知识库移除，文件保留在回收站。当前应用没有一键恢复入口。” Keep the file deletion warning distinct and verify it against actual upload deletion. A success toast should say what happened (“已移入回收站”), not generic “已删除”. Do not promise an in-app restore action until one exists.
- **Caveat:** backend comment says recoverable but current soft deletion plus trash file does not itself prove a supported end-user restore flow. If product wants the word “可恢复” without qualification, define and implement that flow first.
- **Verify:** note/file confirmation copy reflects distinct behaviors, cancel is safe, actual delete moves note to trash/marks row deleted, file deletion warning reflects physical original removal, no false “不可撤销” claim for note.
