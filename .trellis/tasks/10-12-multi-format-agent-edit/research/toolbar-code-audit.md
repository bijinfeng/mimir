- Query: Where do Mimir's DOCX, XLSX, PPTX, Markdown, HTML and PDF toolbars render, which commands are hidden, and how can an Office-style grouped ribbon expose them without changing edit semantics? Also locate persistent explanatory copy.

### Shared code patterns and scope

`EditorShell` owns a `toolbar` row and optional `subbar`, then body, optional footer and status; it renders toolbar and subbar in the same sticky `.mimir-editor__chrome` (`EditorShell.tsx:75-104, 140-180`; `shell.css:140-179`). Its primitive groups already carry accessible names (`EditorShell.tsx:343-358`). It uses antd `Button`, `Input`, `InputNumber`, `Select`, `Segmented`, `Popconfirm`, `Upload`, plus a local `ToolbarMenu` popup (`EditorShell.tsx:54-64, 296-339, 1472-1515`). `ConfigProvider` sets only small component size (`EditorShell.tsx:125-155`); keep existing theme variable bridge.

`CompactToolbar` measures the actual editor-column width with `ResizeObserver`, compares it with each section's `minWidth`, renders fitting sections inline and the rest in a `更多` menu (`CompactToolbar.tsx:16-21, 98-141`). The menu reuses the **same control tree** rather than separate handlers, preserving commands today (`:98`). Its CSS deliberately forces a single row and suppresses visible group captions (`compact-toolbar.css:1-38`); the section caption appears only inside the overflow popup (`:81-101`). The user-selected XLSX screenshot at 826px viewport shows only Find, Previous, Next and More in the editor column. This is consistent with XLSX `minWidth` gates, though actual content-column width was not measured in this audit. An Office-style design needs a tab selector row and a visible selected-tab command region, with grouped controls allowed to wrap/scroll within that region; merely changing thresholds leaves most commands buried. Keep `ToolbarMenu` for natural compound actions such as a font choice or insert type, but remove the blanket width-driven `更多` gateway.

The renderer adapter imports all five file editors from `@mimir/office` and renders each by kind (`OfficeSourceEditor.tsx:23-24, 155-196`); Markdown is likewise rendered from the same package in `NoteEditor.tsx:7, 216`. Therefore a ribbon implemented in `packages/office` is shared by Web and desktop renderer. Host APIs for edit execution remain adapter props (`OfficeSourceEditor.tsx:159-193`), so a UI change must not copy operations into the host or assume backend availability in every mode. Existing `onDirtyChange`, save and Agent handles stay attached to each editor.

### Persistent explanatory copy

The footer/status slots are structurally always available, but some editors use them as instructions. XLSX with no selected cell renders a whole footer solely for `点一个格子改它的内容；按回车应用，Esc 放弃`; status also always prints a formula-recalculation caveat and `编辑会保留单元格格式；图表、透视与多数工作簿操作尚未开放` (`XlsxEditor.tsx:774-838`). With a selected formula cell, the warning is contextual (`:819-824`) and should remain discoverable. PPTX with no selected object renders a footer instruction; with a selection it renders the paragraph editor and a long explanatory line. Its status always includes a general formatting/font/animation caveat (`PptxEditor.tsx:1785-1823, 1844-1854`), while geometry fallback warning is contextual and material (`:1833-1842`). HTML status says to click an element when preview is ready and no element selected (`HtmlEditor.tsx:1322-1332`). PDF footer is already only a dismissible failure notice (`PdfEditor.tsx:1424-1432`); DOCX uses notice only when present (`DocxEditor.tsx:1343-1354`); Markdown idle status does not fill with explanation (`MarkdownEditor.tsx:873-881`). The shared sticky status area can wrap and grow when copy is long (`shell.css:403-435`). Suggested boundary: status keeps concise live state, location/count and save; active-mode hints and disabled reasons appear next to the affected control, tooltip or contextual panel; compatibility/capability caveats live in contextual help or the action that triggers them. Do not discard warnings about a changed source's fidelity (e.g. PPTX geometry fallback).

The user's principle is **use interaction to explain intent**. Concrete replacements: clicking an XLSX cell reveals its address and editable formula/input row, Enter applies and Escape discards; direct ribbon groups show available cell/row/format actions, with disabled state and focus/hover reason instead of a standing paragraph. Selecting a PPTX object reveals contextual text/object controls and paragraph editor; no selection leaves the canvas unobstructed. HTML preview selection highlights the element and reveals its breadcrumb/actions. PDF text insertion switches to an active insertion mode with a cursor/point indicator and inline validation error. Keep short inline failures at the control or affected object. A consequential integrity warning remains visible **when its condition is true**, such as a formula about to be overwritten, a PDF write failure, or a PPTX text box shown at fallback geometry; general feature inventories do not occupy the status/footer.

### Regression and test boundary

- Add a shared ribbon/tab layout primitive in `packages/office/src/shell` or `editors`, then adapt the six editor toolbar compositions. Keep each format's existing command callbacks and save/dirty/Agent APIs. The current `CompactToolbar` test explicitly asserts commands move into More at 320px and back at 800px (`CompactToolbar.test.tsx:37-98`); this contract must be replaced with visible tab/command and keyboard/focus assertions, not left green by preserving More.
- Popup placement is sensitive to the AI sidebar narrowing **editor column** independently of viewport (`CompactToolbar.tsx:33-53`; `pptx-pdf-toolbar.css:63-85`; `shell.css:247-265`). Test with sidebar open, 826px-like viewport, 420px narrow viewport, and desktop/Web. Preserve `ToolbarMenu` pointer/keyboard handling, especially antd `Select` portal ownership documented in `.trellis/spec/office/frontend/shell/pitfalls.md`.
- Keep toolbar/subbar in one sticky chrome (`EditorShell.tsx:80-89`), retain `min-width:0` and vertical body space; DOCX formerly grew to nine rows at 420px (`shell.css:150-161`). A multi-row ribbon needs bounded height or horizontal scrolling, and must keep bottom Save visible. Group captions/labels are currently CSS-hidden in compact layouts, so visible headings require CSS and accessibility review.
- Preserve `ToolbarConfirm` for destructive PDF delete (`PdfEditor.tsx:1163-1178`) and existing `disabledReason` semantics (`EditorShell.tsx:329-335`). Do not infer execution parity from visible controls: XLSX grid itself says some new style/column width changes are written but not rendered (`XlsxEditor.tsx:655-667, 724-735`). Test command → dirty → save → reload/OOXML readback, not click alone.
- Relevant tests: shell primitives in `EditorShell.test.tsx`; responsive `CompactToolbar.test.tsx`; DOCX `docx-toolbar-render.test.tsx`; PPTX `PptxEditor.test.tsx`; PDF `pdf-toolbar-render.test.tsx`; XLSX `XlsxEditor.test.tsx`; Markdown `packages/renderer/src/editor/MarkdownEditor.test.tsx`; HTML `HtmlEditor.test.tsx`. Include actual browser visual and keyboard checks because DOM-only tests have no real editor-column measurements (`CompactToolbar.tsx:107-119`).

## Caveats / Not Found

- This is a code audit, not a live Office/GenOffice visual comparison or implementation. No UI code was changed. The browser screenshot is user-provided page evidence; its viewport width is not necessarily the editor-column width after navigation and AI panes.
- The pinned GenOffice inventory lists many operations Mimir does not yet expose. Ribbon layout and complete editing capability are separate acceptance dimensions; do not mark either finished solely because commands become visible.
