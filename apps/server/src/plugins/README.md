# 插件接缝

这里的「插件」指**内部接缝**，不是第三方插件市场。区别很大：

| | 外部插件市场 | 内部接缝（这里） |
|---|---|---|
| 是什么 | 公开 API，别人能写插件 | 代码按接缝组织，加实现＝加文件 |
| 要付出 | 版本化 API、兼容承诺、文档、沙箱、权限 | 一个注册表 + 一份接口定义 |

本项目的目标是「代码好维护」，对应的是第二种。做成第一种会引入比它解决的问题更多的负担。

## 四条接缝

| 接缝 | 输入 → 输出 | 已有实现 | 规划 |
|---|---|---|---|
| `capturer` | URL / 文件 → 统一 Markdown + 元数据 | 粘贴链接、公众号、GitHub | RSS、Star 同步、扩展 |
| `parser` | 原始内容 → 结构化文本（保留页码/偏移） | Markdown、HTML 正文提取 | PDF、Word |
| `leg` | 查询 → 已排序的文档 id 列表 | 关键词、子串兜底 | 向量、重排序 |
| `provider` | 任务 → 模型调用 | DeepSeek、通义 | 智谱、Ollama |

## 推进规则：先别造框架

**按接缝组织代码，等第二个实现出现了再抽接口。**

理由：`capturer` / `parser` / `provider` 现在一条实现都还没有。凭想象设计接口，
八成会把参数集设计错，然后每加一个实现都要改接口——比不抽还累。

具体顺序：

1. 定接缝的**边界**（上表）
2. 第一个实现直接写，不抽接口
3. 写第二个实现时，从两者的共同点**反推**接口
4. 接口稳定到第三个实现，才算定型

## 目前只有 `leg/` 走完了这个流程

所以这里把它定型了——**它是样板，其余三条接缝照这个模式走**。
