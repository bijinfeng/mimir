## D-001 中文检索用 jieba 预分词

**背景**：Postgres 对中文没有词边界概念。`simple` 配置会把「组件性能优化」
当成一个 token，用户搜「组件」永远搜不到。

**决定**：写入时用 `@node-rs/jieba` 分词，以空格连接存进 `documents.search_text` 列，
在该列上建 GIN 表达式索引。查询串用同一套分词切分后交给 `plainto_tsquery`。

**否决**：

| 方案 | 为什么不用 |
|---|---|
| `Intl.Segmenter`（Node 内置） | 实测把「组件」切成「组/件」、「纪录片」切成「纪录/片」，质量不达标。零依赖但不可用 |
| ParadeDB 的 `chinese_lindera` | 一个索引同时给 BM25 排序和中文分词，比本方案干净。但 Community 版是 **AGPL-3.0**。个人自用无约束，但会成为一个需要解释的依赖 |
| 自建带 zhparser 的 Postgres 镜像 | 能省掉 Node 侧分词，但要多维护一个镜像构建，SCWS 词典还要单独装 |
| `pg_trgm` 直接作用于原文 | 实测相似度只有 0.32，且没有词边界概念 |

**影响**：所有全文索引都必须建立在这个列上。查询侧必须用同一套分词，
两边不一致会静默搜不到。子串兜底通道是分词切错时的补救，不是替代。

## D-002 AI SDK 选 TanStack AI

**背景**：候选三个——`@earendil-works/pi-*`、`@deepseek-ai/dsh`、`@tanstack/ai`。

**决定**：用 `@tanstack/ai` 0.55.0。

**否决**：不是因为另外两个质量差，而是**它们不是同一类东西**。

| 方案 | 实测情况 |
|---|---|
| pi-agent | 是 CLI/TUI 编码 agent 工具箱。`pi-ai` 本身不错（支持国产模型、有成本追踪），但**没有 embedding、没有 rerank**，也没有任何 Web 应用侧脚手架。README 明确说「不包含权限系统」——为本地命令行场景设计 |
| deepseek-harness | **是完整应用不是库**。主包只有 `bin` 字段，没有 `main`/`exports`。架构是 Cordis 插件树，全部子包 `0.0.1-rc.1`。README 明确写着「developer preview，将有不兼容变更」 |
| TanStack AI | 唯一为「嵌入到自己的应用里」设计的。能力拆成可 tree-shake 的 activities，含本项目需要的 chat / embed / rerank |

**影响**：0.x 版本 + 周更，锁死精确版本。两个已知边界见 `TECH.md` §5.2
（`openaiCompatible` 只覆盖 chat；rerank 适配器路径写死）。

## D-003 RAG 不引入框架，检索层自建

**背景**：调研了三个层次的方案。

**决定**：检索层就是约 100 行 SQL 加一个分词函数，模型调用交给 TanStack AI。

**否决**：

| 方案 | 实测情况 |
|---|---|
| RAGFlow | 91k★，Apache-2.0。但最低 **4 核 / 16GB 内存 / 50GB 磁盘**，编排拉起 ES/Infinity + MySQL + MinIO + Redis + NATS + ClickHouse。引用是它自己 UI 里的引用 |
| Dify | 156k★，修改版 Apache **含商业限制条款**。是平台不是库 |
| Mastra RAG | 分块器与 reranker 不错，但 `@mastra/core` 是 peer 依赖（31 个直接依赖），`@mastra/pg` 会接管向量存储，与自己的 Drizzle schema 形成两个真相源 |
| LlamaIndex.TS | `@llamaindex/postgres` 是 **0.0.66**，依赖 `pg-promise`——又一个 PG 驱动并存 |

**共同问题**：它们都想接管文档与分块的数据模型，而本项目必须让引用能指回自己的表。

**影响**：检索质量完全由自己负责。参数（RRF k、各通道权重）暴露在设置页里，
最终要按自己的语料调。

## D-004 布局三栏，导航会话优先

**背景**：原型阶段比较了三种布局与两种导航结构。

**决定**：三栏（左导航 / 中列表 / 右内容），左栏会话历史排在文档入口之前。

**否决**：

- **单栏 + 强命令面板**：最专注，但发现性差——不记得存过什么时连「翻一翻」都做不到。
  而「想不起存过什么」正是个人知识库的头号问题
- **文档优先导航**：写笔记是主要活动，听起来更合理。但用户明确选了会话优先

**影响**：这个决定改变了**中栏的语义**，不只是排序：

| 模式 | 中栏 | 右栏 |
|---|---|---|
| 对话 | 本次引用了哪些文档 | 对话 |
| 文档 | 文档列表 | 阅读 / 编辑 |

会话优先意味着「问答」是主场景，那么**「它读了什么」就该和「我有什么」一样可见**。

## D-005 编辑器用所见即所得，接受非无损

**背景**：Tiptap 会按自己的规范重写 Markdown。实测表格会被补齐列宽。

**决定**：只用所见即所得，不做源码模式。

**否决**：源码 + 预览分栏（对技术内容更精确，但写的时候要脑内渲染）。

**关键实测**（`apps/web/src/editor/drift.test.ts`）：

```
输入      | 1 | 2 |
首次保存  | 1   | 2   |   被整理成编辑器的规范形
之后每次  | 1   | 2   |   不再变化
```

**不是无损的，但是幂等的。** 这个区别决定了适用边界：

- **可以**作为唯一编辑器——内容不会逐次劣化
- **不要**用 Obsidian / VS Code 改同一批文件——两边各有一套规范形

正文、标题、列表、代码块、引用、链接往返逐字节一致；表格是唯一被重排的结构。

## D-006 删掉 AI 侧栏

**背景**：侧栏原本是「不离开阅读位置就能问当前文档」。

**决定**：删掉。AI 只有一个入口——主视图对话。

**理由**：侧栏被两头夹掉了。

- 问某一段 → 内联工具条的「就这段提问」，锚定选中内容，更精确
- 问整篇 → 主视图对话 + 范围选「当前文档」

侧栏的范围比内联宽、比主视图窄，两边都不如。代价是 392px 屏幕和一个要维护的面。

**删除后补的三件事**（不做这些会让「问当前文档」比以前更难）：
文档工具条的「问 AI」带上下文进主视图；内联「就这段提问」预填引用；
**「返回对话」入口**——从对话点引用跳去文档后，没有它用户会以为对话没了。

## D-007 插件架构指内部接缝，不是外部市场

**背景**：「插件架构」在实践里指向两种成本差一个数量级的东西。

**决定**：只做内部接缝（代码按接缝组织，加实现＝加文件）。

**否决**：外部插件市场（公开 API、版本化、兼容承诺、沙箱、权限模型）。
那是为有生态野心的产品准备的，对个人项目会引入比它解决的问题更多的负担。

**推进方式：先别造框架。**

四条接缝的边界已定（capturer / parser / leg / provider），但只有 `leg` 有
两个实现，所以只有它抽了接口。**规则：等第二个实现出现，从共同点反推接口。**
凭想象设计接口八成会设计错。

## D-008 共享包以编译产物发布

**背景**：`@mimir/shared` 最初以源码形式发布（`exports: "./src/index.ts"`）。
开发时正常（tsx/vite 会处理），生产容器启动直接报：

```
ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING
```

Node 拒绝从 `node_modules` 里剥离 TypeScript 类型。

**决定**：编译到 `dist` 以产物发布，构建顺序固定为 shared → web/server。

**影响**：这是**在 Docker 构建时才暴露**的问题——本地开发完全正常。
教训：声称能部署就得真的构建并运行一次。

## D-009 开启 React Compiler

**背景**：编辑器组件持有大量状态，手写记忆化的依赖数组很容易写错。

**决定**：通过 `@vitejs/plugin-react` 的 `compiler` 选项开启，并保留
`logDiagnostics: true`。

**否决**：`babel-plugin-react-compiler` 与 `@rolldown/plugin-babel`。
它们是插件的 optional peer，但属于**另一条路径**（单独导出的
`reactCompilerPreset`）；`react({ compiler: true })` 只动态导入
`oxc-transform-react`。

**验证方式不是读文档，是逐字节对比**：删掉那两个包的声明前后，
构建产物完全一致（805393 字节，`cmp` 无差异）。

**影响**：不要手写 `useMemo` / `useCallback` / `memo`；不要抑制 React 规则
（会让编译器跳过整个组件）。

## D-010 工具链用 oxc，版本集中管理

**背景**：需要 lint + format，以及跨包版本一致性。

**决定**：oxlint + oxfmt；依赖版本进 pnpm catalog。

**否决**：

- **ESLint + Prettier**：lint 跑得慢的直接后果是没人跑。oxlint 单命令跑全仓约 100ms
- **oxfmt 格式化 Markdown**：它按字节算列宽，中文表格会被补齐得更难读。
  排除 `**/*.md`——Markdown 是内容不是代码

**catalog 的主要价值不是去重**，而是让「必须版本一致」成为结构保证：
`@tiptap/*` 有 10 个包，版本错开会冲突 ProseMirror schema，
而这类错误报得晚、很难查。

**补充（同 D-011 同批）**：`.agents/**` 也排除出 oxfmt。那是 vendored 的第三方
skill（由 `skills-lock.json` 锁定哈希），`.claude/skills`、`.zcode/skills`、
`.trae/skills` 都只是指向它的符号链接。格式化它们会让下次同步 skill 时冲突，
而且它们不是我们的代码——和排除 `**/*.md` 是同一类判断：排除内容，不排除代码。

## D-011 设计规范以 Ant Design 为底，但覆盖语义色与文字阶

**背景**：前端已有 antd 6 与一个交互原型（`output/index.html`），但两边各有一套
视觉值——原型有自己手挑的灰阶和状态色，antd 有它的默认值。`main.tsx` 里只配了
主色/圆角/字号三项，其余全走默认。需要一份统一的设计规范，否则每做一个页面
都要重新决定一次「这个灰用多少」。

**决定**：以 Ant Design 的体系为骨架（4px 网格、字体阶、圆角语义、动效三档、
三层表面模型、主色 `#1677ff`），但**覆盖两处**：

1. **语义色改用原型那套深阶色**，且以叶子 token 形式覆盖
2. **文字阶改为不透明色**（`#1c1c1c` 系派生 → `#5c6570` / `#68707c`）

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 全盘接受 antd 默认 | 实测它的语义色在自家浅底上不达 AA——successText on successBg 只有 **2.21:1**、warning **1.83:1**、error **2.99:1**。这些色是给图标和边框设计的，不是给文字。三级文字（`rgba(0,0,0,.45)`）也只有 2.75:1 |
| 替换 antd 的**种子色**（`colorSuccess: '#137333'`） | 实测会派生 `colorSuccessBg: '#a8b3aa'` 这种灰绿脏色。派生算法假定种子是亮色，改种子会让整套派生色一起跑偏且方向不可预测 |
| 不用 antd，自建一套 token | 组件库已经定了（`apps/web/AGENTS.md`：样式走 antd token，不新引入 CSS 方案）。自建的 token 与 antd 的派生体系并存，等于两套真相 |
| 照搬原型 CSS 变量原文 | 原型是单文件手写 CSS，没有主题体系也没有深色模式的余地；它的**值**是对的，**结构**不能搬 |
| 只覆盖主色，其余留默认 | 那就等于放弃了「状态必须看得见」这条原则（`PRD.md` §5.9）。一个看不清的「保存失败」比不提示更糟 |

**关键实测**：覆盖成叶子 token 后，四组语义文字色对全部达标——
成功 5.24:1、警告 4.58:1、错误 5.48:1、信息 5.78:1。文字阶在四种底
（容器/列表/导航/布局）上也全部 ≥ 4.5:1。这些数字进了
`apps/web/src/theme/design.test.ts`，会被真正计算而不是写在文档里。

**在真实浏览器里验证时又发现三处**（只看代码看不出来）：

1. **`<App>` 包装层会断掉 `height:100%` 的链条**——`.ant-app` 默认没有高度，
   登录卡片因此不垂直居中，`Layout height:100%` 只撑到内容高度。不报错，
   只是布局不对。已在 `global.css` 补 `#root > .ant-app { height: 100% }`
2. **antd v6 的 `<Tag bordered={false}>` 已废弃**，正确写法是 `variant="filled"`
3. **列底色定义了却没用上**——规范说好的三栏靠底色区分，但页面里没人引用那两个
   变量。补齐后才真正生效（实测 `#fbfbfc` / `#fcfcfd`）

**影响**：

- `theme/tokens.ts` 是 token 的唯一真相来源，`main.tsx` 只负责接线
- **不要替换 antd 的种子色**，只覆盖叶子 token（原因见上）
- **不要把 `colorPrimary` 当文字色用**——它在选中态浅底上只有 3.61:1。
  文字角色走 `colorLink: #0958d9`（≥ 5.41:1）
- 字体栈只有一处定义（`global.css` 的 `--mimir-font-sans`），`tokens.ts` 用
  `var()` 引用它，避免两处字体栈漂移
- **来源徽标不要用 `<Tag color="green">` 预设色**——预设走 antd 自己的调色板，
  对比度不由我们控制。色对收在 `components/DocumentBadges.tsx`
- 改了 token 导致 `design.test.ts` 红了，**改设计不改断言**

**未做的部分**：深色模式。antd 有 `darkAlgorithm`，但列底色、内容区排版、
来源徽标都需要在深色下重新校准。半成品的深色模式比没有更糟，仍列在
`PRD.md` §6 待决项。

**后续（D-012）**：本条的**视觉决定全部不变**（不换种子色、文字走 `colorLink`、
语义色成对、来源徽标不用预设色）。变的是落地方式——样式从手写 `global.css`
改为 antd-style 的 `createStyles` / `createGlobalStyle`，因此文中「字体栈定义在
`global.css` 的 `--mimir-font-sans`」与「列底色是 `--mimir-*` 变量」两处已过时：
值相同，位置改到 `theme/tokens.ts` 与 `theme/customToken.ts`。

## D-012 样式方案采用 antd-style，取代手写 CSS 文件

**背景**：D-011 定下「以 antd token 为底」，但落地方式是一份手写的
`styles/global.css` 加页面里的内联 `style`。这套做法在页面只有两三张时看不出
问题，往后会分叉出三类麻烦：

1. **内联 style 越来越多**。`routes/docs.tsx` 一个文件里就有九处内联样式，
   条件态（选中项）只能写成三元表达式，颜色和布局混在 JSX 里
2. **`:root` 与组件之间要来回倒变量**。字体栈、列底色定义在 `:root`（因为
   `--ant-*` 注入在 antd 的 DOM 子树上，`:root` 拿不到），组件再 `var()` 引用。
   一个值在两处出现，改一处忘一处就漂了
3. **没有类型**。`var(--ant-color-text-tertiary)` 拼错是运行时静默失效——
   颜色不对但不报错

**决定**：引入 antd-style（`createStyles` / `createGlobalStyle`），把样式写进
组件旁边的 `.style.ts`，token 从 `createStyles` 的入参直接取。

四件事随之调整：

1. **字体栈从 CSS 变量变成 TS 常量**（`tokens.ts` 的 `FONT_SANS` / `FONT_MONO`）。
   原先用 `var(--mimir-font-sans)` 是为了让 `:root` 与 antd token 共用一份值；
   现在 `createGlobalStyle` 能直接读 theme，间接层没有存在意义了
2. **列底色、行内代码色、高亮底改走 `customToken`**，不再有 `--mimir-*` 变量
3. **内容区排版（`.note-body`）搬进 `NoteEditor.style.ts`**。它管的是编辑器渲染
   出的裸 DOM，是一个组件的样式，就该有作用域
4. **provider 栈抽成 `MimirProvider`**，让守门测试能渲染和线上完全一样的结构

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 保持现状（global.css + 内联 style） | 见背景三条。现在改的成本是 6 个文件，等页面铺开之后再改成本是全部文件 |
| Tailwind | 与 antd token 体系是两套心智：Tailwind 的 `bg-blue-500` 不认识 `colorPrimaryBg`，要用就得把 token 映射成配置，从此主题值有两处真相。且 D-011 已定「不引入第二套方案」 |
| CSS Modules | 能用 token，但要靠 `var()` 字符串，回到「拼错不报错」。而且它解决的是「作用域」这一个问题，antd-style 同时给了类型、token 访问和动态主题 |
| styled-components | 多 10KB+ 体积（antd-style 官方对比数据）；且它把样式绑在组件上用，而 mimir 大量场景是「给已有 antd 组件加类名」，`createStyles` 更贴 |
| 只迁移页面、不动 `global.css` | 字体栈与列底色会留在 `:root`，`--mimir-*` 与 `customToken` 并存——正是要消掉的那种两处真相 |

**关键实测**（`design.test.ts` 里会真跑）：

- **`ConfigProvider` 内层不能再传 `theme`**。antd 的 `useTheme` 会在传入 theme 时
  用新的 `useId` 重算 `cssVar.key`，`--ant-*` 的变量名随之改变（实测类名从
  `.mimir` 变成 `.css-var-r1`）。不传时 antd 直接继承外层 theme 的 key。
  **这是静默的**：不报错，只是所有引用变量的地方颜色不对
- **`colorFillSecondary` 是半透明的 `rgba(31,35,41,0.06)`**，算行内代码对比度时
  必须先合成到底色上。不合成直接算会得到 2.86:1 这种把黑色当底色的假结果；
  合成到白底实际是 4.93:1
- **`createStyles` 的嵌套选择器能穿透 Tiptap 渲染的裸 DOM**。实测 `.tiptap` 的
  `h1` / `pre` / `th` / `code` 全部命中且带作用域，`createGlobalStyle` 里的
  `#root > .${prefixCls}-app` 高度链也正常注入

**影响**：

- **组件样式一律走 `createStyles`**，不新增 `.css` 文件，全局样式只有
  `styles/global.ts` 一个出口
- **`ConfigProvider` 只负责 locale**，主题归 `ThemeProvider`——重复传 theme 会
  静默换掉变量名
- **`createGlobalStyle` 里拿不到 `--ant-*`**，要用 `${(p) => p.theme.xxx}` 取主题值
- **覆写 antd 组件内部结构时用 `${prefixCls}`**，不写死 `.ant-`
- 字体栈的唯一真相来源改为 `tokens.ts` 的 `FONT_SANS` / `FONT_MONO`
- 列底色等四个值的唯一真相来源改为 `theme/customToken.ts`

**顺带修的**：`vitest.config.ts` 原先没有 `@` 别名（只有 `vite.config.ts` 有），
一旦测试要 import 用 `@/` 的模块就会失败。现在两个配置从 `alias.ts` 取同一份定义。

## D-013 对话 UI 与状态交给 TanStack AI 的 React 层

**背景**：M0 把原型的三栏界面接上真实后端时，对话部分最初是手写的——
自己维护消息数组、自己拼流式 token、自己做乐观追加与错误回退。
写完之后发现：这套东西与 TanStack AI 提供的 `useChat` 几乎逐条重合，
而手写版在细节上更差。

**决定**：对话的**消息状态与流式接收**用 `@tanstack/ai-react` 的 `useChat`；
**消息渲染**用同一包的 `createChatUI`（`@tanstack/ai-react/ui`）。
服务端走 AG-UI 协议（`toServerSentEventsResponse`）。

这一层只保留四件 SDK 不该知道的事：

1. 会话 id 的维护（新建会话、切换会话）
2. 把服务端推来的 `trace` / `citations` 自定义事件收进 state
3. 结束后让 TanStack Query 的会话与文档列表失效
4. 把引用回传给中栏

**为什么手写的更差**（实测）：

| 方面 | 手写 | `useChat` |
|---|---|---|
| 流式 token 拼接 | 自己攒 `delta`，顺序与去重都要自己保证 | 按 part 累积，协议层处理 |
| 并发发送 | 要么禁用输入、要么丢弃 | 内置排队（`whenBusy: 'queue'`），可取消 |
| 中断清理 | 容易漏掉「停止后残留的 loading」 | `stop()` / `status` 由客户端维护 |
| 消息渲染 | 自己写 markdown 渲染 | `TextPart` 自带流式 markdown 解析、HTML 转义、代码高亮入口 |

最后一行尤其重要：自己写 markdown 渲染意味着要自己处理**流式过程中的
半截语法**（`**` 只到了一半），以及 XSS 转义。`TextPart` 这两件都做了。

**两个必须踩对的接口细节**（都写进了代码注释）：

1. **`initialMessages` 只在挂载那一刻生效**。`useChat` 把客户端建在
   `useMemo(..., [])` 里，之后传的变化不会重新灌入。所以打开历史会话时
   必须**等数据取回再挂载**对话体，用 `key={conversationId}` 保证切会话时重建。
   先挂载再补数据的症状是：右栏一直空白，而中栏的「本次引用」正常显示——
   两栏说的不是同一件事
2. **会话 id 放在请求体（`forwardedProps`）而不是 URL**。`useChat` 在
   connection 变化时会重建 ChatClient，**重建会切断正在进行的流**。
   代价是新建会话时客户端不知道 id，所以服务端用 `mimir.conversation`
   事件回传

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 继续手写消息状态 | 见上表。而且它已经出过一次错：历史会话打开是空的 |
| 只用 `useChat`、不用 `createChatUI` | `createChatUI` 提供 part 分发与空/加载/错误态，自己写一遍又是一轮重复 |
| 用协议原生的 `THINKING_*` part 承载检索过程 | 它只是一个字符串，而 trace 是结构化的分步记录（每步带图标、关键词、具体数字）。塞进字符串就得在两端各写一遍序列化 |
| 把 citations 也做成自定义 part | 引用卡片是「本轮的结果」，横跨整列渲染（PRD §5.2），不是消息流里的一个片段。做成 part 反而要跟它的位置较劲 |

**影响**：

- `lib/use-mimir-chat.ts` 是对话状态的唯一入口；组件不直接碰 `useChat`
- 服务端的流式端点固定为 `/api/chat`，**路径里不含会话 id**
- 自定义事件名（`mimir.trace` / `mimir.citations` / `mimir.conversation`）
  定义在 `packages/shared`，前后端共用——两边各写一遍字符串，
  打错一个字母是静默失效
- 非流式的 `POST /api/conversations/:id/ask` 保留：测试与 curl 用它，
  且与流式版共用同一套检索

**顺带发现的检索缺陷**（D-014 单列）。

## D-014 检索的召回门槛：从 AND 到「至少命中一半」

**背景**：把界面接上真实检索后，用自然语言提问全部返回 0 条——
「React 重渲染范围怎么缩小？」在知识库明明有对应笔记时也搜不到。

**根因**：关键词通道用 `plainto_tsquery`，它把所有词用 **AND** 连起来，
要求每个词都出现在同一篇文档里。四个词里有一个没出现就全盘落空。

**决定**：改成「**命中的词数 ≥ 查询词数的一半**」（向上取整，至少 1 个），
排序仍交给 `ts_rank_cd`（命中的词越多、越集中，排得越前）。

配套两处调整：

1. **子串兜底通道改为逐词匹配**。原实现拿整条查询串去 `ILIKE '%...%'`，
   对「向量检索」成立，但对一句话提问**永远不可能命中**——没有任何正文
   包含那整句话。这个「兜底」在真正需要它的场景里恰好是失效的
2. **新增查询侧过滤 `queryTokens()`**：去掉纯标点、单个汉字、疑问词与结构助词。
   它们不承载检索意图，却会抬高命中门槛

**为什么不是纯 OR**：中途试过全部 OR，`zzzz不存在的内容zzzz` 这类无意义
查询立刻返回十几条（「内容」出现在太多文档里）。**纯 AND 太窄、纯 OR 太宽**，
门槛值落在中间。

这条也**免掉了停用词表**：门槛挡住了「只有通用词命中」的文档，
不需要再维护一份「哪些算通用词」的清单——那份清单永远不完整。

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 保持 AND | 自然语言提问全 0 命中，已在浏览器里复现 |
| 纯 OR | 无意义查询返回噪声，测试 `无结果时返回空列表而不是报错` 立刻变红 |
| 引入停用词表 + 纯 OR | 要维护一份永远不完整的词表；门槛已经解决了同一个问题 |
| 把子串通道的门槛放宽到「命中任意一个」 | 试过，同一个测试变红。**兜底不等于不设门槛** |

**影响**：

- `plugins/leg/keyword.ts` 与 `plugins/leg/substring.ts` 的门槛必须一致，
  否则融合层会把两个通道的偏好混在一起
- `lib/segment.ts` 新增 `queryTokens()`。**只用于查询，不用于索引**——
  索引侧必须保留全部词元，删掉会让短语子串匹配失效
- `search.test.ts` 新增 3 个回归用例，覆盖自然语言提问、部分词匹配排序、
  以及 tsquery 语法字符的安全性

## D-015 编辑器的状态也交给 `@tiptap/react`

**背景**：`NoteEditor` 一开始用命令式的 `new Editor()` 手写实例管理，
为此需要三个「必须靠注释提醒自己」的约束：

1. 回调里读的 `title` / `onDirtyChange` 要用 ref 承接（否则闭包读到过期值）
2. 那些 ref 必须**声明在使用它们的 effect 之前**，否则 React Compiler
   静默跳过整个组件的优化
3. 初始正文要用 `useState` 的惰性初始化而不是 `useRef`——渲染期读 ref
   会让编译器拒绝优化（`react(refs): Cannot access refs during render`）

**决定**：改用 `@tiptap/react` 的 `useEditor` + `EditorContent`。

`useEditor` 把传入的**每个回调都包一层**、从 `options.current` 读取，
所以回调里直接写 `save` 和 `title` 就行，那三条约束全部消失。
它的 `deps` 传空数组时只 `setOptions` 而不重建实例，正好满足
「保存回写不丢光标」这个要求。

**为什么不用 `Tiptap` + `useTiptap()` 那套 provider**：
`BubbleMenu`（来自 `@tiptap/react/menus`）接受 `editor` prop 直接传实例，
不需要 provider。少一层 context 就少一处「provider 与实例不同步」的可能。

**影响**：

- `NoteEditor` 从 260 行降到约 230 行，且不再有 ref 声明顺序的隐式约束
- 内联工具条用官方的 `BubbleMenu`：跟随选区、滚动重算、边缘翻转、
  点工具条不取消选区这四件事它都处理好了。自己算 `getBoundingClientRect`
  会在长文滚动、换行选区、触屏这三个场景出错
- 工具条里的控件仍是 antd（`Button` / `Divider` / `Tooltip`）——
  BubbleMenu 只管浮层的位置与显隐，里面放什么由我们决定

**顺带修的三个真实缺陷**（都是浏览器实测发现的，测试没覆盖到）：

| 症状 | 根因 |
|---|---|
| 点「问 AI」/「就这段提问」没有任何反应 | 只 `setAskDraft` 而没 `navigate`，草稿存下了但界面没换 |
| 打开历史会话右栏空白，而中栏的「本次引用」正常 | `useChat` 只在挂载那一刻读 `initialMessages`，先挂载后补数据不生效 |
| 新会话提问后右栏什么都不显示 | 建会话 → 写 URL → key 变化 → 重挂载，把刚收到的流丢了。用 `ownedId` 区分「自己建的」与「切换过去的」 |
| `FailureCard` 写好了但永远是空的 | 从未被渲染；且模型连接错误**不会抛出**，而是以 `RUN_ERROR` chunk 顺着流发出来，只写 `try/catch` 的话 catch 根本不执行 |

最后一条值得单独记：适配器把连接类错误转成 chunk 而不是异常，
所以「每类失败给不同出路」的分支必须同时看 chunk 与 catch。
只处理异常会让这个特性完全失效，而且不报错。

## D-016 失败分类由服务端给出

**背景**：前端要按失败类型选出路（额度用尽 / 超时 / 被截断 / 网络不可达），
它得先知道是哪一类。

**决定**：服务端在流里推一个 `mimir.failure` 自定义事件，带分类与原文；
前端只管按分类选出路。

**为什么不让前端猜**：**分类依赖服务端的知识**——HTTP 状态码
（402/408/429）、原始错误文本。前端只看到一句被规范化过的 message，
按字符串猜会得到「认不出来就当成超时」这种反复漂移的逻辑。

**事件的顺序**：`conversation → trace → citations → 正文`，
失败时是 `… → trace（带完整耗时）→ failure → RUN_ERROR`。

**两条时序约束**（都是实测踩出来的）：

1. **trace 发两次**：第一次在模型之前（只有检索耗时，但必须抢在模型前
   才能显示「正在检索什么」），整轮结束后再发一次带完整耗时的覆盖它。
   否则界面上永远显示「耗时 0.0s」——用户以为什么都没做
2. **失败前也要补一次 trace**：失败同样是「这一轮结束了」

**影响**：

- `packages/shared` 的 `EVENT_FAILURE` 与 `FailureEventPayload` 是前后端
  唯一的真相来源，两边各写一遍字符串的话，打错一个字母是静默失效
- 落库的消息也带 `failure`，所以刷新后能重放同一条失败卡片

## D-017 字号收进阶梯，不再逐处硬编码

**背景**：用户反馈「页面太粗糙」。查下来最根本的一条是——全仓散落过
**11 个不同的 font-size**（10 / 10.5 / 11 / 11.5 / 12 / 12.5 / 13 / 13.5 /
14 / 15 / 16），而同一个**角色**在不同页面用了不同值：

```
元信息（时间戳、计数）  文档页 12.5px，列表页 11.5px，导航 11.5px
```

这不会报错，只会让整页看起来不整齐——用户说不清哪里不对，但会觉得粗糙。
字号是最容易被随手改的样式，因为它看起来无害。

**决定**：`theme/tokens.ts` 导出 `FONT_SIZE`，九档，**每档对应一个角色**
而不是「差不多大就用它」：

| 档 | 值 | 角色 |
|---|---|---|
| `display` | 28 | 文档标题 |
| `pageTitle` | 19 | 正文 H2、设置页 H1 |
| `section` | 16 | 正文 H3、卡片标题 |
| `body` | 14 | 按钮、输入、对话正文 |
| `item` | 13.5 | 列表项标题、导航项（被**扫读**的） |
| `excerpt` | 13 | 摘要、表格、代码 |
| `note` | 12.5 | 次级说明、引用片段、检索过程 |
| `meta` | 12 | 时间戳、路径、计数 |
| `badge` | 11.5 | 徽标、计数（有底色衬托） |

取原型实测的 .5 级差，而不是 antd 默认的 12/14/16/20/24：这份界面信息密度高
（列表项里同时有标题、摘要、徽标、计数），整数档在相邻层级之间跳得太大——
摘要 13px 与元信息 12px 挤在一起时几乎同高。

**守门**：`design.test.ts` 扫源码，**组件里不许出现字面的 font-size**。
唯一的例外是图标字形（`font-size: 9px !important; /* 图标字形，非文本 */`），
必须在行内写明 `非文本` 才放行——故意留一个需要解释的口子，而不是一个静默的豁免。

**影响**：新样式先找角色；找不到再考虑加档，并在 `FONT_SIZE` 的注释里写清理由。

## D-018 三栏的高度链断了（真 bug，不是样式问题）

**背景**：用户反馈「列表不能滚动」。

**根因**：grid / flex 里项目的自动最小尺寸是 `min-height: auto`，意思是
「不能小于内容的高度」。中栏那两千像素的列表于是把整行撑到两千像素，
`height: 100%` 形同虚设——**整页滚动**，而中栏里那个 `overflow-y: auto`
永远不触发（它自己已经和内容一样高了）。

**症状很迷惑**：看着像「列表不能滚动」，实际是高度链断在中间那一层。
与 `docs/DESIGN.md` §7.6 记的 AntApp 断链是同一类问题——都是**不报错、
只是布局不对**。

**决定**：`.app` 与它的三个子项都加 `min-height: 0`，外层加 `overflow: hidden`
兜底（万一某处仍溢出，让它被裁掉而不是把页面撑长）。

**验证**（实测数据，改前 / 改后）：

```
改前：documentElement.scrollHeight 1987px，视口 942px，grid 高 1987px
改后：documentElement.scrollHeight 900px，视口 900px，
      中栏自身 clientHeight 771 / scrollHeight 944 → 它自己滚
```

**排查心得**：不能只看「那个滚动容器有没有 `overflow-y: auto`」——
要看它的**祖先链**上有没有 `min-height: auto` 把它撑开。

## D-019 品牌标记：引号即井

**背景**：此前项目没有任何品牌标记——`index.html` 没有 favicon，界面上品牌就是
一行 `<b>mimir</b>`。用户提出要做 logo。

**名字的来源**：Mímir 是北欧神话里的至智者，守护智慧之井 Mímisbrunnr。
奥丁为喝一口井水献出了一只眼睛。

**决定**：两个引号，每个的碗里掏空一个圆 —— **引号本身就是一口井**。

这个形状有**两层读法，且第一层不需要任何前提**：

| 层 | 读法 | 谁读得到 |
|---|---|---|
| 1 | 引号 | 所有人。「带引用地问答」是产品的核心差异点（`PRD.md` §2.2 / §5.2），纯笔记应用不需要引号 |
| 2 | 井 | 知道神话的人。多得到一层，但不影响第一层成立 |

**这个双层结构是刻意的**：反过来（一个必须懂神话才看得懂的符号）会把多数人挡在外面。

**否决的方案**（都渲染出来在 16px 下逐一看过）：

| 方案 | 否决原因 |
|---|---|
| 同心环（井口 + 涟漪） | 16px 下三层环糊成一块色斑 |
| 井的剖面（三条递减横线） | 16px 下读作「文本对齐」图标 |
| 深度计（竖线 + 刻度） | 16px 完全糊掉 |
| 引号由细线环构成 | 16px 下笔画粘连成两个实心球（放大 8 倍确认） |
| m 字即井 | 形状可用，但导航里会变成「m mimir」——与文字首字母重复 |
| 井中之眼 | 故事最好，但「眼睛」在个人数据产品上有被监视的联想 |

**两条实现约束**（都写进了代码注释与守门测试）：

1. **井口用 `fill-rule="evenodd"` 挖空，不是拿白色圆形盖上去。**
   白圆在白底上看着没问题，但标记放到主色按钮或深色浮层上就会露出白点。
   evenodd 让孔是**真的空的**，于是它在任何底色上都成立。
2. **颜色走 `currentColor`。** 写死 hex 的话主题换色时 logo 不跟随，
   它会成为全站唯一一个不服从主题的元素。

**落地**：

```
apps/web/public/favicon.svg          SVG favicon，内部用 prefers-color-scheme
                                     在深色标签栏里换成白色
apps/web/src/components/BrandMark.tsx  <BrandMark />（标记）/ <BrandLockup />
                                     标记 20px（导航）、28px（登录页）、16px（favicon）
```

**守门**（`design.test.ts`）：

- 标记必须含 `evenodd`、必须用 `currentColor`、内部不得出现字面色值
- **favicon 与组件必须是同一个形状**（逐字比对 path 的 `d`）。
  这条拦的是「两处各画一遍然后慢慢分叉」——品牌一旦分叉，用户会先察觉
  「哪里不对」但说不清

## D-020 所有者账号由环境变量决定（不再只是「先注册先得」）

**背景**：用户提出「开发环境的账号密码是多少，也需要添加到环境变量中，
如果环境变量存在账号和密码，就可以跳过首次注册」。这里有一个**我原本会搞错的地方**——
我最初把它设计成「只在开发环境生效」，理由是生产的既定路径是首次注册。
用户随即澄清：**生产环境也要**。

这个澄清是对的，而且生产环境恰恰是更需要它的那个：

| 场景 | 只有「先注册先得」时的后果 |
|---|---|
| **服务已暴露公网，你还没注册** | 谁先访问谁就成为那个唯一用户，**拿到的是你整个知识库** |
| 清库重建（换分支、改 schema） | 账号一起没了，要重新注册 |
| 忘记密码 | **没有任何找回路径**——没有邮件服务，也没有第二个用户能帮你重置 |

所以这不是「开发便利」，而是 self-hosted 单用户产品的正确部署形态
（Grafana / Gitea 等都这么做）。

**决定**：`OWNER_EMAIL` + `OWNER_PASSWORD`，**开发与生产同一套语义**——
它是所有者账号的**真相来源**。

| 库里的状态 | 行为 |
|---|---|
| 没有账号 | 按环境变量创建（跳过首次注册）|
| 邮箱一致、密码不同 | **同步密码** ← 这是「忘记密码」的找回方式 |
| 邮箱不同 | 只警告，**不动它** |

**第二条是刻意的**：改 `OWNER_PASSWORD` 重启即生效。能改 `.env` 的人本来就有
服务器的完全控制权（他能读 `AUTH_SECRET`、能直连数据库），所以这不放宽攻击面。

**第三条同样刻意**：静默替换掉库里那个账号是破坏性的——对方很可能已经在用，
里面存了他的东西。

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 只在开发环境生效 | 见上表。生产才是最需要它的地方 |
| 只建号、不同步密码 | 就没有找回路径了，「忘记密码」只能清库重来 |
| 邮箱不同时替换掉现有账号 | 破坏性。用户换个 `OWNER_EMAIL` 就会静默丢掉别人的数据 |
| 直接往 user/account 表插行 | 要复刻 Better Auth 的密码哈希（算法、盐、参数），升级时会**静默失配**——密码看着存进去了、登录永远失败 |
| 用 `auth.api.setPassword` | 那个端点要求一个已登录的 session，服务端启动时没有 |

**实现**：密码走 `auth.$context.password.hash` —— Better Auth 自己的实现。
写库时**只改 `account.password` 与 `updatedAt`，不动账号 id**：
换 id 会让已登录的 session 全部失效。

**引导放在 `serve()` 之前**：反过来的话会有一个窗口——服务已经能接登录请求，
但账号还没建好，此时登录会得到「密码错误」，而它其实是「马上就好」。
这个窗口只有几十毫秒，但表现是**随机的登录失败**，最难排查。

**决策逻辑抽成纯函数**（`decideOwnerAction`）：四条分支里有两条是破坏性的，
而「邮箱不一致时不动别人账号」这条在手工测试中很容易因为环境恰好匹配而走过。
纯函数让四类情形可以逐个断言——见 `src/test/bootstrap.test.ts`。

## D-021 登录页拆成两种形态，错误信息不再误导

**背景**：登录页原本是「一个表单，先试登录，401 就改试注册」。
这个猜测的代价很具体：

```
用户输错密码
  → 登录返回 401（Invalid email or password）
  → 前端当成「还没有账号」，改去注册
  → 注册返回 400（User already exists）
  → 界面上显示「该邮箱已被使用」
```

**用户看到的是「邮箱已被使用」，而他真正的问题是「密码打错了」。**
两个错误叠在一起，没有一句话说到点子上。

**决定**：服务端提供 `GET /api/auth/setup/state` 明确告知状态，前端不再猜。

| 形态 | 何时 | 表单 |
|---|---|---|
| 首次注册 | 库里一个账号都没有 | 邮箱 + 密码 + **确认密码** |
| 登录 | 已有账号 | 邮箱 + 密码 |

**注册加二次确认**：它是**唯一一次**设置密码的机会（单用户规则下没有
「忘记密码」的界面路径）。打错的密码此刻没有任何反馈，直到下次登录才发现。
登录不加确认——输错了重输的成本远低于每次登录多打一遍。

**这个端点免鉴权**（登录页在登录前就要调），所以它只能暴露「有没有账号」
这一个布尔值。**预填凭据只在非生产环境返回**——把密码明文交给一个不需要
鉴权的端点，生产环境下等于任何人访问它就能拿到密码。已实测确认生产返回 `null`。

**一个路由注册顺序的坑**：`/api/auth/setup` **必须注册在
`auth.handler` 的 `/api/auth/*` 通配之前**。Hono 按注册顺序匹配，
反过来写会被 Better Auth 接走并返回 404（实测踩过，而且不报错、
只是那个端点从此访问不到）。

## D-022 只有文档模式有中栏

**背景**：原型定义了「中栏随模式变形」（`PRD.md` §5.2）：

| 模式 | 中栏 |
|---|---|
| 对话 | 本次引用了哪些文档 |
| 文档 | 文档列表 |

用户在使用中提出：「对话时不需要中间这一栏吧」「设置时也不需要」。
复盘后确认**这个判断是对的**，而且比原型的意图更准确。

**对话模式的中栏删掉，三个理由**：

1. **它与回答下方的引用块重复。** 每条 AI 回答下面已经是一列引用块，带类型徽标、
   标题、原文片段与命中通道。中栏那几张是副本，而且更差——少了「这个来源
   支撑的是哪句话」这层对应关系
2. **它有一半时间显示的是别的东西。** 新对话时中栏按 §5.10 显示**待整理收件箱**，
   与「本次引用」毫无关系，看起来却像。用户的原话是「我理解是不需要中间
   这一栏的吧」——那个误解本身就说明这个设计有问题
3. **它是静态的。** 打开旧会话时显示历史引用，而用户此刻想做的是「继续问」
   或「去看那篇文档」，两者都不需要它

**设置模式的中栏删掉**：设置是「进一个分区改完就走」，中栏在那里只能显示
文档列表——**与正在做的事完全无关，却占掉四分之一宽度**，还容易被当成设置的
一部分。设置页自己有左侧分区导航，那才是它需要的那一栏。

**决定**：

| 模式 | 左栏 | 中栏 | 右栏 |
|---|---|---|---|
| 对话 | 会话历史 + 知识库 | **无** | 对话（含检索过程与引用）|
| 设置 | 同上 | **无** | 设置分区与表单 |
| 文档 | 同上 | 文档列表 | 阅读 / 编辑 |

**补偿**：§5.10「新对话的中栏不空着」搬到**对话空态里**——待整理内容列在
输入框上方，点一下把范围锁到那一篇。动机（「我刚收了几篇东西，想问问」）
没有丢，而且比原来更贴切：原来那些条目与输入框隔着一栏。

**代价**：失去「一次看到这次对话的全部来源」。由回答下的引用块满足
（滚动即可），且引用块多一层「支撑哪句话」的信息。

**顺带修的**：中栏的渲染改成条件渲染而不是「渲染但隐藏」——隐藏的话
`ListColumn` 仍会跑它的文档查询与检索，而结果在另两种模式下没人看。

**实现代价**：`AppShellContext` 里的 `citations` / `setCitations` /
`conversationLoading` 三个字段随之删除（它们的存在理由就是喂中栏）。
一次对话少一次 `GET /api/conversations/:id`。

## D-023 `@mimir/shared` 以源码发布，编译交给使用方

> **工具部分已被 D-033 取代**：`apps/server` 的开发与生产都改成了 Vite
> （`tsx` / `tsdown` 退役）。本决定的原则——以源码发布、编译责任随使用方走——
> 没有变，下面的否决与影响仍然成立。

**背景**：契约包原先 `tsc` 到 `dist`，以产物发布（`main`/`types` 指向 `dist`）。
代价是每个消费它的脚本都要先跑一次 `pnpm --filter @mimir/shared build`：
`build` / `typecheck` / Dockerfile / 前端脚本里各写了一遍，多出一条
「顺序不能反」的隐性约束。改一行 schema 要等一次独立编译，忘了先构建
就会拿到过期的类型。

**决定**：`@mimir/shared` 不再构建，`exports` 直接指向 `src/index.ts`。
「谁来编译 TS」这个问题按使用方各自的构建链回答：

| 使用方 | 谁编译 shared 的源码 |
|---|---|
| `apps/web`（开发与生产）| Vite |
| `apps/server`（开发）| tsx |
| `apps/server`（生产）| tsdown，把 shared 打进 `dist` |

> 上表已被 D-033 取代（后两行改成 Vite）。留在这里是为了让「为什么换」可对照。

服务端构建从 `tsc -p tsconfig.build.json` 换成 tsdown。这不是可选的：
Node 拒绝执行 `node_modules` 里的 TS（`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`），
而且源码一旦落在 `node_modules` 下连类型剥离都不允许——所以必须编译进产物，
不能靠运行时加载。

tsdown 的两个配置都是必需的，不是调风格：

- `unbundle: true`：`lib/static.ts` 用「本文件所在目录往上两级」推导前端产物
  位置。打包成 chunk 后文件被重命名成 `dist/static-xxxx.js`，`import.meta.url`
  跟着变，推导出的根少一级——**不报错，只是静态资源 404**
- `outExtensions: () => ({ js: '.js' })`：默认输出 `.mjs`，而镜像与 `start`
  脚本跑的是 `node dist/index.js`

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 保持产物发布（`tsc` 到 `dist`）| 每个使用方多一条前置构建与顺序约束。这份重复的构建逻辑在 4 处各写了一遍，是这个决定要解决的问题本身 |
| 源码发布 + 运行时直接加载 TS | 实测报 `ERR_MODULE_NOT_FOUND`：Node 不做 `.js` → `.ts` 的路径改写，`src/index.ts` 里 `export * from './auth.js'` 解析到不存在的 `auth.js`。即使改成无扩展名，生产环境仍会拒绝剥离 `node_modules` 里的类型 |
| 用 `tsc` 直出 + 只给 shared 加一个编译步骤到 dist | 回到第一行的形态，且 shared 会同时存在 `src` 与 `dist` 两份真相 |
| 不用打包器，把 shared 的源码复制进 apps/server 后一起 `tsc` | 复制出来的副本会与 `packages/shared` 漂移，且 Drizzle/前端拿到的仍是另一份 |

**影响**：

- `pnpm build` 不再有 `shared` 这一步（根脚本从「先 shared 再其余」简化成 `pnpm -r build`）
- Dockerfile 少一个构建阶段，也不再需要「顺序不能反」的注释
- CI 增加 `pnpm -r build`——打包坏了必须在 CI 就被发现，而不是部署时
- 服务端 `dist` 里多出 `dist/packages/shared/src/*.js`（编译后的 shared），
  这些是产物，不进 git
- 前端 bundle 里 shared 仍被 Vite 按需 tree-shake，体积不变
- `packages/shared/tsconfig.build.json` 与 `dist/` 目录删除；该包只剩 `typecheck` 脚本

## D-024 不拆多知识库；库是组织单位，不是性能单位

**背景**：用户提出担心——文档量上来之后，全库检索会不会变慢、AI 对话过程中
「索引文档的时间」与 token 消耗会不会随库增长，是否该拆成多个知识库。

调研与实测见 `RESEARCH.md` §9。三条关键事实：

1. **竞品没有一家用拆库解决速度。** RAGFlow / FastGPT / MaxKB 都把**所有库的
   chunk 放在同一批物理索引里**，用 `kb_id` 之类的过滤字段区分（MaxKB 是唯一
   把库当性能单位用的：逐库查询以命中局部 HNSW 索引，但库仍是逻辑对象）。
   FastGPT 的官方措辞最直白：集合「仅是为了对数据进行分类管理，**与搜索效果无关**」。
2. **拆索引让全量查询更慢，这是引擎厂商的共识。** Elasticsearch：查很多小分片
   「不一定比查少量大分片快」，每个分片有固定开销（空分片也占内存）；Qdrant：
   「全局查询会更慢，因为必须扫描所有分组」；Pinecone 的成本模型是扫描字节数，
   跨 N 个 namespace 就是 N 份成本。大厂分片的真实动机是运维——Notion 的 480 个
   分片是为了治 autovacuum 与 TXID 回绕，不是查询速度。
3. **真拆了库的产品，代价是失去跨库检索。** NotebookLM 官方文档写明
   「can't access information across multiple notebooks at the same time」，
   用户为此反复请求「合并 notebook」。而官方给源数量上限的理由全部落在上下文与
   回答质量上——**没有一条说是检索慢**。也就是说，库是模型上下文逼出来的隔离单位。

**决定**：保持单库。不引入用户可见的「知识库」对象，不加 `knowledge_base_id` 列。

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 拆成多个用户可见的知识库 | 收益是假的（见上三条），代价是真的：`documents`、`tags`、`conversations` 全部要加库 ID 并改所有查询的过滤条件，是一次穿透全栈的迁移。而且它直接把 `PRD.md` §5 认定的头号问题（「想不起存过什么」）变成永久问题——用户得先想起存在哪个库 |
| 提前做 list 分区 / 局部索引 | pgvector 的分区确实有用（Sentry 实测提升了延迟与召回），但收益在**运维**（各分区独立 vacuum）与选择性过滤上，不在「查全部」。现在的量级离触发点还远，属于「等第二个实现出现再抽接口」的同类判断 |
| 现在就重写召回 SQL | **这不是否决，是排期**。谓词下推本身要做（见影响），但它不是架构决定，不需要为它引入库的概念 |

**影响**：

- **索引不在对话链路里。** 写入路径是增量的：`createNote` / `updateNote` 只对
  这一篇算 `excerpt` / `searchText` / `contentHash`；全量 `reindexVault()` 只由
  `POST /maintenance/reindex` 显式触发。对话里只有查询，没有索引。
- **检索上下文的 token 有上限且与库大小无关。** `CONTEXT_CHAR_BUDGET` = 6000 字符、
  每条引用 1200 字符、取前 8 条——它是**每轮重新计算的预算**，不是累积量。
  会随对话增长的是**历史消息**（`assistant-stream.ts` 把客户端带来的 history
  原样拼进 `messages`，没有窗口），这是另一个维度。
- **待办（检索层，与库无关）**：两条召回通道的门槛都写在**外层查询**里，
  过滤条件引用计算列，GIN 与 trigram 索引静默失效。5 万行实测：关键词通道
  零命中也要 **292 ms**，命中 1/7 时 328 ms；谓词下推到 `WHERE` 后零命中降到
  **0.012 ms**。这是 O(N) 的逐行成本，随库增长线性变慢——**拆库也不会治好它**，
  只是让每个库各自全表扫描。见 `RESEARCH.md` §9.5。
- **将来若要拆，触发条件不是「文档多」**，而是：HNSW 索引装不进内存
  （`maintenance_work_mem` 默认 64MB，pgvector 在 10 万条量级会报 graph 装不下）、
  rerank 与 LLM 富化的成本、或索引构建时间。而且拆的理由必须是**组织与情境隔离**，
  并保住跨库检索。

## D-025 设置页的分区导航改横向，配置值从服务端读

**背景**：用户反馈「设置页面的整体布局需要调整一下，太丑了」。截图复核后确认
问题不在某个值，而在**结构**——三个可复现的现象：

1. **两条左栏。** 页面在 760px 的内容列里又用 `tabPosition="left"` 摆了一套
   分区导航，与全局左导航并排。位置反馈因此重复：左上角的「设置」已经说明
   你在哪一页
2. **正文被挤成窄条。** 限宽的 760px 内容列里再切掉约 100px 的 tab 竖栏，
   正文实际只剩约 570px，而右侧空着半个屏幕
3. **ink bar 像渲染坏了。** antd 的选中指示条是一条脱离文字的蓝色竖线

另有三处独立的缺陷，一并修掉：

- 说明文字里的 `**Markdown 文件是真相**` 被当字面量渲染，星号直接显示在界面上
  （这些文字是 JSX 普通文本，不走 Markdown 渲染）
- 插件条目用了 `<Tag color="green">` 预设色——`AGENTS.md` 与
  `DocumentBadges.tsx` 都明确禁止，预设走 antd 自己的调色板，对比度不由我们控制
- 每个插件条目右侧挂了一个 `disabled` 的 `Switch`：它看起来像能打开的开关，
  实际永远打不开，也没有 tooltip 说明。那比没有更糟

**决定**：

| | 之前 | 现在 |
|---|---|---|
| 分区导航 | 内容列内的左侧 Tabs | 页头下方的横向 Tabs |
| 内容列 | 760px 里再切掉 tab 列 | 完整 760px（`DESIGN.md` §5.4） |
| 分区状态 | 组件内的 `useState`（隐含） | URL 的 `?section=` |
| 面板 | `Card` + `Descriptions bordered`（三层边框） | 一个自绘面板，键值行之间一条浅线 |
| 插件状态 | `disabled` 的 `Switch` | 徽标（`已注册` / `待开发`），只陈述事实 |
| 插件行的实现状态 | 硬编码在前端 | 仍在前端（注册表是代码事实），但**模型与检索参数从服务端读** |

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 保留左侧 Tabs，只把宽度调宽 | 治不了「两条左栏」——那才是这一页最刺眼的地方。而且位置反馈重复会让人以为自己进错了层级 |
| 每个分区一个独立路由（`/settings/models`） | 六个分区各占一条路由，但它们的**布局与生命周期完全相同**，只是内容不同。为它们建六条路由会让路由表变长而不增加能力；`?section=` 已经能给出可分享的链接 |
| 分区状态留在组件里（`useState`） | 那样「去设置 > 数据与备份」就没法给一个链接，刷新也会回到第一个分区。用 URL 的代价只是一个 `validateSearch` |
| 让 `/api/config` 可写 | 配置的真相是 `.env` 与代码常量。做成可写的等于让界面成为第二个真相来源——那是另一半麻烦，见 `TECH.md` §7.4 |
| 设置页继续硬编码模型名 | 它会在用户改了 `MODEL_CHAT_MODEL` 之后说谎。这一页自己的原则是「画一个存不进去的假表单比没有更糟」，显示一个说不了真的值属于同一类问题 |
| 用 `<Tag color="green">` 表示「已注册」 | `AGENTS.md` 第 8 条：预设色走 antd 调色板，对比度不由我们控制。改用语义色对（`colorSuccessText` on `colorBgContainer`，实测 5.95:1） |

## D-026 侧边栏可折叠，顶栏按钮从「返回上一处」改为折叠开关

**背景**：用户指出左导航顶栏那个箭头「不应该是返回按钮，应该是侧边栏的
折叠展开按钮」。

**这个判断是对的，而且问题不只是位置。** 复盘时发现两件事：

1. **它是全局历史导航，却挂在栏内。** 用户想「回去」时会去看内容区，
   而想「收起这一栏」时会来看这个角落——需求与位置错位
2. **它的可用性有一半时间是关的。** `disabled={!router.history.canGoBack}`
   意味着首次进入、或新开标签页时它是一个灰掉的箭头。一个常驻控件
   大半时间是失效状态，本身就是「它不该在这里」的信号

**决定**：顶栏那个位置改为折叠开关（`MenuFold` / `MenuUnfold`），
折叠后左列 200px → 48px。

| | 之前 | 现在 |
|---|---|---|
| 顶栏按钮 | 返回上一处（`router.history.back()`） | 折叠 / 展开侧边栏 |
| 左列宽度 | 200px（窄屏 180px） | 展开 200px / 折叠 48px |
| 折叠状态 | — | `localStorage`（`mimir.nav-collapsed`） |
| 目录树 | 常驻 | 折叠时整块不渲染 |
| 状态归属 | — | `_app.tsx`（网格在哪一层，状态就在哪一层） |

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 两个按钮都留（返回 + 折叠） | 48px 的栏宽下没有两个按钮的位置；展开态并排两个 24px 图标会挤在品牌名旁边，而它们一个是导航一个是对栏的操作，性质不同 |
| 折叠状态放 `NavSidebar` 内部 | 折叠要改的是外层的 `grid-template-columns`，而网格属于 `_app.tsx`。放栏内的话栏自己收窄了、网格没变，只会留下一片空的 200px |
| 折叠状态不进 `localStorage`（纯内存） | 折叠是**长期偏好**而不是临时动作——每次刷新都弹回去，用户就得反复点它，而这个按钮的价值恰恰是点一次之后不用再管 |
| 折叠状态放 URL / 服务端 | 它是纯客户端的渲染偏好，服务端不关心。放 URL 会污染可分享的链接 |
| 目录树折叠成图标保留 | 层级树没有「只剩图标」的形态，会变成一列缩进错乱、认不出是什么的文件夹图标。它本来就是低频入口，让位是合理代价 |
| 直接删掉返回按钮，什么都不补 | 空出来的位置是这一栏最显眼的一处，留空比放一个正确的东西更差 |
| 用 antd `inlineCollapsed` 的默认宽度 | 它硬定 80px，而这一栏只留 48px，实测会横向溢出。覆写宽度是必需的；另有三处细节（分组标签、图标居中、计数）各有各的成因，见 `NavSidebar.style.ts` 里 `menuCollapsed` 的注释 |

**影响**：

- **历史返回没有消失**，只是不再占用这个位置：浏览器后退键仍然可用，
  `DocumentPanel` 保留着「返回对话」（从对话点引用跳过来时出现，
  带上下文，比一个通用箭头更明确）
- `_app.tsx` 的网格从两条规则变四条：`app` / `appWide` 各配一个 `Collapsed`
  变体。第一列在两种模式下一样，但 `grid-template-columns` 是一整条声明，
  没法只覆盖一列——所以四条各写一遍，这是 CSS 网格的固有限制
- `NavSidebar` 新增 `collapsed` / `onToggleCollapsed` 两个 props，
  它不再 import `useRouter`（那个 import 的唯一用途就是那个按钮）
- `docs/DESIGN.md` §5.4 记录 48px 这个值，以及「它不随断点变化」的理由
- **一个静默的坑**：antd 折叠菜单会给**没有图标**的菜单项取标签首字当图标。
  空态的「还没有对话」占位项因此渲染出一个孤立的「还」字。补图标是错的
  （那会让人以为它是入口），折叠时整块不渲染才对——见 `NavSidebar.tsx`
  的 `conversationItems`

## D-027 正文排版收敛成一份，修好四个静默失效的编辑器缺陷

**背景**：用户要求优化编辑器体验。逐项复核后发现的不是「样式不够好」，
而是**四类不报错的缺陷**——其中三个只能在浏览器里量出来，代码里看不出来。

### 缺陷一：编辑区下方 800px 是死区

一篇三行笔记的 ProseMirror 高度实测约 **98px**，而可见正文列高约 900px。
下面那 800px 点上去什么都不发生——`activeElement` 仍是 `body`（实测）。
而「打开笔记 → 在末尾接着写」是记笔记最常见的一步。

**修法**：给编辑态的 `.ProseMirror` 一个 `min-height: 46vh`。点击落进编辑区后
Tiptap 会把光标放到最近的文字位置（末行），这是所有编辑器的一致行为。
死区占比从 **79% 降到 7%**（实测）。只给编辑态——只读视图撑出空白没有意义。

### 缺陷二：语法高亮的 CSS 完全缺失

`CodeBlockLowlight` 挂着 lowlight 与 `common` 语法包，解析出的 span 确实带
`hljs-keyword` / `hljs-string` 之类的类（实测一个五行代码块产出 12 个 span、
6 种 token），但**全仓没有一条 `hljs` 规则**——所有 token 渲染成同一个颜色。
看起来像「这个编辑器不支持高亮」，实际只是少了 CSS。

**修法**：在共用排版里补上着色。只用既有语义 token（不新造色值），
函数名与章节名靠**字重**而不是色相区分——再多一个色相会让代码块比正文更抢眼，
而代码块在笔记里是配角。对比度加进 `design.test.ts`。

### 缺陷三：任务列表渲染成「圆点 + 复选框」

Tiptap 的 TaskItem 产出
`ul[data-type=taskList] > li[data-checked] > label > input + div > p`，
**没有自带样式**，于是落进通用 `ul/li` 规则：拿到项目符号（disc）与 20px 缩进，
内层 `<p>` 还带着 12px 上下边距。结果是圆点与复选框并排、文字被挤到第二行。

**修法**：`list-style: none` + flex 一行；去掉内层 `p` 的边距（否则每个待办
比相邻普通列表项高一倍）；已完成项划掉并转三级文字——状态不该只靠复选框里
那一点点颜色差传达。复选框保留浏览器原生控件，只改 `accent-color` 与尺寸：
手绘一个会丢掉键盘与无障碍语义。

### 缺陷四：大图撑破内容列（只在编辑态）

`img { max-width: 100% }` **原先只存在于只读视图**。笔记里插一张 1200px 的图
会让编辑区出现横向滚动条（实测 scrollWidth 1200 / clientWidth 664），
而同一篇文档在只读态正常。

### 根因：同一套排版手抄了两份

上面第二到第四条，根因都是**编辑态与只读态各自维护一份正文排版**：
`NoteEditor.style.ts` 的 `body` 与 `DocumentPanel.style.ts` 的 `readOnly`。
两个视图都让 Tiptap 渲染同一份 Markdown，排版**必然**要同源，而两份手抄的
规则已经漂移出四处。

**决定**：正文排版收敛到 `components/ContentTypography.style.ts` 的单个
`content` 类，两个视图共用。`readOnly` 那 93 行重复块删除。

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 只补 `img` 规则，保留两份 | 治的是症状。两份手抄的规则会继续漂移，而下一次漂移同样不报错 |
| 把排版挪到 `src/styles/` | `design.test.ts` 的字号字面量扫描只覆盖 `src/components` 与 `src/routes`，挪出去会让本项目最密集的排版规则脱离守卫 |
| 手绘复选框替代原生 input | 会丢掉键盘操作与无障碍语义，而 Tiptap 已经配好了 aria-label |
| 给只读视图也加 `min-height` | 只读正文撑出一片空白没有意义——它没有可落笔的地方 |
| 用一个 Markdown 渲染库统一两端 | 与 `MarkdownBody` 现有决定冲突：两端都用 Tiptap 才能保证「编辑时看到的」与「只读时看到的」是同一个规范形 |

**影响**：

- 新增 `apps/web/src/components/ContentTypography.style.ts`；
  `NoteEditor.style.ts` 只剩外壳（宽度、保存行、书写区高度），
  `DocumentPanel.style.ts` 少 93 行
- `design.test.ts` 增加一条：语法高亮配色在 `tintNav` 与白底上 ≥ 4.5:1
- `docs/DESIGN.md` §4.3 重写，含「两个视图共用一份」的理由与漂移对照表
- 编辑器与只读视图现在渲染完全一致的正文；以后改正文排版只需改一处

**验证方式**：用 API 建了含全部元素类型的笔记（标题 / 列表 / 任务列表 / 引用 /
代码块 / 表格 / 图片），在真实浏览器里量了：图片宽 = 内容列宽且 `scrollWidth ==
clientWidth`（无溢出）、任务项 `display: flex` 且 `list-style: none` 且内层
`p` 边距 0、代码块 6 个 token 渲染出 4 种不同颜色、行内代码 13px、
点击正文下方空白后 `activeElement` 是 `ProseMirror` 且输入追加到末尾。

## D-028 编辑器布局四改，附带修好一处数据丢失

**背景**：用户反馈四个问题——「标题太大了」「标题上面一大片待整理」「保存状态
在正文上面孤零零的」「中文 focus 还有一圈阴影」。逐项量过之后，第一和第四条
都是**不报错的实现错误**；排查过程中另外发现一处**数据丢失**。

### 一、标题渲染成 38px（规范写的是 28px）

标题是 antd 的 `Typography.Title`，它自带
`h1:where(...).ant-typography { font-size: var(--ant-font-size-heading-1) }`
——`h1` 元素贡献 (0,0,1)、`.ant-typography` 贡献 (0,1,0)，合计 **(0,1,1)**，
而项目里那条 `.acss-*` 单类规则只有 (0,1,0)，**盖不住**。实测 38px。
不报错，看起来只是「标题偏大」。

**修法**：`&.${prefixCls}-typography` 叠成 (0,2,0)。

### 二、整理条排在标题之前

顺序是「一整块待办动作 → 标题」，而用户打开一篇文档时先要知道「这是哪一篇」。
**修法**：移到标题与元信息之后。顺序变成「是什么 → 从哪来 → 怎么办 → 正文」，
动作仍在首屏。

### 三、保存状态孤零零地占一行

它原先渲染在正文上方、标题与元信息之间：一块只有「已保存」三个字的独立行，
两侧都空；而且**位置会跳**——状态出现与消失时整块正文上下移动。

**修法**：移到文档工具条（路径与问 AI 之间）。常驻、不占额外高度、与其他
界面状态同一层。顺带纠正了一处与文档不符：`docs/PRD.md` §5.9 原话就是
「工具条常驻」，之前那个实现并不在工具条上。

### 四、正文的焦点环（`:focus-visible` 在此失效）

规范规定 `contenteditable` 与 `<input>` 的 `:focus-visible` **永远匹配**——
浏览器无法假定用户接下来用键盘还是鼠标，而文本输入需要焦点提示。于是每次
鼠标点进正文都会画出一圈原生环（实测 `outline: auto 1px rgb(16,16,16)`），
围着整个编辑区，而点进正文是几乎每次编辑都会做的事。

两难：直接 `outline: none` 会牺牲键盘用户的焦点可见性（§7.2，那条规范的
存在理由就是它最常被设计洁癖牺牲）；保留原生环就是用户要修的问题。

**修法**：`lib/input-modality.ts` 追踪最近一次输入方式，写到 `html` 的
`--mimir-focus-ring-style`（鼠标 `none` / 键盘 `solid`）。

### 五、数据丢失（排查中发现的，比上面四个都严重）

**症状（实测复现）**：输入之后在 900ms 防抖窗口内切换文档，待保存的写请求
再也不会发出，而「有改动还没保存」的拦截框**也不出现**——用户以为存上了，
实际丢了。

**根因**：`NoteEditor` 声明了 `onDirtyChange` / `registerSave` 两个 props 并在
其中注册脏标记与保存入口，而**全仓没有任何调用方传它们**。于是
`lib/unsaved.tsx` 里那套「三选项拦截」的机制从来没有被武装过——它写得很完整，
只是没人接线。

**修法**：编辑器直接从 `useUnsaved()` 取 `setDirty` / `setSave`，不再走 props。
这与 `lib/unsaved.tsx` 开头的设计一致：「脏标记必须提到一个共同祖先，而不是靠
编辑器往下传回调（那样每加一个导航入口都要改编辑器）」。

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 给 `NoteEditor` 补上那两个 props | 那正是**忘了接线**的地方。用 context 从根上消掉这个失误可能——接口在那儿，就没有「忘了传」这回事 |
| 把「离开」的拦截也交给浏览器 `beforeunload` | 它只有两个选项（留下 / 离开），而 §5.9 明确要求三个（继续编辑 / 丢弃改动 / 保存并离开）。`beforeunload` 只作为关标签页的兜底保留 |
| 缩短防抖到 0（每次按键都发请求） | 每个字符一次写请求，且每次都重写整个文件与 `searchText`。用拦截解决，不用流量解决 |
| 焦点环直接 `outline: none` | 牺牲键盘用户的焦点可见性（§7.2）。用输入方式追踪，两边都保住 |
| 给所有控件都套输入方式追踪 | 其余控件的 `:focus-visible` 行为本来就是对的，加一层只是多余的复杂度。这个模式只用在文本输入类元素上 |

**影响**：

- `lib/input-modality.ts` 新增，`main.tsx` 在模块作用域安装（写的是 `html` 上的
  自定义属性，与 React 生命周期无关）
- `NoteEditor` 的 `onDirtyChange` / `registerSave` 两个 props 删除，改为
  `onSaveStateChange`（把状态与重试入口交给工具条）
- `useIndicatorStyles` 删除（保存指示器已移出编辑器），`saveRow` / `title`
  两条死样式删除
- `DocumentPanel.style.ts` 新增 `save` / `saveError`，`title` 抬特异性
- **一个反直觉的点**：`--mimir-focus-ring-style` 里**不能**存完整的 ring 值
  （如 `2px solid var(--ant-color-primary-border)`）。自定义属性里的 `var()`
  在**声明它的元素**上求值，而 `--ant-*` 注入在 antd 组件子树上——声明在
  `html` 上取不到值，整个属性在 computed-value 阶段无效，`outline` 退回
  `none`，键盘焦点环**静默消失**（实测踩到）。只存关键字，宽度与颜色在使用处给

**验证方式**：真实浏览器逐项量过——标题 38px → 28px；DOM 顺序变成
H1 → 元信息 → 整理条 → 正文；工具条上出现「正在保存… → 已保存」，正文里
不再有独立保存行；鼠标点击正文 `outline-style: none`、键盘模式
`outline: solid 2px rgb(145,202,255)`。数据丢失那条第 B 组：输入后立刻点导航，
拦截框出现，点「保存并离开」后服务端正文确认含新输入。

## D-029 配置分层：DB 覆盖 > 环境变量 > 默认，键集是闭集

**背景**：M0 的配置全在 `.env`，改一个模型名要改文件 + 重启。M1 起有十几个
要调的参数——embedding 模型与维度、分块大小与重叠、各通道权重、RRF k——
把「调权重」变成「改 `.env` 再重启」，会直接劝退调参这件事本身。

但另一面是 M0 已经写进 D-025 的判断：**配置的真相是 `.env` 与代码常量，
做成可写的等于让界面成为第二个真相来源。** 这两条看起来矛盾。

**调研**（`RESEARCH.md` §1.5）：WeKnora 的解法是三层解析
`DB 行 > os.Getenv > 内置默认`，留空自动回落。它的实现里有四处细节
是这个方案能成立的前提，不是可选的优化：

| 细节 | 不做的后果 |
|---|---|
| 键集在代码里注册（`settingSpec`），写入拒绝未知键 | 界面能存一个没有任何代码读的值，用户以为改了行为 |
| 迁移**不 seed** 默认行 | 部署方在 `.env` 配的值被空默认值静默覆盖 |
| 写入时按类型校验（400 返回） | 坏值等到第一次调用才炸，或更糟——静默用默认值跑 |
| 每键声明 `requires_restart` | 用户改了一个启动时才读的键，界面上显示已生效 |

**决定**：加一层 DB 覆盖，**但键集是闭集，且不是所有键都能写**。

```
解析顺序（每个键独立判断，不整份回落）
  1. settings 表里那一行（有值才用）
  2. process.env[该键的 env 名]
  3. 代码里的默认值
```

三个可写分区：**模型**（`model.*`）、**检索**（`retrieval.*`）、
**抓取**（`capture.*`）。端口、数据目录、数据库地址、认证密钥一律不进
spec——它们改了就重启不了，出现在界面上是假表单。

**为什么「界面 > 环境变量」而不是反过来**：`.env` 表达的是**部署事实**
（连哪个库、哪个地址），界面表达的是「我现在想调一下权重」。冲突时后者赢，
因为它是用户**此刻**的意图；而 `.env` 的意图在它被写下的那一刻就固定了。
代价是必须让来源可见——设置页每一行都显示 `来源：界面 / 环境变量 / 默认`，
否则用户看不出自己是在覆盖还是在跟一个环境变量叠加。

**「清除覆盖」是一个真实动作**：删掉那一行就回到环境变量。界面上每行有这个
按钮，而不是让用户猜「改成空串行不行」（空串与非空串的语义差异是这类界面上
最常见的困惑）。

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 保持只读（D-025 的方案） | 那是 M0 的正确选择——当时只有 5 个模型键，且没有要调的参数。M1 之后权重与分块参数是**要反复试**的，只读等于把调参推给 `.env` |
| 全部可写（含端口、数据目录） | 那需要热重启进程，且一半的键改了不生效。**「可写」应当只覆盖真的能生效的键** |
| 环境变量优先于界面 | 那界面上的编辑框在多数部署里都是假的（`.env` 里恰好配了那个键时），用户会以为坏了 |
| 界面存一份、服务端不读 | 那就是 D-025 已经否决过的「第二个真相来源」，只是换了个方向 |
| 给每个键都做 `requires_restart` 热重启 | 单用户自托管，为一个权重值重启进程属于自伤。**改不了就如实说改不了**（M0 设置页的原则） |
| 引入多套命名的模型配置（WeKnora 的卡片列表） | 它的角色与消费者多（每个知识库、每个智能体各自绑定），需要一层间接。本项目的角色是固定的五六个，每个角色一行就地改更直接 |
| 键放在一个 JSON 列 | 单行 JSON 的并发写法是「读-改-写」，两个设置同时改会丢一个。按 key 一行、`ON CONFLICT DO UPDATE` 没有这个问题，且能按 key 查「谁改过」 |

**影响**：

- 新增 `settings` 表（`key` 主键、`value` jsonb、`updated_at`）与
  `settings/specs.ts`（键注册表：类型、默认值、env 名、说明、是否密钥、改了要不要重建索引）
- `GET /api/config` 从「只读快照」变成「设置 + 插件 + 模型就绪状态」三块；
  新增 `PATCH /api/config/settings`（整批校验，任一键不合法则整批拒绝——
  半批成功会让用户面对一个说不清的状态）
- **校验逻辑只有一份**：spec 里的校验钩子同时被 PATCH 端点与解析层使用。
  两处各写一遍必然漂移，而漂移的表现是「存进去了，但读出来是另一个值」
- 密钥类键在 `GET /api/config` 里只回 `{ configured, source }`，值一个字都不给
- 环境变量在 spec 里以 `envName` 声明，`env.ts` 仍是**启动期**事实的读取处
  （数据库地址、数据目录、认证），模型与检索键的读取改走解析层

**验证方式**：`apps/server/src/test/settings.test.ts` 覆盖三条回落路径
（DB 有值 → 取 DB；删掉 → 取 env；再删 → 取默认），以及拒绝未知键、
拒绝类型不符的值、整批拒绝。手工验证：在设置页改 RRF k → `GET /api/config`
的来源显示「界面」→ 重启服务仍是界面值 → 点「清除覆盖」→ 来源变回默认。

## D-030 接缝描述符：可用性由实现自己回答

**背景**：设置页的插件清单是**前端硬编码的数组**（`PluginsSection.tsx`），
与 `plugins/leg/index.ts` 的真实注册表**没有连接**。加一个通道要改两处，
而界面上的「待开发」条目连文件路径都是手写的。这正是设置页自己宣称要避免的
「设置里有开关但代码里没有对应逻辑」——只是它当时是反过来的：代码里有实现，
界面里有一份会漂移的抄本。

同时 M1 要问「向量通道现在能不能用」，这个答案取决于
「有没有配 embedding 模型、key 在不在」。把它写进设置页的判断里，
就是给每个实现加一条要同步维护的分支。

**调研**：WeKnora 的做法是让实现自己回答
（`EngineRegistration.CheckAvailable(connected, overrides) (bool, reason)`，
`RESEARCH.md` §1.5）。两个细节值得抄：

1. **可用性不是静态检查**：MinerU 那类控制器会真的 ping 端点。
   「配置齐了」不等于「能用」——地址填错、key 过期、模型名下架都要发一次才知道
2. **reason 是给用户看的**：「MinerU API Key not configured」而不是「不可用」。
   界面用绿/红徽标 + tooltip，界面上只说徽标，原因在悬停里

**决定**：每个实现提供一个 `PluginDescriptor`（描述符），与运行接口分开放。

```ts
interface PluginDescriptor {
  seam: 'capturer' | 'parser' | 'leg' | 'provider'
  id: string            // 稳定，会写进 matchedBy 与 URL
  name: string
  description: string
  file: string          // 仓库相对路径，设置页直接显示
  configKeys: string[]  // 反查「改了 X 会影响谁」
  status: PluginStatus  // active | needs-config | unavailable | planned
}
```

`status` 是**四态**而不是布尔：`planned`（代码还没有）与 `unavailable`
（代码在但干不了活）对用户的含义完全不同——前者是「将来会有」，
后者是「现在缺个东西，补上就能用」。

**探测是显式动作，不是自动的。** WeKnora 的 `CheckAvailable` 里那个真实
ping 如果挂在「打开设置页」上，就是每次进设置都花钱且慢。所以：

| 状态 | 来源 | 成本 |
|---|---|---|
| 未配置 | 描述符静态算 | 零 |
| 未测试 | 默认 | 零 |
| 可用 / 不可用 | `POST /api/config/probe` 的结果（内存缓存） | 一次真实调用，用户点才发生 |

探测结果**不进数据库**：它是「刚才通不通」的观测，不是配置。重启即回到
「未测试」，比留一个可能过期的「可用」诚实。

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 前端继续维护插件清单 | 已经在漂移了。它的存在本身就是这次改动的理由 |
| 描述符里带上运行函数（一个对象什么都装） | 那会让 `/api/config` 与设置页 import 到 `keywordLeg` 的实现，进而拖进数据库连接。**描述符必须能在没有数据库的环境里构造**（测试、构建期） |
| `status` 用布尔 `available` | 「规划中」与「不可用」在界面上必须可区分（前者不该有红色徽标）。三态以上用联合类型比布尔 + 附带字段清楚 |
| 打开设置页时自动探测所有 provider | 每次进设置花钱；且用户没要求验证时，一次失败的探测会让界面显示「不可用」——那是误导 |
| 把探测结果写进 settings 表 | 观测与配置混在一张表里，语义会烂掉。而且它的时效性远短于配置 |

**影响**：

- 新增 `apps/server/src/plugins/types.ts`（描述符与 `PluginStatus`）
- 四条接缝的注册表**只导出描述符**给 `/api/config`；运行时对象（`retrievalLegs`
  那种带 `run` 的数组）由编排层直接 import。**两个出口，一个注册表**
- 设置页的插件分区改为遍历 `/api/config` 的 `plugins`，不再有硬编码数组
- `packages/shared/src/config.ts` 的 `runtimeConfigSchema` 重写为三块
  （`settings` / `plugins` / `models`），前端类型跟着更新
- 每个实现的 `file` 字段指向自己所在的文件；「待开发」的条目指向规划中的路径
  或「—」。它是这一页存在的核心价值：**看到「关键词通道权重 1.0」时，
  同时知道去哪个文件改**

**验证方式**：`apps/server/src/test/structure.test.ts` 增加断言——
`/api/config` 的 `plugins` 里每个实现的 `file` 路径在仓库里真实存在
（`active` / `needs-config` / `unavailable` 三类），且 `leg` 分区的
id 集合与 `retrievalLegs` 的 `name` 集合一致。**这条断言防止的正是这次的
起因**：清单与注册表各说各话。

## D-031 不做可切换的存储引擎；Postgres 一个后端到底

**背景**：WeKnora 的「数据与扩展」分区里有向量数据库引擎、存储引擎、沙箱配置、
网络搜索等条目，向量库 10 种、对象存储 8 种、网络搜索 14 家
（`RESEARCH.md` §1.5 第（八）条）。看起来「插件化」= 这些都要做成可切换的。

**决定**：明确不做。本项目只有一个后端：**Postgres**。

**理由**：

1. **它自己也只在真正多实现的地方做抽象。** 图数据库只有 Neo4j 且靠
   `NEO4J_ENABLE=true` 开关（`internal/container/container.go:1721-1725`），
   不是可切换的；对象存储有 allow-list 与按库绑定，是因为企业客户各自的
   对象存储不同。**多后端支持是「兼容各种已有栈」这个需求的产物**，
   不是插件化的结果
2. **Postgres 同时是关系库、全文索引与向量库**（TECH.md §1 的选型理由），
   这是本项目的简化前提。把向量检索抽象成接口，代价是每个查询要过一层
   适配（`<=>` 运算符、`halfvec` 的表达式索引、RRF 的 SQL 都是 PG 特有的），
   收益是零——没有第二个后端，也不打算有
3. 「加一个后端」的真实成本不是写一个适配器，而是**每条 SQL 都要能在两个
   方言下正确工作**。D-024 已经记过一次同类判断：拆索引让全量查询更慢，
   真拆了库的产品（NotebookLM）的代价是失去跨库检索

**与「插件化」的关系**：插件化的目标是**代码好维护**，不是「什么都可替换」。
一个诚实的分界线是：**有多实现（或明确将有多实现）的地方抽接缝，只有一个
实现且不会变的地方不抽**。`capturer` / `parser` / `leg` / `provider`
有四条以上实现或明确规划，Postgres 没有。

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 抽象 `VectorStore` 接口，先只实现 PG | 为一个不存在的第二个实现付接口税。按 D-007 的规则，等第二个实现出现再反推接口——而现在连第二个实现的方向都没有 |
| 把「存储引擎」做成设置页的一个条目（哪怕写着「仅 Postgres」） | 那是一条永远点不动的设置。M0 设置页自己否决过这种条目（disabled 的 Switch） |

**影响**：

- `PRD.md` §1 非目标加一条「可切换的存储 / 向量引擎」
- `TECH.md` §7.2 明确列出「明确不做成接缝的」清单
- 若将来真要换（触发条件见 D-024：HNSW 装不进内存、跨库检索的组织需求），
  那时才从第二个实现的共同点反推接口，而不是现在猜

## D-032 M1 把检索单元下沉到分块，但前端契约不变

**背景**：M0 的检索单元是**文档**：通道返回文档 id，片段是命中之后拿查询词
去 `strpos` 猜位置，猜不到就退回头 240 字（`search/index.ts` 的 `fetchHits`）。
M1 的产品要求是「引用指回原文位置」，而文档级命中点不出位置。

同时 `docs/PRD.md` §5.6 的 trace 里已经承诺了两件 M0 做不到的事：
「用 jieba 切分查询词」与「读取命中的文档并**合并相邻分块**」——
没有分块表，第二句是空话。

**决定**：检索单元下沉到分块，**但 `SearchHit` 的形状不变**。

| | M0 | M1 |
|---|---|---|
| 通道返回 | 文档 id + 名次 | 分块 id + 名次 |
| 引用定位 | `strpos` 猜的位置 | 分块自身的 `[start_at, end_at)` |
| 相邻上下文 | 固定窗口 | 合并相邻分块（同文档、`idx` 连续） |

`SearchHit` 仍是 `{documentId, title, snippet:{text,start,end}, matchedBy}`，
服务端从「文档」换成「分块」再组装回这个形状。所以界面、引用卡片、
跳回原文并高亮都不用改，而位置从「猜的」变成「索引里记的」。

**三处刻意的设计**：

1. **chunk id 是确定性的**（`${documentId}:${idx}`）。重建索引后同一篇的同一段
   仍是同一个 id，于是 `chunk_embeddings` 上的写入是 `ON CONFLICT DO UPDATE`
   而不是插新行——否则每重建一次就攒一批孤儿向量，而且表格增长是静默的
2. **偏移相对完整正文**，不是相对分块。引用与高亮直接可用，不需要再换算一层
3. **不引入 `is_enabled`**（WeKnora 有，`RESEARCH.md` §1.2）。它的用途是
   「不删也能把某段排除出检索」，而那要先有一个「排除这一段」的动作才成立。
   先加后忘的字段会变成没人读的列

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 保持文档级，引用位置继续靠 `strpos` | 那就永远做不到「引用指对了原文位置」这条 M1 判据。段落级高亮是这一期的核心收益 |
| 让 `SearchHit` 带上 `chunkId` | 前端没有用它要做的事（跳转与高亮都只需要 documentId + 偏移）。为将来的可能性加字段是最容易变成死代码的一种改动 |
| `chunks` 表带 `is_enabled` | 见上。加一个没有动作对应的开关字段 |
| 分块时把 `search_text` 省掉、检索时现算 | 违反铁律 4（中文必须预分词），且每次查询都要对全部分块做分词，索引也用不上 |
| 用随机 id + 一张「分块哈希 → id」映射表 | 为了同样的确定性，多一张表和一次查询。`${documentId}:${idx}` 已经够了 |

**影响**：

- 新增 `chunks` 表（含 `search_text` 的 GIN 与 `content` 的 trigram 两个索引，
  与 `documents` 上的同构）与 `chunk_embeddings` 表（按维度分 partial index，
  `halfvec` 突破 2000 维上限）
- `lib/chunk.ts` 的三个硬性质：确定性、`body.slice(start,end) === content`、
  按结构切（代码块不可分、标题是边界、段落优先）
- 两条现有通道（keyword / substring）的 SQL 从 `documents` 改到 `chunks`；
  `fuse.ts` 与 `search/index.ts` 的编排一行不用改——它们只认
  「已排序的 id 列表」，这正是接缝当初留对了的证据
- 写入路径增加「重建分块」这一步（同步、纯计算），嵌入是**尽力而为**的
  后续动作：嵌入失败绝不让笔记保存失败。判据是向量表里有没有行，
  所以补嵌入天然可重入
- `POST /maintenance/embed` 分批补嵌入，M1 后段由 `jobs` 表 + worker 接管。
  **批处理逻辑与触发方式无关**，先证明逻辑对，再决定谁来按按钮

**验证方式**（TECH.md §9.5 的四条，这里说明为什么是这四条）：
分块的正确性无法靠「跑一遍看着对」确认——三段文本切出来都是三段。
所以断言必须落在**可复算的性质**上：偏移可逆（`body.slice` 逐字节等于 `content`）、
确定性（两次运行逐字节相同）、覆盖完整（各块并集等于正文）、配置分层回落。
这四条各对应一类静默失效：高亮偏了、向量表膨胀、有段落永远搜不到、
界面改了不生效。

**实测补充**：HNSW 索引建在 `embedding::halfvec(1024)` 这个**表达式**上，
查询必须写同一个表达式并带 `WHERE dimension = 1024`，否则索引静默不命中、
退化成顺序扫描。这与 D-024 记的「门槛谓词下推」是同一类问题
（SQL 形状决定索引是否用得上），所以它同时写进了 TECH.md §10 的坑表。

## D-033 服务端的开发与构建也交给 Vite（tsx / tsdown 退役）

**背景**：服务端原先用三套工具干三件事：`tsx watch`（开发热重启）、
`tsdown`（生产构建）、外加一份 `alwaysBundle` 手写列表。这带来两个问题：

1. **同一件事（编译 TS）在两套工具里各写一遍。** 前端是 Vite，后端是
   rolldown（tsdown 的内核），配置、忽略规则、别名、目标语法各说各话。
   而 `@mimir/shared` 以源码发布（D-023），「谁来编译它」的答案因此有两个版本
2. **`alwaysBundle` 是一份会漏的手写列表。** 每加一个 workspace 包都要记得加一行，
   漏掉的症状是**生产容器启动才报错**，本地开发完全正常——D-023 本身就是踩了这个坑
   之后写的

Hono 官方有 `@hono/vite-dev-server`：把请求交给一个导出 `fetch` 的应用，
自己负责监听与模块转换。

**决定**：服务端的两条链路都改用 Vite，与前端同一套工具、同一个版本
（`vite` 进 catalog，两个包都用 `catalog:` 引用）：

| | 之前 | 现在 |
|---|---|---|
| 开发 | `tsx watch src/index.ts` | `vite` + `@hono/vite-dev-server` |
| 生产构建 | `tsdown` | `vite build`（SSR 构建 + `preserveModules`）|
| workspace 包编译 | 手写 `alwaysBundle` 列表 | 链接的包默认内联，无列表 |

**三条不能改的契约**（都写进了 `apps/server/vite.config.ts` 的注释，
并有 `plugins.test.ts` 的断言守着）：

- **`preserveModules` 不能关**。`lib/static.ts` 按「本文件所在目录往上两级」
  推导前端产物位置、`db/migrate.ts` 按 `../../drizzle` 找迁移目录。
  打成 chunk 后这两个推导静默算错——静态资源 404，而构建是成功的
- **第三方依赖必须保持 external**（SSR 构建的默认行为）。
  `@node-rs/jieba` 是原生模块，打进产物会丢掉平台二进制
- **workspace 包必须被编译进产物**（也是默认行为）。把它 external 化只需要
  一行配置，症状就是 D-023 那个启动报错

**否决**：

| 方案 | 为什么不用 |
|---|---|
| 只在开发用 Vite，生产继续 `tsdown` | 「谁来编译 shared」仍然有两个答案，而生产那条才是会静默出错的那条。换一半等于把复杂度留在原地 |
| 生产用 `@hono/vite-build/node` | 它会给应用**追加**一段 `serve()` 包装（自己的监听与信号处理）。而我们的入口已经自己调 `serve()`——两段监听会撞端口。而且它固定输出单个 `index.js`，`db/migrate.js` 这个第二入口没有位置，静态资源的拷贝也要重新安排 |
| 用 Vite 的 lib 模式（`build.lib`） | 输出形状围绕「发布一个包」设计（`es`/`cjs` 双格式、单一入口），与「产出两个可执行入口、保持目录结构」不是一回事 |
| 保留 `tsx watch`，只换构建 | 开发失去真正的模块级失效（tsx 是整进程重启），而两套工具的收益差距正是这次要消掉的 |
| 用 Vite 的 `ssrLoadModule` 自己写 dev 中间件 | 官方插件就是这件事的封装（含排除规则、HTML 注入、HMR 失效处理）。自己写一遍只会多一份要维护的实现 |

**影响**：

- 根 `package.json` 的 `build` / `dev` 不用改：两个包都还是 `vite build` / `vite`
- `vite` 进了 catalog：前后端版本由结构保证一致（错开的症状是
  前端代理指到一个行为不同的后端）
- 服务端 `vite.config.ts` 是新的必读文件，`server` 段是 **API 端口**（不是前端端口）。
  `strictPort: true`：占用时报错而不是换端口，否则前端代理会指向一个没人监听的地址
- 服务端入口拆成三个文件，各有明确的分工（原先 `src/index.ts` 一个文件干两件事）：
  `boot.ts`（启动准备 + 装配，两个入口共用）、`dev.ts`（dev 入口，只导出 app）、
  `index.ts`（生产入口，起监听）
- `pnpm db:migrate` 仍走 `tsx src/db/migrate.ts`（本地脚本，不需要产物）；
  但**编译后的迁移脚本存在**（`dist/db/migrate.js`），容器里可以
  `node dist/db/migrate.js`——它不再依赖 tsx 在镜像里可用
- 构建产物多一个 `dist/_virtual/`（Vite 的运行时辅助代码），这是产物、不进 git

**验证方式**：不只看「构建成功」——静默失效正是这次要防的。

- **dev**：`/healthz` 200、未鉴权 `/api/documents` 401、改一行代码后同一个
  进程里立刻生效（不是靠 `tsx` 的整进程重启）、前端 5173 的 `/api` 代理照常
- **build**：`dist/index.js` 与 `dist/db/migrate.js` 都在（深度正确）、
  产物里没有裸 `@mimir/*` import、`@node-rs/jieba` 保持 external
- **生产冒烟**：`node dist/index.js` 起来后 `/` 与 `/docs` 深路由 200、
  静态资源带正确 MIME、未鉴权 API 401、目录穿越请求回落到 index.html
- **迁移**：编译后的 `dist/db/migrate.js` 对**空库**跑通（12 张表、
  `pg_trgm` + `vector` 扩展、3 条迁移记录、两个检索索引都在）
