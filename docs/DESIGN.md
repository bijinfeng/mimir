# mimir 设计规范

这份文件回答一个问题：**界面上的每个视觉决定，值是多少、为什么是这个值。**

它不是组件库文档——组件用 antd，用法看官方。这里只写 mimir 自己的那部分：
哪些用了 antd 默认、哪些覆盖了、为什么。

代码侧的真相来源是 `packages/renderer/src/theme/tokens.ts`，本文档解释它。
两者冲突时以代码为准，但请把文档一起改掉。

## 与原型的分工

`output/index.html` 是**交互原型**，本文档是**规范**。两者覆盖的层次不同：

| 层 | 谁说了算 | 为什么 |
|---|---|---|
| 值（颜色、字号、间距、动效） | **本文档** | 本文档的值是实测出来的：原型里 `#1677ff` 当文字只有 3.61:1，本文档改用 `colorLink` 并算了 5.50:1。`design.test.ts` 守着这条线 |
| 形态（每个组件长什么样、由哪些值组成） | **§8** | 已定型的界面形态写在这里，原型仅供演示 |
| 交互（点什么会发生什么） | `PRD.md` §5 | 产品交互以需求文档为准 |

原型可能保留早期布局；冲突时以本文档的现行视觉规范和 `PRD.md` §5 的
交互契约为准，不把历史原型当成实现依据。

## 0. 三条设计原则

原则不是装饰。每条都对应下面具体的取舍，评审时可以拿来问「这个决定服务哪一条」。

### 0.1 内容是主角，界面是容器

这是一个**读和写文字的产品**，不是仪表盘。所以：

- 界面本身的颜色克制到近乎无色——只有一套中性灰加一个品牌蓝
- 语义色（成功/警告/错误/信息）只出现在真的有状态的地方，不做装饰
- 正文行距 1.75，比界面元素（1.57）更宽松。中文正文需要更多呼吸
- 内容列的宽度固定 **760px**——同一条内容在列表里和详情里不该有两种宽度

反面例子：给每个类型的文档配一个不同的高饱和标签色。看起来丰富，实际上让
「资料」和「笔记」的区别被淹没在色彩噪音里。

### 0.2 状态必须能被看见，且必须带得走

这是 mimir 从原型阶段就反复出现的主题（见 `PRD.md` §5）：

- 保存状态常驻可见（正在保存 / 已保存 / 失败可重试）
- 检索过程默认折叠但可见（思考 N 轮 · 调用 M 次工具）
- 失败路径每类给不同出路，不给一个统一的「重试」

设计上的后果：**状态色不是装饰，是信息**。所以它们的对比度必须达标——
一个看不清的「保存失败」等于没有提示。见 §3 的实测表。

### 0.3 默认值要能直接用在中文内容上

antd 的默认字体栈、行高、圆角是按英文界面调的。中文内容有三处不同：

| | 英文界面 | 中文内容 |
|---|---|---|
| 行距 | 1.5 足够 | 需要 1.75，汉字是满格方块 |
| 字重 | 400/600 分明 | 中文细体在小字号下糊，正文用 400、标题用 600/700 |
| 字体栈 | 系统 UI 字体 | 必须补 `PingFang SC` / `Microsoft YaHei` 兜底 |

## 1. 为什么以 Ant Design 为底

antd 6 的设计价值观（Natural / Certain / Meaningful / Growing）与 mimir 的需求
重合度高，尤其是 **Certain**——「用户始终知道自己的状态」，这正是 §0.2。

采纳的部分：

| 采纳 | 理由 |
|---|---|
| 4px 间距网格（4 / 8 / 16 / 24 / 32） | 够密也够整，不与任何组件库冲突 |
| 主色 `#1677FF` | 蓝色读作「可信、专注」。原型已用它，无需更换 |
| 字体阶（12 / 14 / 16 / 20 / 24 / 30 / 38） | 层级够用，不再自造一套 |
| 圆角语义（控件 6 / 表面 8 / 全圆只给头像徽标） | 与「容器」的定位一致 |
| 动效时长（0.1 / 0.2 / 0.3s） | 快反馈、中过渡、慢表面，分档合理 |
| 三层表面模型（布局底 / 容器底 / 浮层底） | 用阴影而非颜色区分层级，换主题时不塌 |

**技术上也一并通过**：开 `cssVar`，antd 把自己解析后的值以 `--ant-*` 变量注入。
这样内容排版（编辑器正文）和 antd 组件共用同一套灰阶，
不会出现「界面是 0.88 黑、正文是另一个黑」。

## 2. 不采纳的部分

不是「antd 不好」，而是这三处按 mimir 的内容形态必须改。

### 2.1 默认字体栈缺中文兜底

antd 默认：`-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, ...`

在 Linux 服务器上的浏览器里会一路落到 `sans-serif`，中文可能渲染成点阵字体。
mimir 的字体栈（`tokens.ts` 的 `FONT_SANS`）在系统 UI 字体后补：

```
'PingFang SC', 'Hiragino Sans GB', 'Microsoft YaHei', sans-serif
```

**字体栈只有一处定义**：`tokens.ts` 里的 `FONT_SANS` / `FONT_MONO` 常量。
antd token（`fontFamily`）与文档级样式（`styles/global.ts` 的 `body`）都从它取值，
不重复写第二份。两处字体栈必然有一天不一致。

### 2.2 正文行高 1.5 对中文偏紧

界面元素（按钮、标签、表单）沿用 antd 的 1.57 没问题——它们是一行短文本。

**内容正文改用 1.75**。汉字没有 x-height 的视觉缓冲，1.5 行距下相邻两行会
「粘」在一起，长文阅读时疲劳感明显。

### 2.3 默认圆角 6px 对三栏布局偏小

antd 默认 `borderRadius: 6`。mimir 的面板级元素（导航项、列表项、卡片）
用 6px 时转折处显得毛糙，尤其在大屏 1x 缩放下。

**改为 8px**（`borderRadius: 8`），antd 会派生：`borderRadiusSM: 6`（控件）、
`borderRadiusLG: 10`（卡片/浮层）。控件走 6、表面走 8/10，层级差异保留。

## 3. 颜色

### 3.1 antd 默认的语义色在浅底上不达标

这是本项目最值得记下的一处实测发现。antd 的语义色设计是**给图标和边框用的**，
不是给文字用的。把它们当文字放在同语义的浅底上，实测对比度：

| 色对 | antd 默认 | 对比度 | 判定 |
|---|---|---|---|
| 成功文字 on 成功浅底 | `#52c41a` on `#f6ffed` | **2.21:1** | 不合格 |
| 警告文字 on 警告浅底 | `#faad14` on `#fffbe6` | **1.83:1** | 不合格 |
| 错误文字 on 错误浅底 | `#ff4d4f` on `#fff2f0` | **2.99:1** | 不合格 |
| 信息文字 on 信息浅底 | `#1677ff` on `#e6f4ff` | **3.66:1** | 仅够大字号 |
| 三级文字 on 白底 | `rgba(0,0,0,.45)` | **2.75:1** | 不合格 |

WCAG AA 要求正文文字 ≥ 4.5:1。**原型里手挑的那套反而是达标的**
（5.24 / 4.58 / 5.48 / 5.78:1），因为它们是按「当文字用」选的。

**决定：采纳原型那套深阶色，覆盖 antd 的语义文字色。**

### 3.2 一个陷阱：不要替换种子色

直觉做法是把 `colorSuccess` 从 `#52c41a` 改成深绿 `#137333`。
**不要这么做。** 实测后果：

```
colorSuccess: '#137333'  →  antd 派生 colorSuccessBg: '#a8b3aa'   ← 灰绿脏色
```

antd 的派生算法假定种子是亮色，改了种子，所有派生色（bg / border / hover）
一起跑偏，而且跑偏的方向不可预测。

**正确做法：种子保持默认，只覆盖叶子 token。**

```ts
// ✓ tokens.ts 实际写法
colorSuccessBg: '#e6f4ea',    // 浅底：叶子，直接给值
colorSuccessText: '#137333',  // 文字：叶子，直接给值
// colorSuccess 不动
```

### 3.3 文字阶（四级，每一级都有用途）

antd 默认四级是同一黑色的四档透明度，实测三级（0.45）只有 2.75:1。
改成不透明色，并把「视觉更弱」这件事用**字号和字重**表达，而不是只靠变淡。

| 层级 | Token | 值 | 用途 | 四种底上的对比度 |
|---|---|---|---|---|
| 文字-1 | `colorText` | `#1f2329` @ 0.88 | 正文、标题 | 10.23 – 10.89 |
| 文字-2 | `colorTextSecondary` | `#5c6570` | 摘要、表单标签、引用原文 | 5.47 – 5.91 |
| 文字-3 | `colorTextTertiary` | `#68707c` | 时间戳、路径、计数 | 4.63 – 5.00 |
| 占位/禁用 | `colorTextQuaternary` | `#8b939c` | 输入框占位符、禁用态 | 2.88 – 3.11 |

「四种底」= 容器底 `#fff` / 列表底 `#fcfcfd` / 导航底 `#fbfbfc` / 布局底 `#f5f6f8`。
文字阶必须在每一种上都达标——只测白底会漏掉「元信息落在导航列上」这类真实组合。

**文字-3 的取值是硬的**：`#6b7280`（Tailwind gray-500）在布局底上只有 4.47，
差一点；`#68707c` 才是四底全过的最小改动。

**占位符允许低于 4.5**。它不承载信息，用户看不见也不影响完成任务；但低到
2:1 以下就等于没画，所以守一个 3:1 的下限。

### 3.4 语义色对（必须成对使用）

| 语义 | 文字色 | 浅底 | 对比度 |
|---|---|---|---|
| 成功 | `#137333` | `#e6f4ea` | 5.24:1 |
| 警告 | `#b45309` | `#fff3e0` | 4.58:1 |
| 错误 | `#c5221f` | `#fef7f6` | 5.48:1 |
| 信息 | `#1a56c4` | `#e8f0fe` | 5.78:1 |

**规则：状态色永远成对出现，不要拆开用。** 单独拿 `#b45309` 当强调色配白底，
或者拿浅底配中性灰文字，都会破坏这组已经校准过的关系。

### 3.5 主色与链接色是两个角色

`#1677ff` 作**填充**（按钮底、选中态底）没问题：白字压在上面 4.10:1，
按 WCAG 大字号/非文本标准足够，且它是 antd 的既定手感。

但 `#1677ff` 作**文字**不够——在选中态浅底 `#e8f1ff` 上只有 3.61:1，
而「选中项的文字」正是导航里最常见的组合。

**所以文字角色单独用 `colorLink: #0958d9`**（antd 同色阶第 7 阶）：

| 组合 | 对比度 |
|---|---|
| 链接色 on 容器底 | 6.16:1 |
| 链接色 on 选中项底 `#e6f4ff`（`colorPrimaryBg`） | 5.50:1 |
| 链接色 on antd 浅蓝 `#e6f4ff` | 5.50:1 |
| 白字 on 主色填充 `#1677ff` | 4.10:1 |

**悬停 / 按下的链接色要显式给，否则比常态更弱。** antd 从种子派生的
`colorLinkHover` 是 `#579df2`（浅色白底 **2.80:1**）、深色那边更是
`#15417e`（**1.80:1**）——鼠标一放上去链接就淡到像被禁用。
两个键不是种子名（`formatToken` 不删），所以直接写进主题：

| 外观 | `colorLinkHover` | `colorLinkActive` |
|---|---|---|
| 浅色 | `#1562d6`（白底 5.60、选中底 5.00） | `#0f4bbd`（7.60 / 6.79） |
| 深色 | `#a5d0ff`（容器底 11.29） | `#c6e2ff`（13.58） |

`design.test.ts` 守「两档都 ≥ 4.5:1 且不比常态更弱」。

一条推论：**不要把 `colorPrimary` 直接用在文字上**。要强调的文字用 `colorLink`，
要强调的填充用 `colorPrimary`。

这条推论**对 antd 自己的组件同样成立**：它们有一批默认取 `colorPrimary`
的文字角色（`Tabs.itemSelectedColor` 就是），不覆盖就会同时犯两处错——
文字对比度不够，且与同排未选中项的强调关系颠倒。这类角色的处理见 §3.8 的表，
组件级 token 写在 `theme/tokens.ts` 的 `COMPONENT_TOKEN`（两套外观各一份）。

选中态（导航项、列表项）的底色用 antd 派生的 `colorPrimaryBg`（`#e6f4ff`），
不再单独定义。原型里的 `#e8f1ff` 与它对比度等价（5.41 对 5.50），
用 antd 派生值可以少维护一个变量。

### 3.6 表面层级（三层 + 一列底）

antd 是三层——布局底 / 容器底 / 浮层底，其中容器底和浮层底同色，
靠阴影区分。

mimir 加第四层：**列底**。三栏布局里「中栏列表」和「左栏导航」需要与右栏内容
有一道不靠边框的区分，用大面积的 `#f5f6f8` 太重，用边框又太吵。

| 层级 | 浅色 | 深色 | 用在哪 |
|---|---|---|---|
| 布局底 | `colorBgLayout` `#f5f6f8` | `#0b0c0e` | 应用背景、登录页 |
| 容器底 | `colorBgContainer` `#ffffff` | `#141618` | 内容区、卡片、浮层 |
| 列底-列表 | `customToken.tintList` `#fcfcfd` | `#111315` | 中栏列表、文档大纲 |
| 列底-导航 | `customToken.tintNav` `#fbfbfc` | `#0f1113` | 左导航、浮层页脚 |

列底色是 antd 没有的语义，走 mimir 的 `customToken`——定义在
`theme/customToken.ts`，由 `MimirProvider` 注入，代码里用 `token.tintList`
消费。这样它有类型（拼错报错）、有作用域（跟着 ThemeProvider 走），
而且只有一处定义。

**深色下四层的相对顺序与浅色一致**（布局底最暗、容器底最亮，两个列底夹在
中间且互不相同）。这不是自动成立的：深色若照搬浅色的值，列底会比容器底
还亮，于是「右栏内容区」看起来像凹下去的，而没人会说得出哪里别扭。

两套外观的列底与容器底、布局底都必须能分开（`design.test.ts` 守 ≥ 1.02 /
1.04）。阈值刻意低——这个差本来就是「几乎看不见的一层冷色」，规范要的是
分隔，不是边框。

### 3.6.1 热力图色阶（四档 + 一个「未知」态）

贡献图需要一条四档色阶，antd 没有这个语义，所以同样走 `customToken`
（`heatL1`–`heatL4`）。浅色取 antd 蓝色阶的第 2 / 3 / 5 / 7 阶：

| Token | 浅色 | 深色 |
|---|---|---|
| `heatL1` | `#cfe6ff` | `#10395e` |
| `heatL2` | `#91caff` | `#1c5fa8` |
| `heatL3` | `#4096ff` | `#3b8fe6` |
| `heatL4` | `#0958d9` | `#7bbcff` |

**空格子用 `colorFillQuaternary`（浅色 `rgba(0,0,0,.04)`、深色
`rgba(255,255,255,.04)`），不用容器色。**
理由是这条：antd 的 `colorPrimaryBg`（`#e6f4ff`）与白底只差 1.05:1，
拿它当最浅档会让「有一点活动」和「完全没活动」在屏幕上几乎一样——
**而这正是贡献图最常见的失败**（空和有活动看起来一样）。所以最浅档
往下压到 `#cfe6ff`，空格子反过来填一层浅灰，两边都让开。

**深色下这张图是「越忙越亮」，方向与浅色相反。** 底是暗的，所以色阶必须
往亮走；照搬浅色那套深蓝会在深底上糊成一片（`heatL1` `#cfe6ff` 与深色
容器底差 8:1 以上，看起来像整片格子都被填满了）。判据仍是同一条：
最浅档与空格子要能分开、相邻两档要能分开。`design.test.ts` 用同一条规则
守两个方向（深色断言「明度递增」、浅色断言「明度递减」）。

四条约束：

1. **相邻档要能分开。** 断言写「相邻两档 ≥ 1.15」，不是 3:1——
   格子不承载文字，靠**形状**而不是可读性；但低于 1.1 就等于四档变两档
2. **「有调用但用量未知」用斜纹，不用颜色。** 45° 的
   `repeating-linear-gradient`，条纹色 `colorTextQuaternary`，底
   `colorFillQuaternary`。**它不能退化成空格子**——那等于图在说
   「我那天没用」，而事实是「用了但没上报」。斜纹是唯一的非颜色线索，
   色盲用户也能分辨
3. **今天那格加一圈 `colorPrimaryBorder` 描边。** 当天的数据不完整，
   描边说明「这一格还在长」
4. **图例标出最深一档的区间**（如「最深一档 ≥ 12.3 万」）。分档按这一年的
   分位数算，不写出来用户只能猜「深蓝是多少」。**范围固定一年**，
   所以一档对应一个确定的区间，不需要再声明「按当前范围分档」
   （`PRD.md` §5.11：第一版有范围切换，那句声明是它的必要补偿）

### 3.7 来源徽标

`PRD.md` §2.3 要求「资料与笔记必须一眼可分」，所以每种来源有自己的色对。
**两组**色对分浅 / 深两张表（`components/DocumentBadges.tsx` 的
`STATUS_STYLE`），两套都实测达标。来源徽标随 D-047 退役、收件箱徽标随
D-054 退役、归档徽标随 D-065 退役，剩下的都是**偏离常态**的状态——`ready`
刻意不给徽标：它是绝大多数文档的状态，给每张卡片都盖一个「已就绪」
等于什么都没说：

| 徽标 | 浅色（文字 on 底） | 对比度 | 深色（文字 on 底） | 对比度 |
|---|---|---|---|---|
| 提取失败 | `#c5221f` on `#fef7f6` | 5.48:1 | `#ff8f8a` on `#2f1b1c` | 7.38:1 |

**原先还有第八组 `pdf`，已删除（D-044）。** `kind` 是**来源**而不是格式：
PDF、Word、Excel、图片、压缩包都是「文件」，共用一个徽标；格式写在元信息行里
（§8.3）。按「一格式一色」走下去，每加一种格式就要多一组色对——而格式是
**开放集合**，来源才是封闭的。这正是 §0.1 反对的「给每个类型配一个颜色」。

**格式不是徽标。** 它是一条中性文字（`colorTextTertiary`），与来源徽标并排
但语义不同：徽标回答「从哪来」，格式回答「是什么」。给格式配底色会立刻遇到
一个问题——格式有几十种，而配色要两套外观各校准一次。

**文档元信息里的「手动编辑 / AI 整理」不走这张表**，它们直接成对使用语义
token（`DocumentPanel.style.ts` 的 `originManual` / `originAuto`）：
手动编辑是信息色对（`colorInfoText` on `colorInfoBg`），AI 整理是
中性色对（`colorTextSecondary` on `colorFillTertiary`）。原先它们是写死的
浅色 hex，深色下会变成「深蓝字压在浅蓝底上」——那两种标注是**状态**，
用语义 token 才跟着外观走。

**上传件的标注是「本机导入」**（走 `originManual` 那一对）。说「AI 整理」
是在说一件没发生的事，而元信息行里的每一条都该是真的。

**实现注意**：这些是 `bg + 文字` 的自定义配色，用 `Tag` 的 `color` 传预设色
（`color="green"`）走的是 antd 自己的调色板，与上表无关——要用 `KindBadge`
这类会说两套外观的组件。

预设色板的对比度由 antd 决定，我们无法保证；而且要改就得改主题，不该散在页面里。
色对集中在 `DocumentBadges.tsx` 一处，页面只传来源类型——**深色那套也一样**，
不要在页面里写 `appearance === 'dark' ? … : …`。

### 3.8 深色不是浅色取反

深色（`theme/tokens.ts` 的 `mimirDarkTheme`）是一套**独立的、逐项校准过**的值，
不是在浅色上套 `darkAlgorithm` 就完事。四处必须手工处理的地方：

| 问题 | 为什么自动算法不够 | 处理 |
|---|---|---|
| 链接色 | antd 深色**自带**的 `colorLink` 在容器底上只有 **3.50:1**，不达 AA。而「与种子同名的覆盖值」会被 `formatToken` 丢掉——在 `token` 里写 `colorLink` 不生效，实际值是算法派生的 `#4b93dc` 系，在选中底上只有 3.97:1 | 用**校准层**（`MappingAlgorithm`，跑在算法链最后）写最终值 `#79b8ff`：容器底 8.74:1、选中底 6.17:1 |
| 焦点环 | 深色算法把 `colorPrimaryBg` 与 `colorPrimaryBorder` 设成**同一个值**（`#15325b`）。前者是选中项的底、后者是焦点环——同值意味着焦点环落在选中项上完全看不见（实测 1.00:1） | 单独校准描边为 `#4b93dc`（与选中底 3.97:1） |
| 文字阶 | antd 深色默认的三级是白色 45% 透明度，在容器底上只有 4.54:1，刚好压线且是**最弱的那一档**（元信息、路径、计数全用它） | 提到 52%，并把四级从 25% 提到 40% |
| Tabs 的选中标签 | `itemSelectedColor` 默认取 `colorPrimary`——那是**填充**角色（§3.5），而同一排里**未选中**的标签走 `colorText`，于是强调关系是反的：深色选中 `#1668dc` 3.50:1 对未选中 13.23:1，浅色 `#1677ff` 4.10:1 对 10.89:1（都在容器底上，13.5px 正文低于 AA） | 给 `theme.components.Tabs.itemSelectedColor` 显式取值（组件 token 是**最终值**，不参与算法派生，所以两套外观各写一次）：深色 `#79b8ff` 8.74:1、浅色 `#0958d9` 6.16:1。ink bar 是填充角色，仍由 antd 取 `colorPrimary` |

其余颜色（表面、语义色对）按深色重挑，但**沿用浅色的层级关系**：
文字阶仍是四级、语义色仍成对、表面仍是三层加两列底。

**跨外观的不回归规则**：`design.test.ts` 里有一条逐项比较——深色的每一个
文字色在容器底上都必须**不弱于**浅色对应的那个。深色最常见的退化是
「看着还行就用」，而单看深色的截图判断不出来。

## 4. 字体与排版

### 4.1 字体栈

```ts
// packages/renderer/src/theme/tokens.ts
FONT_SANS = "-apple-system, BlinkMacSystemFont, 'Segoe UI',
             'PingFang SC', 'Hiragino Sans GB', 'Microsoft YaHei', sans-serif"
FONT_MONO = "ui-monospace, SFMono-Regular, 'SF Mono', Menlo, Consolas, monospace"
```

界面与内容共用同一套 sans。正文里的等宽只用于：行内代码、代码块、文件路径、
检索关键词、插件的 `seam` 标识。

### 4.2 字号阶梯

| 名称 | 字号 | 字重 | 行高 | 用在哪 |
|---|---|---|---|---|
| 展示 | 28px | 700 | 1.3 | 文档标题（编辑器 H1） |
| 页面标题 | 20px | 650 | 1.4 | 设置页 H1、内容区 H2 |
| 小节标题 | 16px | 600 | 1.5 | 卡片标题、空态标题 |
| 界面正文 | 14px | 400 | 1.57 | 正文、按钮、列表项、输入 |
| 辅助 | 13px | 400 | 1.6 | 列表摘要、次要说明 |
| 元信息 | 12px | 400 | 1.6 | 时间戳、路径、计数、标签 |
| 徽标 | 10.5–11.5px | 500–600 | 1.6 | 类型徽标、字母间距 +0.02em |

**下限是 10.5px**，且只用于徽标——它们有底色衬托。任何需要连续阅读的文字
不小于 12px。

字重只用 400 / 500 / 600 / 700。**不用 300**：中文细体在 14px 下发虚。
`font-weight: 550` 这类值在原型里能用，但在只装了 400/700 的系统字体上会被
吸附到最近的一档，效果不可控——规范内统一用整数档。

**代码侧的真相来源是 `theme/tokens.ts` 的 `FONT_SIZE`**（见
`docs/DECISIONS.md` D-017）。九档，每档对应一个**角色**：

| 档 | 值 | 角色 |
|---|---|---|
| `display` | 28 | 文档标题 |
| `pageTitle` | 19 | 正文 H2、设置页 H1 |
| `section` | 16 | 正文 H3、卡片标题 |
| `body` | 14 | 按钮、输入、对话正文 |
| `item` | 13.5 | 列表项标题、导航项 |
| `excerpt` | 13 | 摘要、表格、代码 |
| `note` | 12.5 | 次级说明、引用片段、检索过程 |
| `meta` | 12 | 时间戳、路径、计数 |
| `badge` | 11.5 | 徽标、计数 |

**组件里不要写字面的 `font-size`**——`design.test.ts` 会扫源码拦下来
（扫描根含 `packages/chat/src`，见 §10.4）。包内写的是
`var(--mimir-chat-font-note, 12.5px)` 这种形式（值由宿主填，回退值与上表
一致）。唯一的例外是图标字形，必须在行内标注 `非文本` 才放行。

采 .5 级差而不是整数档：这份界面信息密度高（列表项里同时有标题、摘要、
徽标、计数），整数档在相邻层级之间跳得太大。

### 4.3 内容区（Markdown 渲染）

正文排版只有**一份**：`components/ContentTypography.style.ts` 的 `content`。
Tiptap 渲染出的 `<h1>` `<pre>` `<table>` 是裸 DOM、不是 React 组件、拿不到
className，所以从挂载点的祖先类名往下写嵌套选择器——这正是 `createStyles`
里嵌套选择器的用途，而且规则有作用域，不会泄漏到别处。

**编辑器与只读视图共用这一个类。** 两个视图都让 Tiptap 渲染同一份
Markdown（`MarkdownBody` 的注释解释了为什么不用第二个渲染库），所以排版
必须同源。这一条曾经各自手抄一份，漂移出四处且都不报错：

| 元素 | 曾经（编辑态 / 只读态）| 现在 |
|---|---|---|
| `img` | **无规则** / `max-width:100%` | 共用（大图不再撑破内容列）|
| 行内代码底 | 字面量 `#f0f1f3` / `fill-secondary` | `fill-secondary` |
| 行内代码字号 | 12.5 / 13 | 13（`excerpt`）|
| 任务列表 | 都没处理 | 共用 |

| 元素 | 规则 |
|---|---|
| 段落 | 上下间距 12px，行高 1.75 |
| H1 | 28px/700，下间距 16px |
| H2 | 20px/600，上 26px 下 10px |
| H3 | 16px/600，上 20px 下 8px |
| H4-H6 | **没有专门的字号**（浏览器默认 1em / 0.83em / 0.67em 配字重）。编辑器允许写它们（markdown 本来就允许六级标题），只是规范没给它们定档——D-061 |
| 行内代码 | 13px 等宽，`customToken.inlineCodeFg` 色，`fill-secondary` 底（4.93:1） |
| 代码块 | 13px/1.6，`tintNav` 底 + `border-secondary` 边框，圆角 8px |
| 语法高亮 | 注释 `text-3` 斜体、关键字 `colorLink`、字符串 `colorSuccessText`、数字 `colorWarningText`、函数名正文色 + 600（全部实测 ≥ 4.5:1，`design.test.ts` 守）|
| 引用 | 左侧 3px 边框，文字用文字-2，不做背景色 |
| 表格 | 13px，单元格边框 `border-secondary`，表头 `tintNav` 底 |
| 任务列表 | `list-style: none` + flex 一行（复选框与文字同排），已完成项划掉并转 `text-3` |
| 图片 | `max-width: 100%`，圆角 6px |
| 高亮 `mark` | `customToken.highlightBg` 底，字色继承（11.82:1） |
| 链接 | `colorLink`，下划线 + `text-underline-offset: 2px` |

**内容区的颜色一律引用 `--ant-*` 变量**，不写字面量。这样界面灰阶调整时
正文不会掉队。

**语法高亮曾经静默失效**：`CodeBlockLowlight` 挂着 lowlight 与 common 语法包，
解析出的 span 确实带 `hljs-keyword` 之类的类（实测一个五行代码块产出 12 个
span、6 种 token），而全仓没有一条 `hljs` 规则——所有 token 渲染成同一个颜色。
看起来像「编辑器不支持高亮」，实际只是少了 CSS。着色只用既有语义 token，
不新造色值。

**书写区高度**（编辑器专有，只读视图不需要）：`NoteEditor` 给
`.ProseMirror` 一个 `min-height: 46vh`。它是**「点空白处也能接着写」的前提**——
ProseMirror 的高度默认等于内容高度，所以一篇三行笔记的编辑区只有约 98px，
而可见正文列高约 900px，下面 800px 是**死区**；点上去 `activeElement`
仍是 `body`（实测）。给足高度后那一击落进编辑区，Tiptap 把光标放到最近的
文字位置（末行）。

## 5. 间距、形状与阴影

### 5.1 间距

4px 网格。可用值：**4 / 8 / 12 / 16 / 20 / 24 / 32 / 40**。

常用组合：

| 场景 | 值 |
|---|---|
| 图标与文字 | 6–8px |
| 列表项内边距 | 上下 6–10px，左右 10–11px |
| 卡片内边距 | 15–17px |
| 内容区边距 | 上下 28–36px，左右 40px |
| 章节之间 | 20–26px |

### 5.2 圆角

| 值 | 用途 |
|---|---|
| 4px | 徽标、行内代码、小标签 |
| 6px | 控件（按钮、输入框、导航项、列表项） |
| 8px | 表面（卡片、代码块、浮层）、`borderRadius` 基准 |
| 10px | 大卡片（设置页） |
| 12–14px | 对话框、命令面板、输入框组 |
| 全圆 | 仅头像、状态点、计数气泡 |

### 5.3 阴影

只用 antd 给的两档，不自造：

| 档 | 值 | 用途 |
|---|---|---|
| `boxShadowTertiary` | `0 1px 2px rgba(0,0,0,.05), 0 1px 6px -1px rgba(0,0,0,.03), 0 2px 4px rgba(0,0,0,.03)` | 卡片微浮起 |
| `boxShadowSecondary` | `0 6px 16px rgba(0,0,0,.08), 0 3px 6px -4px rgba(0,0,0,.12), 0 9px 28px 8px rgba(0,0,0,.05)` | 浮层：对话框、命令面板、下拉 |

**阴影层次不超过两档。** 三级阴影的差别人眼分辨不出，但会让规范失去约束力。

### 5.4 布局尺寸

**全部两栏**（`docs/DECISIONS.md` D-047）：左导航 + 主区；
文档模式的主区在库（浏览）与详情（阅读）两个状态间切换。

| 元素 | 值 |
|---|---|
| 左导航栏 | 200px（窄屏 180px） |
| 左导航栏（折叠） | **48px** |
| 文档大纲列 | 196px，标题数 ≥ 2 才出现（`PRD.md` §5.10） |
| 内容列 | 760px 居中 |
| 对话列 | 860px 居中 |
| 设置内容列 | 760px |
| 库卡片网格 | 自适应列：`repeat(auto-fill, minmax(260px, 1fr))` |
| 工具条高度 | ≥ 48px |
| 搜索框 / 输入框 | 高度 32px（antd `controlHeight`） |

**内容宽度只有一个值（760px）**。列表项里的摘要是 2 行截断，不是另一个宽度。

**折叠宽度 48px 不随断点变化。** 窄屏那套（180px）只管展开态——折叠若也
跟着变，同一次「折叠」会在两种屏幕宽度下折出两种宽度。48px = 图标 20px +
左右各 14px，与展开态共用同一套内边距节奏，所以折叠时图标的落点与展开态
文字的左边界在同一条竖线上。

**折叠态下 antd 的 `inlineCollapsed` 必须覆写宽度。** 它把菜单硬定成 80px
（实测计算样式 `width: 80px`），48px 的栏装不下，会横向溢出并把右栏顶走。
其余需要一并覆写的三处（分组标签、图标居中、计数）见
`NavSidebar.style.ts` 里 `menuCollapsed` 的注释——它们**各有各的成因**，
不是「顺手调一下」。

**展开态那条 `width: 100%`（占满整行）在 48px rail 里要改成
`calc(100% - 8px)`。** 折叠态菜单项带 `margin-inline: 4px`（图标靠它居中），
与 100% 宽度叠加后项盒 [4, 52] 比栏宽多 4px：图标偏右（中心 28 而非 24）、
body 多出一条横向滚动条（实测 `scrollWidth` 52 对 `clientWidth` 48）。
两条规则都在 `menu` / `menuCollapsed` 里，改一条要看另一条。

### 5.5 断点

| 宽度 | 全部模式 |
|---|---|
| > 1100px | 两栏 200 / 1fr |
| ≤ 1100px | 两栏 180 / 1fr |
| ≤ 880px | 两栏 48 / 1fr——导航**强制折叠**为图标条（隐藏等于断了所有导航） |

**窄屏折叠是「视口决定」，不是「把用户偏好改掉」。** ≤880px 时导航折叠成
48px，栏内**内容**（分组标签、目录树、品牌名）与折叠开关一并退出渲染——
只改网格宽度是不够的：栏里的东西仍按展开态渲染的话，中文标签会逐字竖排、
品牌名与开关叠在一起，全塞进 48px 里（实测 `scrollWidth` 129 对
`clientWidth` 47）。所以这个断点在 `theme/tokens.ts` 定义一次
（`NAV_NARROW_QUERY`），CSS 的 `@media` 与 `lib/nav-collapse.ts` 的
`matchMedia` 共用它；`_app.tsx` 里不再出现这个数字。

用户在宽屏下选的折叠偏好**不被覆盖**——`localStorage` 里始终只存偏好，
窗口变宽后回到那一态。见 D-055。

**同一断点还管两处「按需让位」**（`lib/nav-collapse.ts` 的
`useNarrowViewport`，与导航折叠共用同一个 matchMedia）：

| 面 | ≤880px 的行为 | 为什么 |
|---|---|---|
| 文档大纲（笔记与只读两条路径） | **不渲染** | 大纲列固定 196px（笔记那侧外壳还要再让 220px），420px 视口里正文只剩约 150px——实测一行约 7 个字。正文完整性优先于锚点导航 |
| 设置页分区导航 | 换成 `Select` | 八个分区名排不下，横向 tab 会把某个标签切成半个字（实测） |
| Office 编辑器工具条 | `max-height: 128px` + 自身滚动 | docx 的工具条有八到十个组，420px 视口下折成 **9 行 243px**（占 900px 屏高的 27%），正文只剩一小条。按钮一个不少（不砍功能），但不会把编辑区挤没 |

「问 AI」侧栏在同断点下从固定 400px 改成占满主区：420px 视口减 48px 导航
只剩 372px，400px 面板的右缘会被主区裁掉，输入框右端与发送键都点不到。

办公外壳那条断点在 `packages/office/src/shell/shell.css` 里**写的是字面值
880px**（那个包不认识宿主的断点常量）——宿主改断点时两处要一起看，注释里
写了这条约束。

**移动端不是缩小版**（`PRD.md` §6 待决项）：桌面是「写和整理」，手机是
「速记和查询」，需要单独设计。上表的窄屏规则只是防止布局崩坏，不是移动方案。

## 6. 动效

### 6.1 时长

沿用 antd 三档，**按距离和层级选，不是按组件选**：

| Token | 值 | 用在哪 |
|---|---|---|
| `motionDurationFast` | 0.1s | 悬停、按下、焦点——必须瞬间响应 |
| `motionDurationMid` | 0.2s | 组件内部：展开、折叠、切换 |
| `motionDurationSlow` | 0.3s | 表面级：对话框进出、页面切换 |

**悬停反馈一律 0.1–0.15s。** 原型里的 0.12s 是实测手感，保留。

### 6.2 缓动

| 场景 | 曲线 |
|---|---|
| 入场 | `cubic-bezier(.2,.8,.3,1)`（快出慢停，浮层从上方 6px 落下） |
| 出场 | 比入场快一档，曲线用 ease-out |
| 状态切换 | `ease-out` |

**出场快于入场**：用户已经决定关掉它，等待感只会放大。

### 6.3 只动 transform 与 opacity

不动 `width` / `height` / `top` / `left`——那会触发重排。
展开折叠用 `max-height` 或直接切换 `display`，不做高度动画。

### 6.4 必须尊重 `prefers-reduced-motion`

`styles/global.ts` 里由 `createGlobalStyle` 注入全局降级规则。
这不是可选项：前庭功能敏感的用户会因为 0.15s 的位移而眩晕。

## 7. 组件约定

### 7.1 图标

**用 `@ant-design/icons`，不用 emoji。**

emoji 是字体依赖的，在 Linux 容器里可能渲染成黑白字形或豆腐块；
也不能被主题控制。原型里的 `✓` `✻` 这类字符只用于纯文本状态流，
不作为图标使用。

| 场景 | 尺寸 |
|---|---|
| 行内、按钮内 | 14px |
| 导航项、列表项 | 15–16px |
| 空态、大按钮 | 20px |

同一层级只用一种风格（线性或填充），不混用。

### 7.2 焦点可见

**不移除焦点环。** antd 组件自带，自定义元素用 `:focus-visible` 补
`box-shadow: 0 0 0 3px rgba(22,119,255,.1)` 配 `border-color` 变化（原型既有做法）。

键盘用户必须能看见自己在哪。这是 `ui-ux-pro-max` 检查表里优先级最高的一条，
也是最常被「设计洁癖」牺牲掉的一条。

**例外：文本输入类元素要自己区分输入方式。** 规范规定 `contenteditable`
与 `<input>` 的 `:focus-visible` **永远匹配**（浏览器无法假定用户接下来用
键盘还是鼠标，而文本输入需要焦点提示）。于是笔记正文那个 contenteditable
每次鼠标点进去都会画出一圈原生环 `outline: auto 1px rgb(16,16,16)`，
围着整个编辑区——而点进正文是几乎每次编辑都会做的事。

`lib/input-modality.ts` 记录最近一次输入方式，写到 `html` 的
`--mimir-focus-ring-style` 上（鼠标 `none` / 键盘 `solid`）：

```css
outline-style: var(--mimir-focus-ring-style, none);
outline-width: 2px;
outline-color: var(--ant-color-primary-border);
```

**变量里只存样式关键字，不存完整 ring 值。** 自定义属性里的 `var()` 在
**声明它的元素**上求值，而 `--ant-*` 注入在 antd 组件子树上（§3.4 与
AGENTS.md 样式第 6 条）——声明在 `html` 上的 `var(--ant-color-primary-border)`
取不到值，整个自定义属性在 computed-value 阶段无效，`outline` 退回 `none`，
**键盘用户的焦点环静默消失**（实测过）。

这个模式只用在文本输入类元素上。其余控件继续用标准的 `:focus-visible`
——它们的行为是对的，加一层输入方式追踪只是多余的复杂度。

**一处例外是对话的输入区**（§8.8，D-099）：它是「外层盒子当容器」的结构
（圆角 14px 的框才是可见的输入区），焦点态只提亮**盒子**的边框色，
内层输入框自己的 outline 与 box-shadow 全关——两层焦点提示叠在一起就是
用户看到的双边框。这让「自定义元素补 3px 柔光盘」这条在那一处不适用；
理由是柔光与边框的过渡不同步会让容器看起来抖一下，且 assistant-ui 的
composer 也是这么处理的。

### 7.3 可点击元素

- 必须有 `cursor: pointer`
- 悬停必须有视觉反馈，时长 0.1–0.15s
- 只用图标表达的按钮必须有 `title` 或 `aria-label`（原型里 `<button title="搜索">` 的做法）
- 选中态用 `aria-current` / `aria-pressed` / `aria-selected`，不靠类名猜

### 7.4 禁用态

用 antd 的 `disabled`，不要自定义。**「看起来能点但点了没反应」是最坏的一种**——
要么禁用并降低对比度，要么可用并给出结果。

### 7.5 antd v6 的几处 API 变更

实际跑起来才发现的，写下来避免重复踩：

| 写法 | 状态 | 正确写法 |
|---|---|---|
| `<Tag bordered={false}>` | 已废弃，会打警告 | `<Tag variant="filled">` |
| `<Tag color="green">` | 能用，但走 antd 预设调色板 | 用本规范 §3.7 的色对 |
| `<Modal maskClosable={false}>` | 已废弃，会打警告 | `<Modal mask={{ closable: false }}>` |
| `<Alert message={…}>` | 已废弃，会打警告 | `<Alert title={…}>` |

第二行不是 API 问题，是**对比度不由我们控制**的问题。预设色板的取值由 antd
主题决定，改一处不会同步到规范里。

第三、四行是同一类：**废弃警告与「用了没开」无关**，prop 只要存在就发，
所以挂在应用壳上的那一个 `Modal`（`UnsavedGuard`）会让每个页面加载都在
控制台留一条。而这一屏的语义恰恰是「点遮罩不能走」——不迁移的话，antd 移除
旧 prop 时它会**静默退回**「点遮罩就关」。

### 7.6 `AntApp` 会断掉 height:100% 的链条

`<App>` 包装层默认没有高度，渲染出的 `.ant-app` 会把
`html → body → #root` 的高度链断在那里。症状是登录卡片不垂直居中、
`Layout style={{height:'100%'}}` 只撑到内容高度——**不报错，只是布局不对**。

`styles/global.ts` 里有一条 `#root > .ant-app { height: 100% }` 修它
（`${prefixCls}` 取自主题，antd 换前缀时这条规则跟着换）。
新增顶层容器时如果发现高度不对，先量这一层。

### 7.7 `min-height: auto` 会悄悄撑断高度链

同一类问题的第二处（`docs/DECISIONS.md` D-018）。grid / flex 里的项目
自动最小尺寸是 `min-height: auto`，即「不能小于内容的高度」。于是中栏那
两千像素的列表会把整行撑到两千像素，三栏里那个 `overflow-y: auto`
永远不触发——**整页滚动**，看起来像「列表不能滚动」。

**修法**：三栏外壳与它的三个子项都加 `min-height: 0`，外层加
`overflow: hidden` 兜底。

**排查顺序**：不要只看「那个滚动容器有没有 `overflow-y: auto`」，
要沿**祖先链**找到哪个 `min-height: auto` 把它撑开了。

## 8. 组件形态

上面 §3–§6 定的是**值**（颜色、字号、间距、动效）。这一节定的是**形态**——
每个组件长什么样、由哪些值组成。

**为什么要单独一节**：曾经只有值、没有形态，每个组件各写各的。结果是一个
全仓 11 个不同 `font-size`、导航项与列表项内边距不一致、整理条用饱和警告色的
界面。用户反馈「太粗糙」——粗糙不是某个值错了，而是**没有形态可依**。

**值的优先顺序**：`tokens.ts` / `customToken.ts` > 本节 > 原型。
本节给的数值来自原型的实测（`output/index.html` 的计算样式），
但凡与 `docs/DECISIONS.md` 的实测结论冲突，以那份为准。

### 8.1 导航项（左栏）

```
┌──────────────────────────┐
│ [icon] 全部文档      (17) │  ← 13.5px / 400，padding 6px 10px
└──────────────────────────┘     圆角 6px，间距 1px
    hover  : colorFillTertiary
    selected: colorPrimaryBg + colorLink + 500
```

**计数是胶囊**（`min-width:18px`、`padding:0 6px`、`border-radius:9px`、
`colorFillSecondary` 底）。纯数字贴右边缘会与标题连成一片，读不出「这是数量」。

**图标与文字要真的在同一条中线上——行高不能继承到文字层。**
菜单项设了 `line-height: 30px`（整行高，图标与文字共用的行框），它会
**继承**到里面的文字：13.5px 的中文被排进 30px 的行盒里，行盒上下各留
8px 余量，而中文字形没有西文那种下伸部——墨迹在行盒里天然偏上。实测
「搜索」这一项的文字墨迹中心比图标高 **1.5px**（图标 48.0 / 文字 46.5），
「新建对话」差 0.5px（十字图标的墨迹恰好居中，掩盖了一部分）。用户报的
就是前者。

修法是**只把文字层（label 与右侧 extra）行高压回 `normal`**，不动 li 的
30px 行高（那是行框，改了整行会塌）。压完之后文字由 flex 的
`align-items: center` 真正居中：实测 Δ 从 −1.5px 收敛到 **0**，
右侧 `Ctrl K` 从 +1.0 收敛到 −0.5。残余 ≤0.5px 是字形度量差（中文墨迹
比字体盒中心偏上约 0.5px），不做像素补偿——与知识库 ID 芯片同一条规矩。

**不加描边**。选中靠「底色 + 字色 + 字重」三重线索——单独一道淡蓝描边在
浅蓝底上只有 1.19:1，肉眼看不见，加了只是噪声（见 `design.test.ts` 里那条
测试的注释，它记的就是这个判断被纠正的过程）。

**界面去线（D-070，Notion 对齐）。** 静态分割线一律不画：**分组交给留白与
标签**（「对话」「知识库」分组标签上下的两条菜单 divider 已删）、**分区交给
底色**（侧栏与主区的界线靠 `tintNav` 与 `colorBgLayout` 的色差，右缘竖线已
删——深浅两套都保持「布局底 < 导航底」的次序，色差即边界）。唯一保留画线
理由的是**「固定区 vs 滚动内容」**，而且改成**滚动才显形**：静态时无线，
内容滚动、开始被固定区切断的那一刻淡入（`lib/use-scrolled.ts` 的
`scrollTop > 0` → `data-scrolled` → border-color 过渡；滚回顶部即淡出）。
落在四处：侧栏底部账号行上线、库头部下线、详情标题栏下线、对话输入区上线
（线画在包的 `composerLine` 包裹层，因为消息列表的 scrollTop 归它管——
对话那一份钩子在 `packages/chat/src/hooks/use-scrolled.ts`，**与宿主那份是
刻意的两份**：滚动容器在包内，包 import 不到宿主）。**不显形的场合**：
设置页键值行 / 块之间的行线（表格式信息，行线帮助扫读）、编辑器外壳的工具条 / 子工具条 / 状态行（控件解剖——Office 一族
的母语，且滚动容器在各格式编辑器内部，为一个 hairline 把滚动状态穿透六个
编辑器不值）、命令面板内部的线（输入框下线还兼任聚焦指示，DESIGN §7.2）、
下拉菜单的 divider（隔开动作与危险操作）、正文的 `hr`（那是内容）。
详情页脚「来源 / 被引用」与设置面板标题条的线已删——前者 40px 留白足够，
后者 `tintList` 底色已经分了层。

**知识库分组 = 目录树本体（D-068）。** 「全部文档」导航项已移除——进库
就是默认视图，侧边栏里要出现的是**结构**而不是重复入口（D-066 的「视图 +
降级小标题」形态随之退役）。分组标题行**整行悬停**显形一个 ＋（新建目录；
空库时**常驻**——hover 显形的前提是「已经有东西可指」）；树行 hover 显形 ⋯
（新建子目录 / 重命名 / 删除），拖拽 = 重挂父级（兄弟按名称稳定排序，
拖成兄弟不是实现的语义，`allowDrop` 只放行「拖进」）。行级操作都是
**hover 显形 + focus-visible 显形**：鼠标用户不看到一堆常驻图标，
键盘用户 tab 到时它们必须出现。删除目录只删结构——文档保留、指派清空
（回到库根），文档自己的删除有独立的确认流，藏在删目录里等于绕过防线。

**展开三角与目录图标共用一个图标位（Notion 式）。** rc-tree 的行本来是
「三角一格 + 图标一格」，深一点的三级目录前面有 72px 不是内容。现在
switcher 恒为 0 宽，三角**绝对定位盖在目录图标自己的槽位上**——图标中心
实测在 switcher 左缘 +22px（switcher 盒宽 0 + antd 给它的 margin-inline-end
4 + wrapper 的 padding-inline-start 6 + iconEle 半宽 12，父子两级同值，
缩进整体平移）；行悬停时图标 visibility 让位（盒子留着 24px，标题一个
像素不挪）、三角在原位显形。第一版让 switcher 悬停时长到 24px、三角落在
它自己槽位的中心（12px），比图标中心左偏 10px——用户看到的就是「下拉
图标换了个位置」。两个配套缺一不可：三角 z-index 抬过 content-wrapper
（它是 relative 且 DOM 在 switcher 之后，同为 auto 时盖住三角，
elementFromPoint 实测命中 wrapper、点击落空）；闲时三角 pointer-events
none——这个位置平时点图标 = 进目录，悬停后才轮到展开/收起。有子级的行
才有三角可换；叶子行（暂无子目录）图标常驻。圈定「可换」的行要看
switcher 的 `-noop` 类与行上的 `-treenode-leaf` 类，**不能看
`-treenode-switcher-open/close`**——这版 @rc-component/tree 给叶子行也挂
`-switcher-close`，按它选会把叶子行的图标藏掉却没三角补位。展开收起仍归
rc-tree（点三角 / 键盘方向键），样式只动外观。

**目录树的底色必须透明，而这条静默失效了两个迭代。** antd 默认给
`.ant-tree` 铺 colorBgContainer；treeWrap 类就挂在树根自己身上，写成
`.treeWrap .ant-tree` 的后代式**永远匹配不到根**——目录一直顶着 #141618
的底色坐在 #0f1113 的侧栏上，D-070 删掉右缘线没了遮挡才被人眼看出。修法
是 `&.ant-tree` 同元素选择器。同一个坑还埋着一条：选中态规则
`.ant-tree-node-selected .ant-tree-node-content-wrapper` 也是后代式，而
`-node-selected` 类就在 wrapper 自己身上——那条从没生效过，选中样式一直
是 antd 默认在渲染；死规则已删。样式模板注释里**不能出现反引号**——
css 模板字面量会被它直接终止（仓库的 check-style-backticks 脚本守的就是
这个，实测当场拦下）。

**「全部文档」的入口退役，知识库分组标题退回纯标签**（D-079，用户拍板）。
D-069 曾把整行标题做成回库根的入口——那条路依赖「库根 = 一个混装全部文档
的页」；「全部文档」页随 D-079 退役（进 `/docs` 直接落到第一个知识库），
这个入口没有了目的地，整行可点随之删掉。**知识库列表改平铺**：侧边栏只列
**顶层**（= 知识库），子目录是库内部结构，在知识库页里以文件夹卡片与
「文档 / …」面包屑呈现。随之退场的还有：rc-tree 的目录树（连同下面那套
展开三角 / switcher 几何全部删除）、拖拽重挂父级（`dropTargetPath` 与它
的用例，平铺后父级只有库根一个、没有可拖的东西）、行内菜单的「新建子目录」
（建目录的入口改在知识库页工具条的「新建文件夹」）。行上 ⋯ 保留
**重命名 / 删除**两项（删除语义不变：文档保留、指派清空）。

**平铺行不再有 rc-tree 的行盒陷阱。** 旧树行那套 `display: flex` 修正
（`.ant-tree-node-content-wrapper` / `.ant-tree-title`）随树删除——平铺行
就是一次普通 flex 布局（28px 高、6px 圆角、pill 内距仍归容器统一），
名字 `flex: 1` 省略号、计数与 ⋯ 在行尾。选中态显式写在行上
（`aria-current` → `colorPrimaryBg`）：平铺行不再是 rc-tree 节点，antd 的
`-node-selected` 不会来，不写就没有选中反馈。每行的结构是「行容器 div +
标题 button + ⋯ 按钮」，**不是** button 嵌 button（无效 HTML，读屏会把
两个控件念成一个）。

**侧栏 pill 的左右内距统一在滚动容器（`NavSidebar` 的 body）上给**：
`padding-inline: 6px`——菜单项、树行 pill、分组标题行的悬停 / 选中底色
左右缘因此都落在同一条线上。各子元素自己的横向间隔随之让位：菜单项的
`margin-inline` 归零（antd 还把项收缩成了 fit-content，实测 used width
只有内容宽——`width: 100% !important` 占满整行）、树行 switcher 的
`margin-inline-end`（antd 的 4px）归零（caret 锚点从 22 同步改 18）、
标题行左内距 14 → 8（+容器 6 = 文字位置不变）；「对话」的组标题内距
antd 默认 14 → 8（要 `!important`——与 antd 的规则特异性相同、注入顺序
不定，普通声明实测没盖过去），两个分组标题的文字落在同一条 14px 左缘上。
折叠态豁免（`bodyCollapsed` 的 `padding-inline: 0`）：48px rail 的图标靠
margin-inline 4px 居中，容器再吃 6px 会把图标挤偏 3px。不要用逐元素的
transparent 边框 + `background-clip: padding-box` 做这件事——圆角会被
边框宽度吃掉，右角变直角（实测）。

**树行必须是一次 flex 布局。** 这两处 `display` 是形态的一部分，不是可选的
排版细节。rc-tree 的行结构是 `.ant-tree-node-content-wrapper`（默认 block）
里放「图标 + `.ant-tree-title`（默认**行内**）」，而标题内容（名称 + 计数 + ⋯）
是个块级 flex 盒子——块级盒子放不进行内格式化上下文里图标所在的 line box，
整块被折到下一行。实测每行的标题 top 都比本行高**恰好 28px**（技术
345.2 → 373.2、后端 377.2 → 405.2，七行无一例外），名字画在下一行的行带上、
图标压在上一行的名字上。后果不是「难看」而是**点错**：`elementFromPoint`
取名字字形中心命中的是后一行，真指针点「技术」进的是 `folder:技术/后端`，
点「前端」进 `folder:生活`——而树是进任何目录的唯一入口。

所以 wrapper 给 `display: flex; align-items: center`，标题给
`display: flex; flex: 1; min-width: 0`：图标与名字回到同一行，名称靠左、
计数紧随、⋯ 由 `margin-inline-start: auto` 贴到行尾（实测名字左边缘 58（二级）、
⋯ 右边缘 193，与底部齿轮、标题行的 ＋ 同为一条竖线）。

**知识库有名称、描述与图标**（D-078，用户拍板）。点标题行的 ＋ 打开
**「创建知识库」**表单：名称（必填）、描述（可选，2000 字上限带计数）、
图标（13 格：人文 / 历史 / 社科 / 法律 / 科学 / 理科 / 技术 / 计算机 /
工程 / 教育 / 商业 / 艺术 / 语言，可不选）。图标**键**落库
（`folders.icon`，与 `FOLDER_ICONS` 同源），组件的映射在界面层
（`nav/folder-icons.ts`）——服务端不认识图标库，将来换图标库不用动数据库。
树行按它选图标渲染；未选 / 未知键回退文件夹图标。图标网格再点已选格子
= 取消选择（`aria-pressed` 如实反映）。名称 / 描述 / 图标都**只挂在被创建的
那一级**——`mkdir -p` 补出来的祖先行是路径的副产品，不继承子级的元信息。

**图标库统一为 lucide（react 组件 + 数据两种形态）**（D-078）。界面用
`lucide-react`；要给 morphicons 做形变的图标用 vanilla `lucide` 包的
**IconNode 数据**（`[["path",{d}]]`）——morphicons 吃数据不吃组件。
原有 17 个文件的 `@ant-design/icons` 全部迁移完毕（残留 0）。尺寸用
显式 `size` 而不是字号继承：antd 图标随 `font-size` 缩放、lucide 默认
24px，迁移时按上下文给 14 / 16 两档（小字形上下文 14，常规按钮槽 16）。

**展开三角用 morphicons 做路径形变**（D-078）。收起是右箭头、展开是下
箭头，状态切换时两个路径**形变**过去（spring 物理、中途可打断），不是
淡入淡出；`reducedMotion="user"` 尊重系统「减少动态效果」设置、开启时
退化瞬时切换。antd 默认对收起态再转 -90°，两套机制叠加会得到朝上的
箭头——`transform: none !important` 关掉它，朝向只归动效库一处。渲染函数
放在**模块级**（`renderSwitcherIcon`）：写成内联箭头会被
`react(no-unstable-nested-components)` 判成「渲染期定义组件」，React
Compiler 随即跳过整个 `FolderSection`（铁律 1 的静默退化，实测被 lint 拦下）。
同一坑还有一处：`const Icon = folderIconOf(x); <Icon/>` 的写法同样触发
该规则——`FolderGlyph` 直接调用返回的组件函数，不赋值给局部变量。

### 8.2 知识库页：文件夹卡片 + 文件卡片（D-079，形态由用户给定）

**「全部文档」页退役。** 内容都住在知识库里，`scope=all` 不再渲染列表：
进 `/docs` 时库视图把它**重定向到第一个知识库**（`replace`，不留历史），
一个知识库都没有时给创建引导（「先创建一个知识库」+ 创建按钮，复用
`KnowledgeBaseCreateModal`）。标签视图（`scope=tag:x`）保留——它是横切
筛选，不是容器；它没有可落的目录，所以不带工具条的知识库动作。

**头部是知识库自己的身份，进子文件夹也不变**（用户拍板）：

```
测试知识库                                  ← 28px / 600（FONT_SIZE.display）
暂无描述                                    ← 描述为空时的占位（quaternary 色）
知识库 ID: 7ZZRF7 ⧉   创建者: kebai          ← 元信息行，ID 用等宽字体
─────────────────────────────────────────   ← 静态分割线（用户明确要求）
4 个文档        [卡片|列表] [新建文件夹] [新建文件] [添加文档 ▾]
文档 / 测试文件夹          支持文本（md / txt / rst…）…可直接拖到本页上传。
┌──────────┐ ┌──────────┐ ┌──────────┐
│ 文件夹卡片 │ │ 文件卡片  │ │ 文件卡片  │
└──────────┘ └──────────┘ └──────────┘
```

**面包屑在「文档」那一行**，不在头部：头部回答「我在哪个知识库」，位置感
由这一行表达——「文档」是知识库根（可点回去），中间每一段可点，末段是
当前所在。

**可点的段静息是正常文本色，不是链接蓝**（用户拍板）。这一行是**路径
标签**：「文档 / 资料库」读起来是一句话，末段本来就是正文色，前几段单独
染蓝会让同一行出现两种文字身份，也与右侧的格式提示抢强调级别（§3.5 的
链接色留给正文里的链接与真正需要强调的动作）。可点性靠 hover 给：文字
转 `colorLink` + 下划线——悬停是用户准备点它的那一刻，那时才需要 affordance。

D-070 的静态线原则在此有一处**用户明确要求的例外**：身份区与工具条之间的
那条分割线是静态的（它划分的是两个不同角色的区段，不是内容行边界）；
而「固定头部 vs 滚动列表」的界线仍按 D-070 滚动才显形，挂在「文档」
那一行上。

**知识库 ID 整块是一个按钮**（用户拍板）：`知识库 ID: 7ZZRF7 ⧉` 三件
一起构成热区——hover 整块亮度提一档（文字与短码各再提一档，让「整块都在
响应」看得见）、悬停出 tooltip「点击复制知识库 ID」、点块内任何位置都
复制。复制成功走 message「已复制知识库 ID」；`navigator.clipboard` 失败时
如实报错，不假装成功。

**垂直居中完全交给 flex，不做像素补偿**（用户明确要求）：

```
button   height: 24px + align-items: center   ← 把内层摆到中线
  └ inner  inline-flex + align-items: center  ← 文字与图标摆到同一条中线
```

两个反面写法都试过、都被替换：① `height: auto` + 上下 `padding: 2px`
——那是**用内距凑高度**而不是居中，改字号 / 字体 / 行高时会重新跑偏
（实测盒子 23.6px，且文字墨迹比盒中心高 0.6px）；② `top: 0.5px` 之类的
偏移——把「字体度量造成的亚像素差」硬挪回来，脆弱且不可解释。定高 24px
（与同一行的控件同高）之后，中线由 flex 几何决定，与内容无关；实测容器
中心、内层中心、图标中心、文字墨迹中心四点重合于同一条 y。

内层 `line-height: 1` 是为了压掉中文用不到的**下伸空白**（antd 默认 1.5
会在行盒下方留出西文下伸部的空间，中文字形用不到，行盒看起来「下重上轻」）
——这是让行盒等于字形高，居中仍由 flex 管。残余的亚像素差（≤0.4px）来自
字体本身：中文墨迹 ascent 11 / descent 2，而字体盒 ascent 11 / descent 3。
这是度量事实，不修正。

`margin-inline-start: -6px` 抵消按钮的左内距，文字左缘与下方「N 个文档」
落在同一条竖线上——这条是**水平对齐**，与垂直居中无关。

**卡片是文件展台，扫读的是属性而不是摘要**：

```
┌──────────────────────────────────┐
│ 图标 名称                [PDF]  ⋯ │  ← 13.5px / 600；格式徽标；悬停显形动作
│ 1.4 KB                           │  ← 属性行（大小 / 摘要）
│ [就绪]            2026/09/29 12:54│  ← 状态徽标 + 绝对时间
└──────────────────────────────────┘
```

与旧卡片（D-067）的差别：摘要从三行压到一行、标题行加类型图标与格式徽标、
底部给**绝对时间**（文件习惯）与状态徽标。**属性行不重复徽标的信息**——
格式已在徽标上，属性行给的是它回答不了的那一半（原件多大 / 这一篇里有什么）。
目标稿的属性行还有「N 个分块」：分块要等 M1 的切分做完，现在只如实给
大小与摘要，不放假数字。文件夹卡片与文件卡片同形同网格，点进去是更窄的
scope；网格仍 `auto-fill + minmax(300px, 1fr)`。

**卡片的交互角色不能嵌套。** 卡片里有动作按钮（打开 / 下载 / 编辑 /
替换 / 删除），所以卡片本体**不是** `role="button"`——那是交互角色嵌套，
外层会把内层按钮的文本吸进自己的可及名称（实测外层与内层同时命中
「删除 未命名笔记」，`getByRole` 直接报 strict 冲突）。改成：卡片是普通
盒子（鼠标点任意位置可打开），**标题本身是按钮**（键盘的打开入口，自己的
焦点环），动作按钮是它的兄弟。这与文件管理器（Finder / Google Drive）
的卡片同构。悬停显形的动作条用 opacity 占位（不改变布局），点动作一律
`stopPropagation`。列表布局的行条同此：文件夹行有 ⋯，文档行是纯入口。

**悬停显形的选择器必须用字面类名**（`.kb-card` / `.kb-row`）。antd-style
把样式块编译成哈希类名（`acss-xxxx`），同一文件里的 `.card:hover &`
**永远匹配不到**——宿主元素上没有叫 `card` 的类，规则静默失效：动作条一直
opacity 0，但元素仍在文档流里、仍可点（自动化点得中、人眼看不见），
实测两次都骗过了浏览器测试，是对着截图才发现的。宿主因此额外挂一个字面类
（`className={\`kb-card ${styles.card}\`}`），`FolderSection` 的行是同一做法的先例。

**列表布局是一张表**（用户点名「表格缺少表头」）：表头一行
（名称 / 详情 / 状态 / 更新时间），行与表头**共用同一套网格列宽**
（`grid-template-columns: 22px minmax(0,1fr) minmax(0,300px) 76px 116px`）——
列宽只有一处定义，所以表头与每一行、行与行之间必然对齐（实测四列左缘
逐像素一致：240/272.8/712/1022/1108.8）。不用 flex 的理由就在这里：
内容长度不同的行在 flex 下各自算出不同列宽，表头对不上任何一行。
表头下有一条实线（`colorBorderSecondary`）——这是 D-070「静态线清零」的
又一处理由充分的例外：**这是一张表**，列标签与数据之间没有界线时，
标签看起来像第一行数据。表头 `aria-hidden`：每行的可及名称已是完整的一句话，
列标签对读屏是重复信息，它服务的是「用眼睛扫列」。

**「添加文档」是下拉菜单，四个动作**（用户给的按钮交互）：

```
[＋ 添加文档 ▾]
   ⬆ 上传文件
   ⬆ 上传文件夹
   🌐 网页抓取
   ✎ 直接编辑
```

四条路都**带当前目录**——从知识库页收进来的内容落在这个知识库里：
`openCapture({ tab, folder })`（应用壳的 `CaptureOptions`，对话框按次换
key 以重置初始页签）、上传走 multipart 的 `folder` 字段、抓取走
`captureInputSchema.folder`、直接编辑走 `noteCreateSchema.folder`。
对话框标题与页脚如实写出落点（「收进「技术」」）。空态也给同样两个动作
（上传文件 / 直接编辑）——只有一句话没有动作的空态，跟报错没区别（§7.4）。

**「上传文件夹」按相对路径展开成目录树。** 浏览器给每个文件
`webkitRelativePath`（`论文集/2024/a.pdf`），**首段是所选文件夹自己的
名字**——保留它，用户选的是「论文集」，收进来就叫「论文集」，子目录结构
原样重现（`targetFolderFor`，服务端 `ensureFolders` 补注册表行）。

**整页可拖放上传**（目标稿写着「可直接拖到本页上传」）。拖放区是**整页**
而不是一个虚线盒子：dragenter/leave 用计数器避免子元素抖动，覆盖层
`pointer-events: none`（它出现时指针正拖着文件，任何拦截都会让 drop 落空），
只在知识库视图生效（标签视图没有可落的目录，`canDrop = folderPath !== null`）。

**状态徽标在卡片上恢复两态**（D-079）。D-054 起「只有偏离常态才有徽标」，
`ready` 不显示——那是列表与详情面板的判据，仍保留（那里逐个盖「就绪」
是噪音）。知识库卡片的底部是「这份文档现在能不能用」的陈列位，两态并列
才能扫读，所以 `StatusBadge` 加 `showReady` 开关，只有卡片传它。

**列表布局的行条必须能收缩属性位。** 笔记的摘要是任意长的正文，而属性位
是 `nowrap`——不给它 `min-width: 0` + 省略号 + 最大宽度，一行就被撑到
比容器宽，整页冒出横向滚动条（实测：切到列表布局后页面下方出现横向条）。

**「全部文档」的窗口标题 / scope 文案**随之退役：`SCOPE_LABEL.all` 只在
认不出的 scope 上兜底，`scopeTitle` 不再为 `all` 产出标题（库视图不用它）。

**在目录里搜索时，标题要写出真实范围**。检索契约只有 kind 与 tag，没有
目录（`searchQuerySchema`）——`scope=folder:X` 下搜索，结果其实来自全库，
而侧栏那条目录仍高亮。标题因此写「搜索结果 · 全部文档」；标签视图的搜索
会把 `tag` 真的传下去，标题照旧只说「搜索结果」。**否决**给检索加 folder
过滤：那要改 `packages/shared` 的契约与关键字 / 子串两条 leg，本次不做；
让范围可见比让它悄悄不对要诚实（§0.2）。

**格式提示与「文档」标题同一行**（目标稿）：右侧如实列出可提取正文的
格式（Markdown、文本与代码、CSV / Excel、PDF、Word、PPT）与 50MB 上限，
并说明可直接拖到本页上传。上限的数字取自 `FILE_MAX_BYTES`，不写死。

### 8.3 文档头部（单行）

**头部是一行，不是三行**（D-054）。返回 · 文件名 · 元信息 · 动作挤在 44px 里
——这是 Word / Excel 网页版的标题栏形态：

```
┌──────────────────────────────────────────────────────────────────┐
│ (← 返回库)  文件名.docx   本机导入 · 路径 · Word · 3.2 KB · 9/26  [下载][问 AI][⋯] │
└──────────────────────────────────────────────────────────────────┘
   26px 胶囊   16px/600        12.5px 灰 + 中点分隔              文字按钮
```

- 头部高 44px、内边距 `0 12px`、下边框 1px
- **文件名 16px / 600**。它曾经是 28px 的「文档大标题」——在 44px 的头部里
  挤且丑（用户的原话）。现在它是标题栏里的文件名，不是文章标题
- 元信息项之间用**中点**分隔：五项灰字挨在一起读不出分组，
  看起来像一长串没说完的话。点用 `::before` 画，不占 DOM
- **位置是全行唯一可省略的一项**（笔记的 vault 路径 / 上传件的原文件名 /
  资料的 URL）——只有它可能很长，`flex: 0 1 auto` + 省略号
- 标签与目录**不在这里**：它们在「⋯」菜单里，而那里还能增删。
  同一份信息两条路径迟早不一致，而且标签多起来会把这一行挤爆

原先那三行（28px 大标题 / 元信息行 / 独占一行的返回胶囊）合计约 150px。
文件类文档下面就是纸张、表格、幻灯片——那些是越高越好的东西。

**上传件的这一行多两项**：

```
[文件] 本机导入  PDF · 2.4 MB  📁 目录  #标签 …          2026/9/24
```

- **格式与大小**用 `colorTextTertiary`（中性文字，不是徽标——§3.7）
- **来源标注是「本机导入」**，不是「AI 整理」：后者在说一件没发生的事
- 笔记仍是「手动编辑」，抓取的资料仍是「AI 整理」

**文档标题（`h1`）的字号必须抬特异性。** 它是 antd 的 `Typography.Title`，
自带一条 `h1:where(...).ant-typography { font-size: var(--ant-font-size-heading-1) }`
——`h1` 元素贡献 (0,0,1)、`.ant-typography` 贡献 (0,1,0)，合计 **(0,1,1)**，
而单类选择器只有 (0,1,0)，盖不住。实测标题因此渲染成 **38px**（antd 的 h1 档），
而规范写的是 `display` 档 28px，且不报错、看起来只是「标题偏大」。
写法是 `&.${prefixCls}-typography { … }`，叠成 (0,2,0) 才胜出。

### 8.4 工具条的「⋯」菜单

**整理条已删除（D-054）。** 它曾经是文档顶部一整条橙色横幅
（建议标签 + 归入目录 + 完成整理 + 归档）——占一整行、长期存在，而那些
都是低频动作：读一篇文章时不想被一整行横幅挤压正文。

能力收进了头部右端的「⋯」菜单（归档随后也整体退役，D-065，不在其列）：

| 组 | 内容 |
|---|---|
| 标签 | 建议（后端按正文高频词算的）＋ 已有（点一下移除）＋ 清除全部 |
| 归入目录 | 目录树里的路径 ＋ 移出目录 |

三条实现上的规矩（`document/doc-menu.tsx` 里都有注释）：

1. **不留空子菜单**：没有可选项时给一条禁用的说明项
   （「还没有其它目录」），而不是给空数组——展开后什么都没有会让人以为坏了
2. **当前值禁用**：已经在这个目录里时那一项不可点。可点而无事发生是最坏的
   一种（§7.4）
3. **危险动作不进这个菜单**：删除不可撤销，而它在头部离「问 AI」只有一步。
   它留在库视图的列表项上

随整理条一起退役的还有 `tintWarningSurface` / `borderWarningSurface`
两个自定义 token（只有它在用）。

### 8.4.1 编辑器外壳（六种格式共用）

六种编辑器（docx / xlsx / pptx / html / markdown / pdf）用**同一套外壳**
（`packages/office/src/shell/`），自上而下五个槽位：

```
┌────────────────────────────────────────────┐
│ 工具条（格式操作在左，状态与保存在右）      │  ← 44px 内
├────────────────────────────────────────────┤     ↑ 这两行同包在
│ 次工具条（查找替换栏、幻灯片导航、公式栏）  │     ↑ .mimir-editor__chrome
├────────────────────────────────────────────┤        里，整体 sticky top
│ 编辑区（纸张 / 网格 / 幻灯片 / 正文）       │  ← flex: 1
├────────────────────────────────────────────┤
│ 附属面板（xlsx 的单元格编辑、pptx 的段落）  │  ← 有选中才出现
├────────────────────────────────────────────┤
│ 状态行（左：状态与说明；右：页码 / 字数）    │  ← sticky bottom
└────────────────────────────────────────────┘
```

**工具条、次工具条与状态行常驻**（sticky）：长文档里「改到一半想改格式」不该
要滚回去。Word 也是这样。

次工具条**不能自己再写一条 `position: sticky; top: 0`**：工具条已经占了 `top: 0`
且 DOM 在后，次工具条会盖住工具条右端的「保存」。写死一个 `top: 32px` 之类也不
行——工具条是 `flex-wrap` 的，窄窗口下会折成两行，写死的偏移立刻错位。所以两
行包进同一个 sticky 容器（`.mimir-editor__chrome`），高度由内容决定。

**编辑器铺满容器，四边不留 padding。** 它自己带边框与圆角，外面再垫一层就是
「框套框」，而垫掉的每一像素都是内容能用的高度。正文的**行宽上限 760px**
由外壳内部负责（`.mimir-markdown-body` 居中限宽），不是靠外层容器收窄——
后者会把工具条一起收窄，两条铬条的宽度对不上。

**保存状态落在状态行上**（`已修改，未保存` / `保存中…` / `已保存` /
`保存失败 · 点此重试`），与 Office 一致。原先三种格式各用一套说法：
docx 弹 `message.success`、xlsx 顶栏一个 Tag、pptx 另一个 Tag。

**六种格式共用这一套外壳**（D-056 / D-057 之后）：docx 的纸张、xlsx 的网格、
pptx 的幻灯片、html 的源码 + 预览双栏、markdown 的正文、pdf 的页面画布——
它们都在这五个槽位里，所以「长得一样」不靠约定。两处格式特有的布局：

| 格式 | 内容区怎么排 | 为什么 |
|---|---|---|
| html | 左右各半（窄屏 <1100px 上下叠放），中间一条分隔线；**三档可切**（源码 / 分栏 / 预览） | 源码与渲染结果长度通常不同，让容器统一滚动会让其中一边的工具条滑出视野 |
| pdf | 页面居中、工作台底色 | 与 pptx 的舞台同一个判断：纸是白的，工作台要能区分出来 |

两处都用**固定白底**（html 预览与 pdf 页面）：网页与 PDF 页面默认就是白的，
跟着深色主题走会让「这个东西长什么样」失真——而 PDF 常常是要打印的。

**三条「纸」共用同一套判断，但档位不同**（D-076）：docx 的纸张用
`--me-page-shadow`（`boxShadowTertiary`，§5.3 的「卡片微浮起」——分页视图里
一页接一页，它是内容）；pdf 的页面与 pptx 的幻灯片用 `--me-shadow`
（`boxShadowSecondary`）——它们更大、更像一块独立的画布。三者的工作台底色
都是 `--me-stage-bg`。

**工具条上的组名要能被看见，不只是被念出来**（D-076）。`ToolbarGroup` 只渲染
`role="group"` + `aria-label`，所以两个外观相同的下拉（docx 的「中文字体」与
「西文字体」都是「（默认）」时）只有读屏与 hover 的 `title` 分得出谁是谁——
§0.2 要的是「看得见的状态分得出是谁的状态」，所以组名前补一档 `.me-label`
级的可见前缀，成本是两个字。

**「不是档位里的值」有两句不同的话**（D-076）：`value === null` 是「这里没有
直接取值、继承自别处」（显示「（默认）」），值不在选项里是「有一个具体的值、
只是不在预设档位里」（显示「22（其它）」）。`ToolbarSelect` 的两个参数
（`emptyLabel` / `fallbackLabel`）对应这两句。

**组与组之间要有分隔线**（`ToolbarDivider`），因为 `.mimir-editor__bar` 与
`.me-group` 的 `gap` 都是 2px——不画线时组间隔与组内按钮间隔完全一样，一条
八到十组的工具条会读成一个没有结构的图标带（六种格式都画，笔记原先漏了）。

**html 的三种视图用 `hidden` 切，不是条件渲染**：源码编辑器一卸载，CodeMirror
的实例与编辑历史一起没了，而重新挂载读的是**刚打开文件时**的文本——「切到预览
再切回来」会看到旧内容，接着敲键就把中间改的覆盖掉（D-059）。

**预览有三档设备宽度（桌面 / 平板 768px / 手机 390px）与 50–200% 缩放**：网页是
流式布局，「它在手机上长什么样」只能靠改视口宽度看。缩放是**真放大**（同一份布局
放大着看），不是把视口缩窄再拉宽；缩放的布局陷阱见
`packages/office/src/editors/AGENTS.md`。

**元素路径（面包屑）落在次工具条上**，不在内容区：它是**当前选中**的反映，与
「这份内容怎么了」同一类信息。点一段就把预览与源码一起挪到那个元素（预览那边走
`postMessage`——父页读不到 frame 的 DOM）。它**有选中才出现**，不占一条常驻空行；
没有选中时状态行已经在说「点一个元素可以定位到它的源码」。

**§8.5–§8.8.1 讲的对话块住在独立包 `@mimir/chat` 里**（D-099，
`packages/chat/src/`）。下面各节只说**长什么样**，这里先交代**它怎么长出来的**：

- **状态层在包里**（`@assistant-ui/react` + `@assistant-ui/react-ag-ui`），
  宿主只提供数据与动作：数据是 `composerStatus`（文档列表 / 模型角色 / 用量，
  宿主 `useQuery` 取好），动作是 `ChatIo`（建会话 / 读历史 / 存笔记 / 跳转，
  宿主实现在 `packages/renderer/src/lib/chat-io.ts`）。包 import 不到宿主的
  api / router / queryClient
- **trace / 引用 / 失败是消息里的 data part**（`mimir.trace` /

### 8.6 检索过程

**assistant-ui 官方 registry 的 Reasoning 形态**（D-099 收尾；参照
`packages/ui/.../elements/reasoning.tsx`，shadcn 分发的那一份）——
**一个带边框的圆角盒**，不是时间轴：

```
┌──────────────────────────────────────────────┐
│ 🧠 思考 1 轮 · 调用 2 次工具 (1.4s) ⌄         │
│     先把问题拿去知识库里找相关内容              │
│     用 jieba 切分查询词  这份 文档 讲 了 什么 ？ │
│     通道召回结果  词级召回 7 段 · 子串兜底 2 段  │
│     读取命中的文档并合并相邻分块  来自 1 个文档…  │
│     确认没有遗漏，生成回答                      │
└──────────────────────────────────────────────┘
```

- **盒**：`rounded-lg border px-3 py-2`（官方 ReasoningRoot 的
  variant=outline 是默认形态），`colorBorderSecondary` +
  `borderRadiusLG`
- **触发行**：Brain 图标（16px）+ 标签 + ChevronDown；`text-sm`、
  `colorTextSecondary` → hover 提到正文色；chevron 关闭时 -90°
  （朝右）、打开转正（官方 `ease-[cubic-bezier(0.32,0.72,0,1)]` 换算成
  0.2s ease-out）
- **标签 live 时 shimmer**（官方 `.shimmer` 工具类的换算：
  background-clip:text 渐变扫光）并带计秒
- **内容**：`ps-6 pt-2 pb-2` 的 muted **正文**（非等宽、无行首标记、
  无图标），max-h-64 内滚动；分词结果与每步数字是裸文本，比步骤文字
  再浅一档（`colorTextQuaternary`）——官方 ReasoningText 是纯
  muted prose，没有 Tag 盒子
- 展开跟随与手动开合的优先级、每轮自动归零的秒数，行为同 D-098

**位置在最后一条用户消息之后、它的回答之前**（question → 过程 → 回答，
也是 PRD 这句「回答上方」的字面落位）。现在它就长在**那条助手消息自己的
根里**（`parts/MessageItem.tsx` 的显式顺序：过程 → 正文 → 引用 → 失败/中断
→ 停止 → 动作条）——历史多轮会话里它因此贴着自己那一轮，而不是飘在整个
会话顶上。

组件是包内 `parts/TraceActivity.tsx`，数据只从 `mimir.trace` data part 读
（`parts/data-parts.ts` 的 `useTracePart`，**只认最后一个**——一轮发两份，
后一份带整轮耗时，覆盖前一份）。「还在跑」的判据是消息状态
`running`（或整条 thread 在跑且它是最后一条），不再有旁路的 `stopped` /
`creating` 布尔。

**摘要必须带三个真数字**：`思考 N 轮 · 调用 M 次工具 (耗时 Xs)`——
官方 Reasoning 的标签格式是 `Reasoning (12s)`，mimir 的三个数字按同款
括号包秒落位。它们来自服务端真实执行的结果，不是渲染时编的。

**这条样式翻过两次，都如实记**：最早的 Steps 时间轴 → D-097 改平成
muted 行 → D-099 抽包时一度按文档站自绘版做成 mono 行（引擎换了、参考
对象选错了）→ 用户点名「一定要参考官方实现」后，按官方 registry 的
Reasoning 重写为描边盒形态。**参考对象必须是官方 registry 分发的组件，
不是文档站自己魔改的那套**——两者的差别就是这一课。

**不引入引擎的 ● 脉冲点**：那会成为第二个进度表面（D-098 明令只有一个）。
活态靠 marker 变蓝、文字微光与走着的秒数。

#### 自动跟随：贴底才跟随

| 时机 | 行为 |
|---|---|
| 自己发出的新消息、打开已有会话（挂载）、切换会话 | 无条件跳到底（引擎的三个 `scrollToBottomOn*` 钩子，默认全开） |
| 流式内容变高 | 只在「跟随意图」还开着时跟随 |
| 离底 | **居中**出现「回到底部」圆钮——官方 `ThreadScrollToBottom` 的位形（`-top-12 self-center`：悬在 composer 上方），40px 圆形 outline（`colorBorderSecondary` 描边 + 容器底），不是右下角加阴影 |

**跟随由引擎的滚动原语承担**（`ThreadPrimitive.Viewport` /
`ScrollToBottom`）：意图是一份状态——在 scroll 回调里判「用户往上滚」
（`scrollTop` 减小而内容高度未变）才关掉；内容增长由 `ResizeObserver` +
`MutationObserver` 双盯驱动——只监听 scroll 的话「用户停在中间、回答继续长」
这一段不会有任何回调；而跟随写 `scrollTop` **会再触发 scroll**，引擎在回调里
只在「贴底与否」真的变了才更新 store。贴底判据是它的 `isViewportAtBottom`
（`|scrollHeight - scrollTop - clientHeight| <= 1`，读 0.15.23 的源码确认）。

这一节在搬迁前是手写的 `use-stick-to-bottom` + 32px 闸门。那 32px 曾经要挡的
是「滚动位置是小数」与「一次滚轮约 100px」这两件事，而它背后真正的结论是：
**「是否跟随」必须是状态，不能每次现算距离**——一个 token 在同一行内只改宽度
不改高度、观察器不触发；触发的那一刻是换行，而换行一次长高**一整行**（消息区
实测 40px），已经越过任何小阈值。所以「增长后重算距底、小于阈值才跟随」会在
第一次换行时把跟随关掉，此后每个 token 都不再改高度、也就再没有回调恢复它
（实测症状：点「自己发新消息」后 320ms 就不再贴底）。引擎把这条结论做进了
原语（跟随意图单独存，距离只用来决定「回到底部」按钮的显隐），手写版与 32px
一并退役。

**「回到底部」浮在滚动区之上**，不能放进滚动容器里——那样它会跟着内容滚走。
显隐由引擎的 `ScrollToBottom` 在贴底时置 `disabled` 承担，样式把它
`visibility: hidden`（**不是**条件渲染：浮层从布局里消失会让位置跳一下）。

#### 生成期：检索过程行活着（D-098）

等待期**没有独立的状态行**——检索过程行本尊就是进度表面（Codex 的
「Worked for…」节奏，一个表面贯穿整轮）：

- **发送后立刻出现**。检索结果还没到时是一行「正在检索知识库 · Ns」
  （不是 Collapse——没有可展开的内容就不长成可展开的样子）
- **检索一到就地展开**：折叠标题换成「思考 N 轮 · 调用 M 次工具 · Ns」，
  秒数持续在走（叶子组件 `LiveSeconds` 计时，不在渲染期读时钟）；
  时间轴里 `process` 状态的图标带 1.6s 的呼吸（有这一口气，
  「还在跑」与「跑完了」扫一眼就能区分）
- **正文一出收起**，但行还挂着——折叠标题里的秒数**继续走**
  （模型仍在耗时）；流结束时服务端会再推一份带完整 `tookMs` 的
  trace，秒数换成那个真实的总数。客户端的钟只管「用户已经等了几秒」，
  服务端的钟只出现在折叠摘要里，两者不同屏并列
- **不显示的三种情况不变**：这一轮已经失败（屏幕上该有的是那张带出路的卡）、
  请求报错、用户按了停止。**「活着」的判据是忙**（消息状态 `running`，或整条
  thread 在跑且它是最后一条）——只看「最后一条是 user」的话，打开一个停在
  半截的历史会话会挂出一条永远在走的幽灵计时（StreamStatusLine 时代的真 bug，
  跟着重做修掉；`parts/MessageItem.tsx` 的两个判据取或）

字的规格与旧状态行相同：与消息同一个左边距，`note` 12.5px +
`colorTextSecondary`，数字走 `tabular-nums`。

#### 「已停止生成」那一行

`PauseCircleOutlined` + 「已停止生成 · 以上是已生成的部分」，同样是 `note` 12.5px
+ `colorTextTertiary`。**不用警示色**：停止是用户主动做的，不是错误
（§3.4 的语义色只给偏离常态的状态）。

### 8.8 输入区（composer）

**官方 composer shell 的换算**（D-099 收尾）：`rounded-(--composer-radius)`
= **16px**、`p-2` = **8px 内边距**、底是 **muted 30% 掺透明**
（`colorFillQuaternary`，比实色 muted 轻）、描边最浅一档
（`colorBorderSecondary`）。

聚焦时只把描边提一档（`colorBorder`；官方
`focus-within:border-foreground/25` 同款，不是主色柔光），过渡也只有
`border-color` 一条。原先还叠一圈 `token.controlOutline` 的柔光，D-099
重做时移除了：阴影与边框的过渡不同步，容器会看起来「抖」一下；这是 §7.2
「补 3px 柔光盘」的一处**明确例外**（见那一节末尾）。

**内层输入框不画自己的焦点环。** antd v6 给聚焦的输入类控件加了
focusOutline（实测计算样式 `outline: 1px` 主色），叠在盒子的聚焦边框上
就是用户看到的两层边框。盒子才是容器：输入框在 `:focus / :focus-within /
:hover` 下 outline 与 box-shadow 全部关掉（命令面板当年为同一条关过三处，
这里是第四处——同一个坑散在四处，集中记在 §8.6）。

**发送与停止是一个键位的两种形态，都由引擎原语渲染**：空闲渲染
`ComposerPrimitive.Send`、生成中整颗换成 `ComposerPrimitive.Cancel`
（`render` 把 antd 的观感套上去），可用性也归引擎的
`canSend` / `canCancel`。不要自己写 `<Button onClick={composer.send()}>`：
`canSend` 只管「有没有内容」，而**生成中能不能排队**是另一条规则
（引擎把 `capabilities.queue` 也算进去）——手写那版会在生成中禁掉按钮，
于是「生成中 Enter 排队」这条 D-098 的语义在鼠标路径上根本到不了，而键盘
那条却通着，两个入口行为不一致且不报错（`packages/chat/AGENTS.md` 记了
这条）。**也不要把两颗都常驻**（第一版那样，空闲时停止键是一块灰方块）：
官方 `thread.tsx` 用 `AuiIf` 条件渲染，条件渲染一次解决两件事——
视觉干净，且鼠标路径的键位语义与键盘一致（本包实测修过）。
钮的形态是官方 `size-7 rounded-full`：**28px 圆形、深底浅字**
（shadcn 的 `variant=default` 近黑底，换算成 `colorText` 反色），
图标 ArrowUp / Square(fill)，禁用只降透明度（`disabled:opacity-40`）——
不用 antd Button（它的 disabled 会换灰底盖掉深底形态），是套了
引擎原语的原生 button。

#### 生成中：发送键换「停止」，输入框可打字、Enter 排队（D-098）

| 状态 | 发送键 | 输入框 |
|---|---|---|
| 空闲 | 「发送」（primary，`SendOutlined`），无内容时 disabled | 可编辑 |
| 生成中 | 「停止」（默认样式，`StopOutlined`） | **可编辑**（D-098 前是 `readOnly`），placeholder「生成中 · Enter 排队这条，Esc 停止」 |

**生成中不让打字等于逼用户干等**（Codex 同款）：Enter 在生成中**排队**
——本轮正常结束后自动发出。排队的那条显示在输入框上方一行（「已排队」
+ 单行省略 + ×），× 把它**取回输入框**。

**排队不是百灵鸟**：本轮**停止 / 失败 / 流中断**时，排队的字**还给输入框**
而不发——用户停在半截通常是想改主意，替他把排队的话发出去是说谎般的体贴。
**引擎默认不这么做**（取消时它只 `notifyCancelled()` → 暂停队列），所以
「取首条 → 写回输入框 → 删掉那条」是包在 `onCancel` 里显式做的——漏了它的
症状是用户的字不见了（`packages/chat/src/runtime/use-mimir-runtime.ts`）。
「回填输入框」是一条普通的 `composer.setText`（旧实现里它靠 nonce 重挂载
组件，那个补丁退役）。

队列在引擎里其实是**多条**，而 D-098 定的是单条：界面只显示 `queue[0]`
（「已排队」+ 单行省略 + ×），排在后面的等前一条发出去后依次露头；逐条自动
发送的失败语义留待将来另定。

**为什么不再是 `readOnly`**：等回答的几十秒里正好想好追问；`readOnly`
时代用户只能拿备忘录。Esc 停止的快捷键保留。停止键用默认样式而不是红色：
**停止不是危险操作**，它是用户拿回主动权的那一下（§3.4）。

**Esc 的判据必须带 `isComposing`**：中文输入法里 Esc 是取消候选词，这时按下去
不该把正在生成的回答也停掉。rc-input 对 Enter 就是这个判据
（`@rc-component/input` 的 `TextArea.js`）。

**输入框单行起**（官方 `rows=1 min-h-10`，textarea 透明底
`px-2.5 py-1`），autoSize 长高到 8 行。**底栏的布局语法照官方动作行**：
左边是控件组——「+ 添加上下文」、范围 pill、上下文容量、思考强度、当前
模型——右边只有发送/停止一颗钮。

**+ 添加上下文的钮是官方 ComposerAddAttachment 形态**：28px 圆形幽灵钮
（muted 字 → hover 提亮 + 浅底、按下缩 0.96），tooltip 走 antd。

**+ 添加上下文 = 把本轮检索范围锁到某篇文档**。服务端的检索按
documentId 过滤（`retrieve(question, documentId)`），范围**逐轮生效**：
菜单列最近的文档（M0 无附件 / 技能，后续再扩），选中后底栏出现可移除的
范围 pill，占位符随之变成「就「…」提问…」。范围状态由面板持有，每轮通过
composer 的 `runConfig` 写进**那条消息**（引擎在发送时读 composer 的
runConfig 挂到消息上，队列里存的是完整 AppendMessage，所以排队的那条也带
自己那一轮的范围）；服务端从 `forwardedProps.runConfig` 读（D-099 的
Stage 0，顶层旧通道仍认、顶层优先）。移除 pill 回到整个知识库。

**底栏三个菜单的数据都由宿主取好传进来**（`composerStatus`：文档列表 /
模型角色 / 用量，宿主 `useQuery`——键名、缓存策略与失效时机是宿主的知识）。
三态（加载中 / 失败 / 空）如实传：「读取失败，点此重试」与「知识库还没有
文档」是两件事，混成一支会让用户以为自己的内容没了。

**上下文容量用真记账，不做字符估算**。`usageLog.refId` 记的就是会话 id，
chip 显示该会话最近一次请求的 promptTokens——那是**真的发给模型的完整
上下文**（系统提示 + 全部消息 + 检索命中），SDK 的 usage chunk 带回、
逐次落账。没有记账（新会话还没发过、或供应商没回传）就不渲染 chip——
显示一个 0，与「null 和 0 不能合并」是同一条。点开是明细（模型 / 输入 /
输出 / 合计）。对窗口总量的百分比要等模型配置补窗口大小，M0 不编。
（D-099 剥掉模型那一趟的 `RUN_FINISHED` 时，那份用量被接住转挂在服务端
自己那条 `RUN_FINISHED` 的 `metadata` 上——**目前没有消费者**，记的是
「剥事件不顺手丢数据」；chip 的账始终来自 `usageLog`。）

**思考强度下拉：标准 / 深入** = 用对话角色还是推理角色回答（原「深度
思考」开关的下拉化——开关退役）。M0 的思考强度就是这条角色轴；真正的
effort 透传（低 / 中 / 高）要等后端给流加参数，到那时下拉才扩档。

**当前模型是展示 + 管理入口，不是选择器**：触发器显示「这句话会发给谁」
（随强度联动：标准→对话角色绑定，深入→推理角色绑定；未绑定如实显示
「未配置模型」），菜单里列两个角色的绑定（当前项打勾、禁用——纯展示）
与「管理模型」（去设置页的 `models` 分区——**显式点名目的地**，靠默认值
会在分区顺序调整时悄悄落到别的 tab）。M0 不做会话级换模型：绑定是全局
配置，会话级覆盖要后端加 per-request 参数。

**旧开关的标签教训仍然有效**：Switch 把 children 渲染进轨道，轨道底色
`colorTextQuaternary` 上白字只有 3.11:1——强度下拉的标签直接走文字阶，
不再有那层将就；外包 `<label>` 可关联点击的做法同样保留给下拉触发器。

### 8.8.1 失败卡片与流中断卡片

两张卡共用一套外壳（`colorErrorBorder` 描边 + `colorErrorBg` 底 + 圆角 10px、
`padding 13px 15px`、`margin-top 12px`），因为它们是**并列的两种「没出结果」**：

- **失败卡片**：模型侧的四类失败（PRD §5.8）。标题 + 说明 + 出路按钮 + 一行注
- **流中断卡片**：请求根本没走完。标题「连接中断」+ 原始错误 + 两条出路
  （重试 / 把问题放回输入框）+ 一行注

**两张卡都收进消息列里**（D-099 前它们挂在消息列外侧/末尾）：错误是**这条
消息**的一部分，排在正文与引用之后（`parts/MessageItem.tsx` 的显式顺序），
容器带 `role="alert"`。互斥判据从「旁路 state 里有没有 failure」变成
**「这条消息里有没有 `mimir.failure` data part」**——有 part 说明服务端
已经分过类（走失败卡），没有才是真·中断（走引擎的消息状态
`incomplete` + 错误文本，`MessagePrimitive.Error`）。

**「已停止生成」那一行同源，形态取官方 StoppedRun 的 reason pill**：
mono 药丸（Square 10px 实心 + 「已停止生成」，`colorFillQuaternary` 底、
9999px 圆角）+ 旁边一句「以上是已生成的部分」。判据从自维护的 `stopped`
布尔变成消息状态**`incomplete` 且 `reason === 'cancelled'`**。`reason` 那一半不能省——停止
与失败共用 `incomplete`（失败是 `reason: 'error'`），只判 `type` 会把这一行
挂到失败卡下面，同一屏「请求超时」与「已停止生成」互相打架（实测踩过，
`ChatPanel.test.tsx` 的失败轮用例守着）。**不抄引擎的 StoppedRun 的
Continue / Discard**：服务端没有可续跑的 run 记录，那对按钮会是空壳
（`parts/StoppedNotice.tsx`）。

**回答下的动作条**（存成笔记 / 复制）只在最后一条消息上——三个条件：
这条消息**正文非空**、**没在生成中**（`status` 不是 running）、且**不是
失败/中断轮**（没有 `mimir.failure` part 且 `status` 不是 incomplete）。
前两条管「没有正文的一轮」；第三条是旧实现的明确决定（PRD §5.7/§5.8
「失败卡与动作互斥」）——失败轮的正文是错误原文，「存成笔记」会把一句
400 存进知识库、「复制」只会复制报错，而那时用户要的是出路、不是沉淀。
重做时丢过一次，回归用例补上了。「复制」带 `data-copied` 状态 + 图标
200ms 交换（§7 的同一条曲线）。

**未实现的出路真的 `disabled` + 「M0 未实现」tooltip**，不是看着能点却在
`onClick` 里静默什么都不做。tooltip 要包一层 `<span>`：antd 的 Button 禁用时是
`pointer-events: none`，事件到不了按钮自己，Tooltip 也就不会弹。

出路仍是**按钮**（不是灰字），这样读屏与视觉都还能扫到「还有哪些可能」——
删掉它们等于把 PRD §5.8 的出路表从界面上抹掉。

### 8.9 内联工具条

深色浮层（`#1f2329` 底、白字、圆角 8px）——与正文形成强对比，
因为它浮在**文字之上**，必须一眼区分于内容。这一处刻意离开浅色体系。

按钮禁用时保留在工具条上并给 tooltip 说明原因（M1 才实现的动作），
而不是隐藏——直接删掉用户会找不到入口，做得像能点却没反应是最坏的一种。

### 8.10 命令面板（Ctrl K）

```
┌──────────────────────────────────────────┐  圆角 12px，620px 宽，top: 14vh
│ ⌕ 搜索文档、执行操作，或直接提问…          │  ← 搜索行，13px 18px，下边框
├──────────────────────────────────────────┤
│ 操作                                      │  ← 分组标签 11.5px / 600 / 三级文字
│ ▤ 新建笔记                                │  ← 行：9px 18px，通栏
│   空白 Markdown 笔记，直接落进库             │
├──────────────────────────────────────────┤
│ ↑ ↓ 选择   Enter 打开   Esc 关闭           │  ← 页脚 11.5px，上边框
└──────────────────────────────────────────┘
```

**三段通栏**：搜索行 / 列表 / 页脚各自声明左右内边距（**统一 18px**），
`body` 与 `container` 的内边距都归零。不要用「负外边距抵消容器内边距」的写法做
通栏——容器内边距一改，负数就对不上，行会歪出去或宽出一条。

**定位只靠 Modal 的 `top: 14vh`。** 不要再给内容加负 `margin-top` 当「更靠上」的
微调：那会把搜索框拉到白色面板**外面**，浮在页面内容上，而截图上看起来只是
「面板位置有点怪」。

**搜索框不画自己的边框和焦点环**（浮层本身就是容器），改为让下边框在
聚焦时提亮（`colorPrimaryBorder`）。焦点仍然可见（§7.2），但不常驻一道蓝环。
antd v6 的 `focusOutline` 会画出一圈蓝色胶囊，三处（`input` / `affix-wrapper` /
伪类）都要显式关掉。

**高亮项用三重线索**（同 §8.1 的导航项）：`colorPrimaryBg` 底 + `colorLink` 字色 +
500 字重。只给底色的话，键盘上下移动时视线要去找「哪一行变色了」。
用 `colorLink` 而不是 `colorPrimary`——主色作文字在浅蓝底上只有 3.61:1（§3.2）。

**「问 AI」提示条用 `tintNav` 中性底，不用 `colorPrimaryBg`。** 它紧挨高亮项，
两片浅蓝会连成一块，看起来像跨行的选中态；而且它是**提示**不是状态，
语义色只出现在真的有状态的地方（§0.1）。AI 的暗示由 `✦` 的 `colorLink` 承担。

**圆角 12px，不用 `borderRadiusLG`。** 规范 §5.2 把「对话框、命令面板」定为
12–14px，而 antd 的 `borderRadiusLG` 是 base(8) + 2 = 10px，够不到那个区间。

### 8.11 保存状态（工具条）

```
┌──────────────────────────────────────────────────────┐
│ 2026/09/rag-….md                 已保存     💬 问 AI │  ← 工具条 min-height 48px
└──────────────────────────────────────────────────────┘
```

**常驻在文档工具条上，与路径、问 AI 同级。** 字号 `badge` 档（11.5px），
状态色取自语义 token（保存中用 `colorTextQuaternary`、已保存用
`colorSuccessText`、失败用 `colorErrorText`）。失败态可点重试并带下划线。

三条形态约束：

1. **只在笔记上显示**（`kind === 'note'`）。资料是只读的，给它显示「已保存」
   会让人以为可以编辑（§2.3）
2. **非失败态 `disabled`。** 状态显示被做成按钮只为让失败态可点；其余时候
   若可点却无事发生，那正是 §7.4 说的最坏的一种
3. **不占额外纵向空间。** 工具条本来就在，状态落在它已有的高度里

它原先渲染在正文上方、标题与元信息之间：一块只有「已保存」三个字的独立行，
两侧都空，看起来像没画完；而且**位置会跳**——状态出现与消失时整块正文
上下移动。`docs/PRD.md` §5.9 原话就是「工具条常驻」，之前那个实现与文档
写的位置并不一致。

### 8.11.1 模型分区：只读列表 + 表单（D-080）

**卡片是两列网格 + 一行展开入口**（demo 形态，用户拍板）：

卡级动作的惯常位置；纵排会让每张卡多出一行按钮的高度（实测两种形态的卡高
133px 对 165px 左右）。

**「查看模型」用链接样式而不是按钮**：它不作用于这一张卡，而是**展开这张卡
的另一层**——混在三个动作按钮里会读成第四个动作。链接色 + 无边框 + 箭头
（在文字之后，展开时翻转 180°）把语义分开。hover 只加下划线不换色：
链接色本身已是强调色，换色是重复信号。

**表单里「这一组的动作」放标题条右端**（`Panel` 的 `extra`，demo 形态）：
「拉取模型 / + 手动添加」属于「模型与用途」这一组，放进内容区会让标题与动作
分成上下两块、白占一行高度。标题条因此是 flex 行（`margin-left: auto` 推右，
`gap: 9px` 管标题与接缝标识）。**带按钮的标题条比纯文字的高 4px**
（46 对 42）——这是同一组件两种高度的唯一一处，可接受：收掉内边距会让另外
十几个面板的标题条一起矮 6px，那才是可见的回归。

**动作与导航用两种形态区分**：同一个右端位置上，「拉取模型 / + 手动添加」
是**小按钮**（真的往这组里加东西），「重新选择」是**链接**（只是回到上一层
重新挑预设）。「预设」面板因此没有内容体——当前选的是哪家在标题条的 seam
位里，`Panel` 的 `children` 可省。

**列表只读，编辑进表单；创建与编辑复用同一张表单**（这是用户拍板的形态，
D-080）。三条形态决定：

1. **卡片上只有事实，没有输入框**。名字 + 密钥徽标、地址（等宽）、一行摘要
   （几个模型 · 何时拉过 · 用途分布 · 哪个角色在用）。摘要回答的四个问题
   正是用户来这一页要核对的——原先要从四个输入框里把值读出来，
   而误点一下就是一个未保存的改动
2. **模型明细按需展开**（「查看模型（N）」），展开后是只读行：
   等宽模型名 + 用途 chip + 来源。**与表单里的行共用同一套网格列宽**
   （`minmax(0,1fr) 196px 56px`，只读态少一列动作位），两种状态下
   扫读的竖线一致（列表页表头那条教训，D-079）
3. **表单是同一屏的另一个视图**，不弹窗、不跳路由。供应商配置本来就是
   这一页的内容，弹窗会把「我在配哪一段」的上下文切掉

**用途 chip 是真实 `<button>` + `aria-pressed`**，不是 `Tag.CheckableTag`：
后者只渲染视觉，读屏念不出按下状态（与「图标档的 Segmented」同一类问题）。
选中态配色与导航项同源：`colorPrimaryBg` 底 + `colorLink` 字。
只读态用同一形状的静态 chip（`chipStatic`），可点与不可点一眼可分。

**拉取结果先闪后留**：新加入的行用一次 2.6s 的主色底动画（`modelRowFlash`，
`animation-fill-mode: both` 让底色自行回到透明，不需要定时器摘类）。
只闪新增行——对整块列表做动效等于没告诉任何事。顶部另有一行摘要
（`新增 2 · 移除 1 · 保留 20——用途的来源说明 · 保存后生效`）。

**「保存后生效」这句话必须写出来**：拉取与手改都只在草稿里，
用户点过「拉取模型」看到块内容变了，很容易以为已经落库——
而这时候刷新页面会全部消失。这是「界面已经显示的，不写」（§8.15）的
一处例外：它说的正是界面上**看不出来**的那件事（草稿 vs 已保存）。

**任务分配：供应商 + 模型是一个级联选择器**（用户拍板，取代早先的两个
`Select`）。触发器的值读作「供应商 / 模型」，一次选中叶子才算绑定：

```
┌──────────────────────────────────┐
│ 对话   本地假端点 / voyage-3   ⌄  │  ← 触发器：420px 固定宽，行间对齐
└──────────────────────────────────┘
        ↓ 点开
  ┌────────────┬──────────────────┐
  │ 本地假端点 ›│ fake-chat-pro    │  ← 第一层：家（缺密钥带后缀）
  │            │ hand-added-keep… │  ← 第二层：该角色可用的模型（按用途筛）
  └────────────┴──────────────────┘
```

三个决定：

1. **合并的理由是「半配置状态」**。两个下拉时，用户选了供应商、还没选模型
   的那一刻，角色处于「未就绪」而用户以为配好了（然后发现「测试」按不动）。
   级联把两步收在一次选择里，那个中间态不存在。旧理由（「先选家再选型号
   是用户心里的顺序」）在级联里依然成立——第一层就是家
2. **摘要的空态说「留空（回落到对话模型）」**，其余角色说「选择供应商与模型」。
   摘要允许留空是规则（会回落到对话），不说的话用户以为没配完
3. **行下方不再有说明文字**（用户要求去掉）。原因只在悬停「未就绪」的
   tooltip 里出现——那一行的信息（缺密钥 / 用途不符）本来就该按需读，
   常驻会让四行角色各挂一句解释，把这一屏读成一篇文档（§8.15）

```
┌────────────────────────────────────────────────────────┐
│ 全部       本月      本周      今日                      │  ← Stats 零件
│ 210.4 万   18.2 万   6.1 万    1.2 万                   │
├────────────────────────────────────────────────────────┤
│ 消耗热力图                                            │
│  一 ▫▫▫▪▫▫▫  二 ▫▫▫▫▫▫▫  三 …                          │  ← 54 列 × 7 行
│  一 ▪▫▫▫▫▫▫  二 ▫▫▫▫▫▫▫  三 …                          │
│                                                        │
│ 少 □ ▫ ▪ ▫ ▫ 多 ╱ 用量未上报  最深一档 ≥ 12.3 万              │
│                                       · 按 Asia/Shanghai 聚合 │
├────────────────────────────────────────────────────────┤
│ 按角色                                                  │
│ 角色      模型            调用   输入   输出   失败       │
│ 对话      deepseek-chat    12    8.1万  1.2万   0        │
│ 向量化    bge-m3          204   12.0万  —      0        │
└────────────────────────────────────────────────────────┘
```

**分区里的每一件可交互的东西都用 antd 组件。** 这一条是补的：
第一版用了原生 `<select>`（范围）、手写 `<table>`（按角色）、
`<label>` + 隐藏 `<input type="file">`（头像上传）、裸 `<button>`（账号行）。
理由是「三个选项不值得占一行按钮的宽度」这类**代码量**的考量——
但它们全都**不服从 token 体系**：深浅两套主题管不到，
原生控件的默认外观还各浏览器不同，于是成为整页唯一不属于这套设计的东西。

现在的对应关系：

| 用途 | 组件 | 为什么它就是对的 |
|---|---|---|
| 时间范围（三个互斥选项） | `Segmented` | 与「外观」分区同一个形态；并列选项摊开比藏进下拉少一次点击 |
| 按角色的表 | `Table` | 表头底色 / 内边距 / 行 hover / 边框在深浅两套主题下都已由 token 校准 |
| 换头像 | `Upload` + `Button` | `beforeUpload` 返回 `false` 阻止默认上传，先本地裁剪再传 |
| 左导航账号行 | `Button type="text" block` | hover 底色由 token 给 |
| 行内代码 | `Typography.Text code` | 底色与字色走 token，与正文的 `inlineCodeFg` 同源 |

**表格只留行分隔线，去掉列之间的竖线。** antd 默认画竖线
（border-inline-end），那是给宽表用的——列多、行很长时帮视线横向对齐。
这里只有六列、内容很短，竖线只是把干净的一行切成格子，而且面板本身
已经是一层容器，再来一层网格是双重的分隔（同「面板不套 Card」）。

**网格与标签交给 `@uiw/react-heat-map`**（`TECH.md` §12.8、D-041）。
第一版是手搓的 371 个 div，**实测踩了月份标签的 bug**：判定写成「这一周的
第一天所在月与上一周不同就打标签」，而月份变化常常落在周的中间，
于是整个月被跳过——370 天只打出 3 个标签（应有 13 个）。同类的边界还有
首周补空、`gridNum` 与日期范围对齐等，属于**轮子该别人造**的部分。

选它的三条依据：**零运行时依赖**（peer 只有 react / react-dom /
`@babel/runtime`，而后者本来就在依赖树里）；`rectRender` 能单格自定义
（保住「未上报」那个状态）；`panelColors` 能接我们的分位数阈值。

> 注意这**不是**「引入图表库」的反转。echarts / recharts 那种几十万字节的
> 通用图表引擎仍然不引——它们解决的是「任意数据 → 任意图形」，
> 而这里只要一个日历网格。11px、间距 2px、圆角 2px 的形态不变。

**一行七格而不是一行七列**：竖着看是星期、横着看是周。行列顺序与 GitHub
一致——用户对这张图的肌肉记忆来自那里，不创新。

**图的宽度按列数算死，不用 `width: 100%`。** 库的 `gridNum` 是从容器宽度
推的（`floor((clientWidth - leftPad) / (rectSize + space))`），不是从日期范围
推的——交给 CSS 自适应会**安静地丢掉放不下的那几天**（实测 370 天在 680px
的容器里只渲染 53 列，最后 4 天含「今天」整个消失，而图看起来完全正常）。
左侧内边距因此小于右侧（8px vs 16px），让一年的 730px 刚好放得下、不出滚动条。

**tooltip 同时给两个数**（`PRD.md` §5.11）：

```
9 月 23 日 · 12.3 万 token · 8 次调用
```

颜色按 token，密度按次数。这也是「我花了多少」与「我还在不在用」两个
问题唯一合得住的呈现方式。

**图表的月份标签只用中文数字的一二三，不写「1月」**：横轴挤不下 12 个
标签，而「一月」在 53 列里放得下。

**月份 / 星期标签的颜色必须从 `--rhm-text-color` 给，不能只给容器的 `color`。**
库在 `<svg>` 上写了一条**内联**样式 `color: var(--rhm-text-color, #24292e)`，
标签自己是 `fill: currentColor`——内联优先于样式表，所以在容器上写
`color: token.colorTextTertiary` 会被它整条盖住。不给这个变量的表现是
**深色下标签用库的回退色 `#24292e` 画在 `#141618` 的底上，实测 1.23:1**：
整条时间轴等于没画，哪一列是哪个月、哪一行是星期几都读不出来，图退化成
一片没有刻度的格子（浅色下同一个回退值是 14:1，所以这个洞只在深色露出）。
深色必须不弱于浅色——`design.test.ts` 那条跨外观比较管的是 token，
管不到这种被第三方内联样式挡住的引用。

**图例可以换行，图不能。** 两者待遇不同是因为职责不同：图必须保持列的
形状（放不下时它自己横向滚动），而图例是说明文字，宁可折到第二行。
不折的表现是窄窗口下面板的 `overflow: hidden` 把尾部**硬切**掉——
实测 420px 视口里图例 `clientWidth` 266 / `scrollWidth` 427，可见文字停在
「这一年还没有用」而「· 按 Asia/Shanghai 聚合」整段消失（没有省略号，
看起来像文案本来就是断的）。那半句恰恰是**唯一需要声明的口径**：
这张图的每一天按什么时区归属。

### 8.13 账号行（左导航底部）

```
┌────────────────────────────┐
│ ⚙ 设置                      │  ← 原有的 footer 菜单
├────────────────────────────┤
│ (头像) kemin          换头像 │  ← 账号行：36px 头像 + 名称
└────────────────────────────┘
```

**放在设置下方、最底部**，而不是顶部。理由：它是「关于我自己」的信息，
不是导航目标——点它进设置 › 账号，与上面那行是同一个去处，而顶部
已经有品牌标记。

**无头像时用名称首字的字母头像**（antd `Avatar` 原生行为），底色走
`colorPrimaryBg`、字色 `colorLink`——不用主色填充，那是按钮的语义。

**折叠态只留头像**（36px 会撑破 48px 的 rail，所以缩到 24px 并居中）。

**现状是上面那张图的一行版**（`NavSidebar.tsx` 的 `AccountRow` 有完整理由）：
账号在左、设置图标贴最右，不再有单独的「⚙ 设置」菜单行——两项都通往设置页，
摆成两行只会让人看不出差别。**但两者落点不同**：头像进设置 › 账号
（那是「关于我自己」），齿轮进设置首页（下面第一个分区）。齿轮是**没有名字的
入口**，它不该替用户选一个分区——先前它跟账号共用 `section=account`，
于是点齿轮落在最后一个 tab（用户报的问题）。

#### 账号菜单里的两个快捷入口（D-081）

```
┌──────────────────┐
│ 👤 账号资料       │
│ 🎨 主题        ›  │  ← 级联：悬停/点击展开第二列
│ 📊 数据统计       │  ← 跳设置 › 统计分区
├──────────────────┤          ┌─────────────┐
│ ⏻ 登出           │          │ 跟随系统   ✓ │  ← 勾在**文字之后**
└──────────────────┘          │ 浅色        │
                              │ 深色        │
                              └─────────────┘
```

**主题是级联（子菜单），三个取值在第二列**（用户拍板）。当前值打勾、放
**行尾**（菜单项的 `extra`）而不是行首（`icon`）：三个取值里只有一个带勾，
放行首会让选中项的文字比其他两项整体右移一格，「浅色」与「深色」不在同一条
竖线上。放行尾则文字左对齐（实测三项 label 同在 x=174）、勾右对齐。

**子菜单弹层有一个必须正面处理的坑**（antd 6.6.4 + rc-menu 1.5）：点完子项后
主菜单关闭，但**子菜单弹层留在页面上不消失**——它是**独立 portal**，
`Dropdown` 关闭时 rc-trigger 不再重渲染 overlay，异步的 state 更新赶不上
关闭动作（实测 `aria-expanded` 一直是 `true`、state 早已是 `false`）。
修法是**受控 `openKeys` + 选中时 `flushSync(() => setOpen(false))`**：
同步收起子菜单再切主题，不等 React 的批处理。rc-menu 自己对同类
「React 18 合并事件导致不同步」也用 `flushSync`（其 `triggerOpenKeys` 的
`forceFlush` 分支），这是同一个问题的官方姿势。

**不要退回「分组平铺」**：早先因为没有 `flushSync` 而临时改成 group label +
三个平铺项（少一次悬停、也没有 portal 问题）。用户看过后要求改回级联形态
——主题是一组**取值**，级联把「这是一组的哪几个」与「当前是哪个」表达成
一个可展开的整体，比平铺三行更省纵向空间，也与「账号资料 / 数据统计 / 登出」
这三个动作项在形态上分开（取值 vs 动作）。

**当前值打勾而 `disabled` 留空**：点当前值是无操作，禁用会读成「这一项坏了」
（`ComposerMenus` 里那组「当前模型」是真禁用——那是展示行不是选择行，
两者语义不同）。

**它不改变「主题的家在设置页」**：完整说明（为什么只存在本浏览器、换设备要
重选）仍在外观分区；这里的三个项只是同一份状态的第二个入口，两处都调
`appearance.ts` 的 `setThemeMode`，没有第二份状态可漂移。三个取值与文案
来自 `THEME_MODES` / `THEME_MODE_LABELS` 单例——加一个取值只改一处。

**「数据统计」直接跳分区**（`?section=stats`），而不是跳设置首页：
这一项的名字就是目的地，落在别处等于让用户再找一次。

**横向位置由一套值决定：行内 6px 右侧内边距 + 账号项的 `margin-inline`。**
第一版这里写 `padding: 2px 5px 3px` 而账号项又带自己的 6px margin，两套值
相加把账号盒右移 5px——实测头像落在 x=19 而菜单图标在 x=14，与「头像与菜单
图标落在同一条竖线上」的注释不符。改完头像 x=14、齿轮右边缘 193，与树行的 ⋯、
标题行的 ＋ 同一条竖线。（右侧那个 6px 由行内边距给，不给齿轮自己加
`margin-inline-end`：折叠态是竖排居中，那 6px 会把齿轮推离中线 3px。）

**触发器是 antd `Button`，不是带 `onClick` 的 `div`**（D-042）。`div` 折叠态
下既不在 tab 序列里（整条 rail 的键盘序列会跳过它），也挂不上 `Tooltip`、
按 Enter 不动——一个只剩字母头像的按钮，登出就此失去名字。换 `Button` 一次
拿到焦点环、Enter/Space 激活与可及名称（折叠态 `aria-label` 是
「{名字}，账号菜单」——菜单现在有四项，逐一列举入文案会又长又漏得快）。

### 8.15 设置页的文案：不写界面已经显示的东西

设置页一度长成一篇文档：每个分区上面一段导语、下面一个「说明块」，
讲产品理念（为什么收集摩擦要低）、讲实现理由（为什么导出在服务端）、
甚至讲维护者才知道的事（改注册表要重新部署）。九个分区加起来 **4314 字**，
其中多个分区里没有一行是用户要操作的东西。

清理过程中出现过一次判断偏差，值得留档：第一轮删掉明显的「理念段」之后，
留下的仍被指出是废话——

```
「密钥只存服务端，所以这里只显示『有没有配』，不显示值本身」
「这个选择存在当前浏览器里」（旁边 Segmented 正高亮着）
「能改的在这里改；还不能改的，如实说明原因」（就是这一页本身）
```

它们的共同点：**在复述用户已经看得见的东西。** 密码框是空的、
选项是高亮的、页面就在眼前。于是规则收紧成两条：

> **一、界面已经显示的，不写。**
> **二、不描述这一页自己。**

按下表判断每一句：

| 该留 | 例 | 判据 |
|---|---|---|
| 会改变操作的**后果** | 「切换不会搬运已有数据」 | 不知道就会以为数据跟着走了 |
| **不可逆**的选择 | 「要换邮箱，改服务端的 `OWNER_EMAIL` 再重启」 | 界面上没有入口，不说就找不到 |
| 字段的**填法** | 「自建端点通常需要打开路径风格」 | 填错就连不上 |
| 会**误读数字**的口径 | 「含失败与测试连接，所以调用次数不等于提问次数」 | 不知道就会把调用次数当成提问数 |
| 状态里**用户拿不到的那部分** | 「正在用 s3」「还差：桶名、Access Key ID」 | 徽标只说「未选中/待配置」，缺的是「跟谁比」和「缺哪个框」 |

| 该删 | 例 | 为什么 |
|---|---|---|
| **复述**控件状态 | 「只显示有没有配」「当前浅色」 | 空输入框与高亮选项就在旁边 |
| **描述本页** | 「能改的在这里改」 | 用户正看着这一页 |
| 设计**理念** | 「知识库会死于收集摩擦」 | 它说服的是评审。`PRD.md` 是它的家 |
| 实现**理由** | 「导出在服务端完成，不经过浏览器内存」 | 用户只关心导出能不能用 |
| **架构**叙述 | 「每个来源都是同一条 documents 记录」 | 与操作无关 |
| 维护者**视角** | 「加一家是往预设目录里加一行」 | 使用者不做这件事 |
| **内部标识** | 「需要先配置 `storage.s3.bucket`」 | 界面上的框叫「桶名」，用户对不上 |
| **术语** | 「接缝」「parser 接缝」 | 说「检索通道」「自动提取正文」 |

四条配套约束：

1. **`Note` 的原始用途是「解释为什么这里改不了」**，不是「补充背景」。
   想加一块之前先问：它命中上表左栏哪一行？答不上来就不加
2. **状态 reason 要给出「用户拿不到的那部分」**。`computeStatus` 因此
   把 `requires` 里的键名映射成 `params` 里的 label 再说出口——
   `plugins.test.ts` 有一条断言守着「必须点名」与「不许出现键名」
3. **术语从界面消失，不等于从代码消失**。`SeamTag` 那类标识仍有价值
   （报问题时说「leg 这条接缝」比「检索那个」准），但它属于**调试信息**，
   只在插件分区出现，不扩散
4. **同一句话只写一处**。共用描述（如存储后端的 `description`）会同时
   出现在存储分区与插件分区——只写一遍，不是重复

> 结果：**4314 字 → 约 3000 字**，九个分区里八个的整段导语删除，
> 留下的字几乎都在**行内**（字段说明、状态原因、后果提醒），
> 而不再是页面级的段落。这是「设置页」与「文档」的形状差别——
> 文档按章节递进，设置页按「你要改哪一项」组织。

**分区导航在窄屏换成 `Select`。** 八个分区的名字平铺需要约 256px，而
420px 的视口里导航条只有 247px 可用——`Tabs` 不折行，它会把第一个标签
裁成半个字（实测只剩「型」，后面两个分区只能去右端的 ⋯ 里找）。
≤880px（`NAV_NARROW_QUERY`，与左导航同一个断点）改成下拉：八个名字都完整、
可读。宽屏仍是横向 tab——§8.12 那条「并列选项摊开比藏进下拉少一次点击」
的取舍在摊得下时成立。

### 8.16 文件预览区（右栏）

上传件的正文区。结构由「有几层可看」决定，不是固定两个页签：

```
有正文 + 有查看器               无正文 + 有查看器
┌──────────────────────────┐   ┌──────────────────────────┐
│ [正文 | 原件]             │   │ （直接显示查看器）        │
│ ┌──────────────────────┐ │   │ ┌──────────────────────┐ │
│ │ 提取出的正文          │ │   │ │  PDF / 图片 / 视频    │ │
│ └──────────────────────┘ │   │ └──────────────────────┘ │
└──────────────────────────┘   └──────────────────────────┘

无正文 + 无查看器
┌──────────────────────────────────────────┐
│ ⚠ 这种格式的正文提取将在后续版本支持        │
│   PDF · 2.4 MB                     [下载原件] │
└──────────────────────────────────────────┘
```

**`Segmented` 只在两层都成立时出现。** 一个点了没反应的页签是假的选择
（§7.4）——而多数文件只有一层：PDF 只有原件，txt 只有正文，图片只有原件。
此时**直接显示那一层**，不套切换控件。

**PDF 与 Office 走自己的编辑器而不是浏览器的内置阅读器**：内置的那个
（`<iframe>` 指向下载端点）零依赖，但我们控制不了它——拿不到当前页号、没法在
页上叠层、工具栏还会与我们的工具条长成两层（TECH §15.12）。它曾经是这个
位置的实现（`height: 78vh`），D-057 起被替换。**代价必须说清**：PDF 现在没有
「选文字/复制」了（文字不作可选层，只用来定位查找高亮），换来的是页面级编辑
（旋转 / 删除 / 调序 / 倒序 / 插页 / 导入 / 裁剪 / 纸型）与查找。

**能借浏览器自带能力就借**，借不到的才自己写：

| 格式 | 查看器 | 形态 |
|---|---|---|
| PDF / Office（docx / xlsx / pptx / html） | **`@mimir/office` 的编辑器**（D-052 / D-057 / §8.4.1） | 上工具条 / 中编辑区 / 下状态行，与笔记同壳 |
| 图片 | `<img>` | `max-width: 100%`，圆角 8px，边框 `colorBorderSecondary` |
| 音频 / 视频 | `<audio>` / `<video>` | `width: 100%`，`max-height: 70vh`（Range 由服务端支持） |
| 其他 | 无 → 下载卡片 | 图标 + 「{格式} 没有在线预览」+ 主按钮「下载原件」 |

**查看器加载失败要降级，不留白。** HEIC 这类格式能通过 MIME 判断，但不是所有
浏览器都渲染得了 `<img>`。加载失败时降级成「这个浏览器打不开这种格式 +
下载原件」——空白在那里等于说「这个文件是空的」，而它只是这个浏览器看不了。

**文本类文件的正文用等宽只读渲染，不走 Markdown。** csv / json / 代码里有大量
换行与 `#`，走 Markdown 会把换行折叠、把 `#` 当标题——那是主动把内容显示错。
判据是 `mime.startsWith('text/')` 且不是 `text/markdown` / `text/html`。
容器：`colorFillQuaternary` 底、`fontFamilyCode`、`13px`（`excerpt` 档）、
`line-height: 1.7`、`white-space: pre-wrap`、`max-height: 70vh`。

**Office 提取出的正文要标注来源。** 正文下方一行 `note` 档灰字：
「以上文字是从原件里提取的，版式与原件不同（不含字体、页眉页脚与图片位置）」。
不说这句，用户会拿它跟 Word 比对，然后以为渲染坏了。

**未解析时那句话直接给原因**，不写「暂无正文」——四种原因见 §8.2 的表
（与列表项共用 `parseText` 的判据，措辞在 `@mimir/shared` 的 `parseSupport`）。

**工具条**在文件类上多两项、少一项：

| | 笔记 | 抓取的资料 | 上传的文件 |
|---|---|---|---|
| 左侧 | vault 路径 | URL | **原文件名**（它没有 vault 路径） |
| 保存状态 | ✓ | — | —（不可就地改写，显示「已保存」会让人以为能编辑） |
| 下载 | — | — | **✓ 常驻**（最常用的动作，不该要求先切到原件层） |
| 问 AI | ✓ | ✓ | ✓，但**正文为空时禁用**并在 tooltip 说明原因 |

## 9. 品牌标记

```
┌────┐
│ ‘’ │  两个引号，每个的碗里掏空一个圆
└────┘  引号本身就是一口井
```

**两层读法，第一层不需要前提**：

| 层 | 读法 | 谁读得到 |
|---|---|---|
| 1 | 引号 | 所有人。「带引用地问答」是产品核心差异点 |
| 2 | 井 | 知道 Mímir 神话的人（北欧的至智者，守护智慧之井） |

反过来（必须懂神话才看得懂的符号）会把多数人挡在外面，所以第一层必须能独立成立。

### 9.1 尺寸与用法

| 场景 | 尺寸 | 组合 |
|---|---|---|
| favicon | 16px | 只标记 |
| 左导航 | 20px + 文字 | 标记（主色）+ `mimir`（文字色，700，letter-spacing .06em） |
| 左导航（折叠） | 20px | 只标记，与折叠开关竖排居中 |
| 登录页 | 28px + 文字 | 同上，间距 9px |

**文字用正文色，不用主色。** 主色 `#1677ff` 作文字在白底上只有 4.10:1
（§3.5），导航顶部的品牌名不该是全页唯一不达标的文字。主色只给标记。

**「同上」管的是字重与字距，不管字号。** 两处的字标都必须是 700 /
letter-spacing .06em——字号随标记尺寸走（20px 的标记配 16px 文字、
28px 的标记配 20px 文字），但**字形是同一副**。实测漏过一次：登录页按
antd 标题的默认值渲染成 600 + 0.02em，单看登录页没问题，两处并排就露出
一个更细、字距更紧的字标——而 §9 这张表写的是「同上」。

### 9.2 两条实现约束

1. **井口用 `fill-rule="evenodd"` 挖空**，不是白色圆形覆盖。
   白圆在白底上没问题，但标记放到主色按钮或深色浮层上会露出白点。
2. **颜色走 `currentColor`**。写死 hex 会让 logo 成为全站唯一不服从主题的元素。

### 9.3 为什么是引号而不是别的

候选全部渲染出来在 16px 下看过，淘汰理由记在 `docs/DECISIONS.md` D-019。
一句话概括：**16px 的 favicon 是唯一真正的约束**——同心环、深度计、
细线引号在那里全都糊掉了，只有「实心块 + 掏空」这种高对比结构能活下来。

## 10. 落地方式

### 10.1 样式的组织方式

**样式方案是 antd-style（css-in-js）。** 它不是新的颜色体系，而是把
「token 消费」和「样式书写」合到一处：`createStyles` 里能直接读 antd token，
产出的又是带作用域的类名，不需要在 `:root` 和组件之间来回倒变量。

职责分工：

```
packages/renderer/src/theme/tokens.ts         ← antd token 的真相来源（ThemeConfig）
packages/renderer/src/theme/customToken.ts    ← mimir 自己的 token（antd 没有的语义）
packages/renderer/src/theme/MimirProvider.tsx ← provider 与全局样式的唯一组装处
packages/renderer/src/styles/global.ts        ← 全局样式：重置、高度链、文档字体、底色、动效退化
packages/renderer/src/**/*.style.ts           ← 组件/页面样式（createStyles）
packages/chat/src/**/*.style.ts      ← 对话包的样式（createStyles，同上）
packages/office/src/**/*.css         ← 编辑器包的手写 CSS（模板边界的样式，
                                        读 --me-* 变量；见 §8.4.1 与 office/AGENTS.md）
```

三条约定：

1. **组件样式不写 `:root`，也不写全局类名**。编辑器正文那种「Tiptap 渲染裸 DOM」
   的场景用祖先类名 + 嵌套选择器（`NoteEditor.style.ts` 的 `body`），作用域仍然
   在组件内。只有真正作用于 `html` / `body` / `#root` 的规则才进 `global.ts`。
2. **样式文件独立成 `.style.ts` 时放在组件旁边**，`useStyles` 从那里导出。
   组件简单就合并进组件文件——不必为了「规范」拆出一个只放三行样式的文件。
3. **不要新增 CSS 文件**。全局样式已经有一个出口（`styles/global.ts`），
   再开一个 `.css` 就绕开了 token 体系，也绕开了类型检查。

**跨包的样式有两条通道**（两个前端包按需要各用其一；对话包两条都用，
编辑器包主要用第二条）：

- **antd token 直接读**——包内的 `createStyles` 内部就是宿主的
  `theme.useToken()`，自动继承外观与自定义 token；包**不新建主题**、不传
  theme 的 ConfigProvider（内层传 theme 会重算 cssVar key，`--ant-*` 变量名
  一变，引用处静默失效）
- **CSS 变量桥**——`createStyles` 的样式体是静态字符串，读不到 React
  context，CSS 自定义属性是唯一能跨包流动的通道。宿主在面板/编辑器祖先上
  挂值（`editor-theme-bridge.ts` 的 `--me-*`、`ChatThemeBridge` 的
  `--mimir-chat-*`），包内写 `var(--mimir-chat-font-note, 12.5px)` 并带回退值。
  **挂错位置的表现是样式全退回回退值**——界面能用、字号差半个像素，不报错
- **包内的 `createStyles` 模板串里不能出现反引号**（注释里也不行）——
  `scripts/check-style-backticks.mjs` 守着，它的扫描根含 `packages/chat/src`
  （新包也要加进去：代码搬走了、守卫扫不到，等于静默失去覆盖）

### 10.2 用 token，不要写字面量

```tsx
// ✗ 页面里散落的字面量：改一次主题要全文搜索替换
<div style={{ background: '#e8f1ff', color: '#1677ff' }} />

// ✓ 优先：createStyles 里用 token
const useStyles = createStyles(({ css, token }) => ({
  row: css`
    background: ${token.colorPrimaryBg};
    color: ${token.colorLink};
  `,
}))
```

**列底色、行内代码色、`<mark>` 高亮底是唯一的例外**——antd 没有这些语义，
它们定义在 `theme/customToken.ts`，代码里用 `token.tintList` 这样消费。
页面里不要出现这些字面量。

antd 组件自身的样式覆写用 `ConfigProvider` 的 `theme.components`，
不要用选择器硬压——权重问题会一直跟着你。

### 10.3 主题的注入链路

```
ThemeProvider(appearance, theme=themeConfigFor(appearance), customToken=customTokenFor(appearance))
  └─ ConfigProvider(locale=zhCN)     ← 只负责 locale，不传 theme
       └─ AntApp                      ← message/notification/modal 的 context 版本
            └─ GlobalStyles           ← createGlobalStyle 注入的全局规则
```

**内层 `ConfigProvider` 不能传 `theme`。** antd 会按传入的 theme 重算
`cssVar` 的 key，`--ant-*` 的变量名随之改变，所有引用变量的地方静默失效
（不报错，只是颜色不对）。不传时 antd 直接继承外层的 theme。

`cssVar: { key: 'mimir' }` 固定住了变量类名，所以规则里可以直接写 `--ant-*`。
但变量注入在 **antd 组件的 DOM 子树**上，不是 `:root`——所以：

- `styles/global.ts` 的 `body` 规则拿不到 `--ant-*`，这就是它用
  `${(p) => p.theme.fontFamily}` 取主题值的原因
- 任何**在 antd 组件树之外**渲染的元素（React 之外的 portal、裸 DOM 节点）
  都拿不到变量

新增页面时不需要关心这点（`MimirProvider` 已经包好了）。

**`appearance` 是受控的**，状态的持有者是 `theme/appearance.ts`，不是
antd-style 自己那套 `themeMode`。两个理由：

1. antd-style 的 `themeMode='auto'` 首次匹配走 `setTimeout(…, 1)`，
   **首帧先按浅色渲染再翻成深色**——深色用户每次打开都会看到一下白闪
2. 它的选择不持久化，而这是要记住的偏好

`appearance.ts` 同步地从 `localStorage` 与 `prefers-color-scheme` 算出第一帧
该用哪套色，并把结果写到 `html` 的 `data-theme` 与 `color-scheme` 上。
`index.html` 里有一段等价的内联脚本先跑一遍，覆盖「脚本执行到样式注入」那段
空白——**两处判断必须同源**，改一处要改另一处。

`color-scheme` 不是可选的：它决定滚动条、原生 `<select>` 下拉与表单控件
由浏览器按哪一侧渲染。不设的话深色页面上会挂着一根亮色滚动条，而那不在
我们的样式管辖范围内——改多少 CSS 都盖不住。

### 10.4 守门测试

`design.test.ts` 会真正计算对比度。**浅色与深色跑同一组断言**
（`it.each(APPEARANCES)`），它守住五条线：

1. 语义色对 ≥ 4.5:1（两套外观各一遍，且语义文字落在容器底上也要达标）
2. 文字-2 / 文字-3 在四种底上都 ≥ 4.5:1
3. 文字-1 ≥ 7:1（AAA）
4. 占位符 ≥ 3:1
5. 跨外观不回归：深色的每个文字色都不得弱于浅色对应的那个

**它的扫描根包含 `packages/chat/src`**（D-099，字号阶梯守卫随代码一起搬；
反引号守卫在 `scripts/check-style-backticks.mjs`，同样加了那个根）：
这两条守卫都是靠扫源码工作的，漏掉一个目录的表现是「代码搬走了、守卫以为
它还在」——静默失去覆盖，不是报错。

**深色没有「稍差一点也可以」的分支。** 那种分支一旦存在，深色就会在几次
迭代后变成「看起来还行」而不是「测得过的」。

**改了 token 导致测试红了，不要改断言，先改设计。** 如果确实要放宽标准，
在本文档里说明理由，再改测试。反过来说：**如果某条新规则连浅色的既有取值
都过不了，那说明门槛定错了，不是设计错了**——比如焦点环的浅色基线本来就是
1.74:1（antd 派生的淡蓝），这时该守的是「深色不比浅色弱」而不是硬提 3:1。

## 11. 明确不做的事

| 不做 | 原因 |
|---|---|
| **深色的第三套主题**（高对比度 / 护眼等） | 深色本身是校准过的（§3.8），再加一套就要重算全部对比度，而收益不明。antd 支持自定义 appearance，但**支持不等于该做** |
| **第二套 CSS 方案**（Tailwind / CSS Modules / styled-components） | 样式走 antd-style 是既有决定（`apps/web/AGENTS.md`）。两套方案并存会让「同一个圆角有几个值」变成需要查两处的问题 |
| **替换 antd 种子色** | 见 §3.2，派生色会跑偏 |
| **自造字体阶 / 间距阶** | antd 那套够用。自造的第二套迟早和它对不上 |
| **超过两档的阴影** | 见 §5.3 |
| **骨架屏 / 加载动画的花样** | 用 antd 的 `Spin` / `Skeleton`。加载态不该是展示设计的地方 |
| **给每个文档类型配高饱和色** | 见 §0.1 反面例子。**格式同理**：`kind` 只到「来源」这一层（七组，§3.7），格式是中性文字——格式是开放集合，每加一种就多一组色对，而那正是 §0.1 的反面 |
| **缩略图与网格视图** | 需要一条缩略图管线（图片解码 + PDF 首页渲染），而「文件名 + 格式 + 大小」已经足够认出是哪份文件（`PRD.md` §1） |
| **自建编辑器 UI** | PDF 批注在 M2。docx 的编辑界面用 vendored 的 GenOffice 组件（D-049），**不自建**；「下载 → 外部工具改 → 替换原件」仍然是保留路径，所以「替换原件」必须有 |
| **外观偏好同步到服务端** | 它是纯客户端的渲染偏好，服务端一个字节都不需要知道。存进设置表会让首帧要等一次请求才知道用哪套色（闪一下），还会让同一台机器上两个浏览器的偏好互相覆盖。代价是换设备要重选一次，这一点写在界面上（`AppearanceSection`） |

## 12. 交付前检查

新增或改动界面后，逐条过一遍：

**对比度**
- [ ] 新增的文字色对算过对比度（≥ 4.5:1 正文 / ≥ 3:1 非文本）
- [ ] **两套外观都算过**（浅色过了不等于深色过了，反之亦然）
- [ ] 状态色成对使用，没有拆开
- [ ] 没有把 `colorPrimary` 直接用在文字上

**外观**
- [ ] 新增的颜色走 `token.*` / `customToken`，没有写死浅色 hex
- [ ] 需要两套外观的映射表（如徽标色对）用 `useAppearance()` 分支，
      不是在样式里写 `appearance === 'dark' ? … : …` 的散落判断
- [ ] 深色的值不是浅色的副本（`design.test.ts` 会逐项比对）

**内容**
- [ ] 中文长文行高 ≥ 1.75
- [ ] 内容列宽度是 760px（对话 860px）
- [ ] 内容区颜色走 `token.*`，没有新字面量

**样式写法**
- [ ] 组件样式在 `createStyles` 里，没有新增全局类名或 `.css` 文件
- [ ] 覆写 antd 内部结构时用 `${prefixCls}`，没有写死 `ant-`
- [ ] 没有往 `ConfigProvider` 重复传 `theme`（会换掉 cssVar key）

**交互**
- [ ] 焦点环可见，没有被 `outline: none` 干掉
- [ ] 所有可点击元素有 `cursor: pointer` 和悬停反馈
- [ ] 图标按钮有 `title` / `aria-label`
- [ ] 禁用态用 antd `disabled`，不是自己画一个灰的

**动效**
- [ ] 悬停反馈 ≤ 0.15s
- [ ] 没有动画 `width` / `height` / `top` / `left`
- [ ] 新动效在 `prefers-reduced-motion` 下会退化

**响应式**
- [ ] 1100px / 880px 两个断点下布局不崩
- [ ] 没有横向滚动

**验证方式**
- [ ] `pnpm check` 通过（含 `design.test.ts`）
- [ ] 在浏览器里实际看过，不是只看代码推断（根目录 `AGENTS.md` 完成定义第 4 条）
