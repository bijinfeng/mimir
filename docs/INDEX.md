## 各文档的职责

| 文档 | 保留什么 |
|---|---|
| `PRD.md` | 产品范围、非目标、关键交互 |
| `TECH.md` | 当前有效的架构、数据契约、部署与维护方法 |
| `DESIGN.md` | 当前有效的视觉和交互规范；深色值以该文档为准，原型仅展示浅色 |
| `DECISIONS.md` | 改变既有取舍时仍需理解的理由和被否决的路径 |
| `RESEARCH.md` | 未来可能需要复核的调研证据及其适用条件 |
| `AGENTS.md` | 开工入口、必须遵守的边界、容易静默出错的区域性坑 |
| `output/index.html` | 可交互的浅色原型；与现行规范不一致时以现行文档为准 |

## 维护规则

1. **只记录长期有效、且不容易从代码直接看出的信息。** 产品边界、当前契约、
   非显然的技术取舍和可复现的静默坑值得保留。普通修复、实现步骤、一次性的
   排错经过、构建输出、测试数量和目视验证过程放在提交信息或 PR 中。
2. **每个事实只有一个真相来源。** 行为改变时，只更新确实被影响的规范；
   其他文档用链接或决策编号指路，不复制整段说明。文档与代码同批提交。
3. **决策日志记录取舍，不记录施工流水。** 只有推翻既有决定，或作出未来可能
   被误改的实质选择，才新增决策。写清背景、结论和关键理由即可；普通修复
   不需要新编号。被取代的决策标明后继编号，保留必要的历史原因。
4. **区分已验证与未验证。** 调研结论写明证据和适用条件；尚未验证的部分
   明确标注，不把推测写成约束。
5. **静默坑按区域就近记。** 只留下症状、根因和避免方法；所属区域写在其
   `AGENTS.md`，跨区域写在根 `AGENTS.md`。`TECH.md` §10 只指路。

判断例子：修复一个按钮但不改变既定交互，只在提交里写验证结果；改变按钮
的用户可见语义，更新 `PRD.md` 或 `DESIGN.md` 的现行条目；改变存储/接口
契约，更新 `TECH.md`；否决一个看似合理的替代方案且未来容易误选，才追加
`DECISIONS.md`。不要为这四种情况另建“本轮总结”文件。
