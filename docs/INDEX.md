## 文档之间的关系

```
PRD.md          做什么、不做什么         ← 产品判断
  │
  ├─→ TECH.md   怎么做                   ← 工程实现
  │     └─→ DECISIONS.md  为什么这样选    ← 决策日志，按时间追加
  │
  ├─→ DESIGN.md 长什么样                 ← 视觉与交互规范
  │
  └─→ RESEARCH.md  为什么不用别的         ← 调研证据
```

### 三份文档 + 一个原型，各管一层

| 层 | 谁 | 说明 |
|---|---|---|
| 交互怎么走（点什么会发生什么） | `PRD.md` §5 | 产品判断 |
| 值（颜色 / 字号 / 间距 / 动效） | `DESIGN.md` §3–§6 | **实测**出来的，`design.test.ts` 守着；颜色分浅 / 深两套 |
| 形态（每个组件长什么样） | `DESIGN.md` §8 | 数值取自原型的计算样式 |
| 以上三者的可运行验证 | `output/index.html` | 交互原型，双击打开 |

**原型只有浅色。** 深色那套（`DESIGN.md` §3.8）没有原型可依——它的每个值
是按 antd 深色的实际派生值重新校准的，判据是对比度而不是「与原型一致」。
这是这份规范里唯一一处「原型不是参照物」的地方。

**原型在「形态」上更成熟，`DESIGN.md` 在「值」上更成熟。** 冲突时按上表判断，
而不是一律以某一方为准。

`DESIGN.md` §8 是这份文档曾经缺失的一层。只有值、没有形态时，每个组件各写
各的——于是出现过全仓 11 个不同字号、导航与列表内边距不一致的界面。
用户说「太粗糙」，粗糙的不是某个值，是没有形态可依。

`RESEARCH.md` 单独存在的理由：**证据最容易被丢掉**。半年后有人问
「为什么不用 RAGFlow」，如果答案只写在结论里，就得重新调研一遍。

## 维护规则

1. **每条规定只有一个真相来源。** 不要在 `AGENTS.md` 里重复 `PRD.md` 的内容——
   只指路。重复必然导致两处说法不一致。
2. **文档与代码同批提交。** 分开提交等于制造「谁说真话」的问题。
3. **被取代的决策不要删。** 标上「已被 D-0xx 取代」并保留原文，
   否则后人会重新踩一遍已经踩过的坑。
4. **区分「确定的」和「未验证的」。** `RESEARCH.md` §5.4 标了一处未能验证的结论
   （ParadeDB 的中文分词质量）。这种标注比假装确定有用。
