# mimir 产品需求文档

> 自托管的个人知识库：写 Markdown 笔记、收集外部资料、带引用地问 AI。
> 单用户，部署在自己的服务器上。

---

## 1. 非目标

明确不做的事。写下来是为了在功能诱惑面前有据可依。

| 不做 | 原因 |
|---|---|
| 多人协作、团队权限、审计日志 | 单用户自托管，这些是纯负担。WeKnora 的 RBAC 四层角色矩阵对一个人是负资产 |
| 公开发布 / 博客平台 | 偶尔想分享一篇时，导出 md 即可，不值得为它做一套发布流程 |
| 全功能任务管理 | 只做「笔记里的 `- [ ]` 能聚合出一个清单」这一层。不做看板、甘特、提醒 |
| 知识图谱可视化 | 好看，日常几乎不点。反链列表 + 相关笔记已经够用 |
| 外部插件市场 | 见 TECH.md 的插件章节。「插件架构」在本项目里指内部接缝，不是第三方生态 |
| 可切换的**数据库** / 向量引擎 | 数据库是**受控双实现**而非可切换产品（D-045）：服务器部署 = Postgres 17 + pgvector，本地开发与桌面端 = SQLite，由 `DATABASE_URL` 协议头决定——它是部署事实，不进设置页、没有界面开关、不做第三种后端。SQL 方言分支收敛在五个点名处（见 TECH §1）。**文件存储不在此列**——它有多实现（本地与 S3），且第二次实现不是为了兼容已有栈：远程部署的人本来就没有本地文件可开。见 D-031、D-038 |
| 排版级编辑器 | 不做 LaTeX 排版、不做协同编辑、不做块级拖拽 |
| **自建兼容 Word 的编辑器** | PDF 批注在 M2（那时它是「划线与注释」的一部分）。Office 的在线编辑**不做自建**——那等于从零写一个兼容 Word 的编辑器，而本项目的定位是知识库不是办公套件。但**借**一个是可以的：docx 的编辑由 vendored 的 GenOffice 引擎承担（D-049、`TECH.md` §15），因为它的补丁式保存做到了「改两个字不重排整篇 XML」。现实路径「下载 → 外部工具改 → 替换原件」仍然保留（`替换原件` 因此必须有） |
| **缩略图与网格视图** | 需要一条缩略图管线（图片解码 + PDF 首页渲染），而「文件名 + 格式 + 大小」已经足够认出是哪份文件 |
| **OCR**（从图片/扫描件里取字） | 它是另一个模型通道（视觉模型），成本与失败模式都与文本提取不同。图片里的文字搜不到是一条**明示的边界**，不假装能 |
| **格式转换导出**（PDF → md、Word → PDF） | 导出回答的是「把我的东西拿走」，而不是「帮我转格式」。原件与提取的正文都给了，转换交给专业工具 |
| 用户管理（用户列表 / 角色 / 权限 / 改邮箱） | 单用户自托管。**改自己的名称与头像是「账号资料」，不在这一条里**——它没有引入第二个用户，也没有新增任何一处权限判断。改邮箱尤其不做：`OWNER_EMAIL` 是所有者账号的真相来源（D-020），改邮箱等于换账号 |

## 2. 三条核心洞见

这三条驱动了后面几乎所有设计。评审时可以问：某个功能是在服务哪一条？

### 2.1 知识库死于「收集摩擦」和「再也不看」

不是死于存不下。绝大多数个人知识库的生命周期是：兴致勃勃搭好 → 收集了一堆 → 再也没打开过。

**设计后果**：
- 收集入口的摩擦必须低于「先在浏览器收藏，之后再说」
- 检索质量是**核心功能**，不是附属特性。搜不到等于没存

### 2.2 闭环是五环，断一环整个就废

```
收集  →  整理  →  检索  →  使用  →  沉淀
```

原型阶段两次补洞都源于这个诊断：

| 断裂处 | 症状 | 修补 |
|---|---|---|
| 收集 | 界面上根本没有地方粘贴链接 | 抓取对话框（自动识别来源并提示该来源特有的坑） |
| 整理 | 只有「待整理」橙色徽标，没有任何整理动作，收件箱是死胡同 | 整理条：建议标签 + 归目录 + 完成 + 归档 |
| 沉淀 | 对话产出结论，但界面上无处可去 | AI 回答下的「存成笔记」，保留引用来源 |

### 2.3 「资料」与「笔记」行为不同，但不做浏览分类

| | 笔记 | 资料 |
|---|---|---|
| 来源 | 自己写 | 抓取（博客 / 公众号 / GitHub）或**上传文件** |
| 可编辑 | 是 | 否（只读） |
| 真相 | 文件 | **原件 + 派生正文**（抓取件：原始快照 + 派生正文） |
| 检索权重 | 高 | 正常 |

这些差异体现在**行为**上：笔记可编辑、抓取件只读；检索时自己的笔记加权。
它们**不体现在浏览分类上**（修订，D-047）：界面不按来源分组、不放来源
筛选与来源徽标——库就是**一个统一的文档集合**，组织靠目录、标签与搜索。
理由：按来源分类是「稍后读列表」的心智（我的笔记 / 收集的资料两个入口），
而知识库的浏览主角是库本身；「这是笔记还是资料」在打开详情的那一刻自然
可知（能不能编辑），不需要一枚常驻徽标提前替用户分类。

**上传的文件属于「资料」，但不是一种新的东西。** 它和抓取的资料共用同一条
`documents` 记录、同一套整理动作（标签 / 目录 / 收件箱 / 归档）、同一次检索，
区别只在原件的来源不同（本机 vs URL）。所以：

- **`kind` 是来源，不是格式。** 五种：笔记 / 网页 / 公众号 / GitHub / 文件。
  PDF、Word、Excel、图片这些是**格式**，写在元信息行里——格式决定预览方式
  （PDF 在线看、Word 提取正文），不决定它是不是知识
- 唯一的例外是 **`.md` 上传**：它变成**可编辑的笔记**。md 本来就是可编辑格式，
  做成只读副本会立刻产生两个真相（原件不再变、而正文可以改）

## 3. 内容来源与抓取方案

三类来源的难度差异极大，方案必须分开设计。

### 3.1 技术博客

**主路径：RSS / Atom 订阅。** 掘金、博客园、Medium、Substack、Hugo/Hexo 站点基本都有 feed。定时轮询、新文章自动进收件箱，比爬首页稳得多，也不需要处理反爬。

**辅路径**：无 feed 的站点用「粘贴 URL → 服务端 Readability 提取正文」。

### 3.2 微信公众号

**这是最难的一类。** 现实约束：

| 约束 | 后果 |
|---|---|
| 服务端直接 GET 多数情况能拿到正文（在 `#js_content`），但近年加了环境校验，高频访问会撞墙 | 只能低频，且需要限速与退避 |
| 正文图片在 `mmbiz.qpic.cn`，下载必须带 `Referer: https://mp.weixin.qq.com/` | 不带就 403，文章变空壳 |
| RSSHub 的公众号路由维护成本高、易失效 | 不作为唯一方案 |
| 技术号经常把代码贴成**截图**，正文里根本没有代码文本 | 只能 OCR 或接受。摘要里要标注「该段为图片」 |
| 文章会被删除 | **全文快照 + 图片本地化是刚需**，不是可选项 |

**方案**：主路径是浏览器扩展（在用户的会话里抓，绕开反爬、拿到完整 DOM）；服务端抓取作为辅路径（低频、带 Referer、失败时提示「改用扩展」）。

### 3.3 GitHub

用 GitHub API（PAT 可把限额从 60 次/小时提到 5000 次/小时）：

- 取 repo 元数据 + README（raw）+ topics + license + releases + 最近提交时间
- AI 生成解读：解决什么问题 / 技术栈 / 适合什么场景 / 是否值得深入 / 与已有笔记的关联
- **Star 同步**：每天拉一次自己 star 的仓库，新的自动入收件箱。对技术人这是最省力的知识来源
- 只抓 README 和 `docs/`，不克隆整个仓库

### 3.4 优先级

| 来源 | M0 | M1 | M2 |
|---|---|---|---|
| 手动新建笔记 | ✓ | | |
| 粘贴 URL（服务端抓取） | ✓ | | |
| GitHub API | ✓ | | |
| 公众号（服务端，低频） | ✓ | | |
| **文件上传（任意格式，原件 + 预览 + 下载）** | | **✓ 已落地** | |
| **文本 / HTML / Office 的正文提取（可搜）** | | **✓ 已落地** | |
| RSS 订阅轮询 | | ✓ | |
| 浏览器扩展 | | ✓ | |
| PDF 的**文本提取**（内容可搜） | | | ✓ |
| GitHub Star 同步 | | | ✓ |

## 4. 功能范围

### M0 —— 可用

目标：能真实地写笔记、收集资料、搜到东西。

- Docker Compose 骨架 + Postgres
- 单用户登录（首个注册者成为唯一用户，之后注册自动关闭）
- Markdown 笔记：所见即所得编辑，文件落盘为纯 md
- 笔记 CRUD + 标签
- 粘贴 URL 抓取（网页 / 公众号 / GitHub），进收件箱
- 整理：建议标签、归目录、完成、归档
- 全文检索（中文分词，见 TECH.md）
- 收件箱 / 全部 / 笔记 / 资料 四个视图 + 目录树 + 标签
- 全量导出（**含上传的原件**——对一份 PDF 来说原件才是内容）

**判据**：能连续用一周不觉得别扭。

### M1 —— 有用

目标：问它「我以前记过什么」，能给出准确且带引用的答案。

- **配置面**：模型按角色配置（对话 / 推理 / 摘要 / 向量化）、解析与
  抓取实现的清单可见、检索参数可调。全部可在界面上改，不必改 `.env` 重启
  （环境变量仍是部署的真相，界面是覆盖层，见 TECH.md §7.5）
- 分块 + 向量化（pgvector）
- 混合检索：关键词 + 子串 + 向量，加权 RRF 融合
- 带引用的知识库问答，**引用指回分块的真实偏移**（不是猜出来的位置）
- AI 自动摘要、标签建议
- 内联改写（选中一段 → 改写/翻译/精简/扩写）
- **文件上传**（任意格式）：原件入库、列表、按格式预览、下载、替换原件、
  随导出打包带走。`parser` 接缝新增 text / docx / xlsx / pptx 四个实现，
  所以文本、HTML 与 Office 的内容**可搜、可被 AI 引用**。**PDF 的文本提取**
  留到 M2（它需要另一套库），而 PDF 的**预览**已经可用（浏览器自带阅读器）
- **编辑**：Markdown 与 **.docx** 可编辑——docx 走浏览器内编辑器（D-049、
  `TECH.md` §15），保存回原件并重算正文。PDF 批注在 M2；xlsx / pptx 的编辑
  未评估（见 §5.12 的格式表）
- RSS 订阅
- **账号资料**：改名称、换头像（头像进 `data/avatars/`，**不进 vault、不进检索、不进导出包**——
  导出包回答的是「我的知识」，不是「我的账户」）
- **用量统计**：每次模型调用记账（token / 耗时 / 成败），设置页「统计」分区给出
  token 消耗热力图与按角色的用量表。表与采集点先落，界面后做（见 TECH §12.6）

**判据**：问「我以前关于 X 记过什么」，回答带引用且引用指对了原文位置。

M1 的推进拆成五段（顺序与依赖见 `TECH.md` §11）：

| 段 | 内容 | 为什么在这个位置 |
|---|---|---|
| A | 插件骨架：注册表 + 配置分层 + provider 角色化 | 后面每一步都要读写配置，而且向量通道要问 provider「有没有可用的 embed 模型」 |
| B | 分块与向量化 | 检索单元下沉是 C 的前提 |
| C | 混合检索 | 两条老通道改返回分块 id，加向量通道 |
| D | 带引用的问答、摘要、标签、内联改写 | 消费 C 的结果 |
| E | 文件上传、Office 与文本的正文提取、RSS | `parser` 接缝的四个新实现，可以独立推进。**上传与提取已落地**，RSS 未做 |

### M2 —— 好用

- 浏览器扩展（解决公众号、知乎、付费墙）
- PDF 的**文本提取**（内容可搜可引用，选型见 RESEARCH 的规矩）
- GitHub Star 同步
- 划线与注释（读 PDF/网页时高亮 → 变成可检索的引用片段）
- 对话沉淀成笔记的完整形态（自动带引用来源）
- 移动端速记（窄屏独立设计，见下）

### M3 —— 长期

- 回顾机制：随机回顾、每日回顾、「一年前的今天」
- 关联推荐（自动发现未链接的提及）
- 多篇资料生成技术调研综述
- 模型侧成本优化（按内容哈希缓存、增量向量化）

## 5. 关键交互决策

这些是原型阶段逐条定下来的。每条都附了理由，因为「为什么不用另一种」比「用了哪种」更容易被遗忘。

### 5.1 布局：两栏 + 库视图（修订，D-047）

左导航 / 主区。主区有两种状态：

| 状态 | 何时 | 主区显示 |
|---|---|---|
| **浏览态** | URL 无 `id` | **库**：搜索框 + 卡片网格（标题、摘要、标签、时间），筛选靠左导航的 scope（收件箱 / 全部 / 目录 / 标签） |
| **阅读态** | URL 有 `id` | 详情占满主区（阅读 / 编辑），顶部返回库 |

否决史：「两栏 + 命令面板」曾因「不记得存过什么时连翻一翻都做不到」被否决
（那条理由是对的）——但解法不是把浏览面塞回一条 300px 的窄栏，而是让
**主区本身就是浏览面**。三栏的窄列表 + 详情是邮件客户端的 master-detail
心智，把库压成了配角；两栏库视图里，收集的东西才是主角（对齐 DEVONthink /
Eagle / Cubox 这类知识库应用的形态）。

代价：收件箱整理从「左列表右详情」变成「点开 → 处理 → 返回」，多一次点击；
补偿是整理动作（建议标签 / 归目录 / 完成）都在详情的整理条上，不依赖并排。

### 5.2 左导航：会话优先

顶部是「新建对话」+ 会话历史，然后才是文档入口。

**全部两栏。** 文档模式的主区在浏览态与阅读态之间切换：

| 模式 | 左栏 | 主区 |
|---|---|---|
| 对话 | 会话历史 + 知识库入口 | 对话（含可折叠的检索过程与引用） |
| 设置 | 同上 | 设置分区与表单 |
| 文档（浏览态） | 同上 | 库：搜索 + 卡片网格 |
| 文档（阅读态） | 同上 | 阅读 / 编辑，顶部返回库 |

**设置页为什么也不该有中栏**：设置是「进入一个分区改完就走」的场景，而中栏
在那里只能显示文档列表——**与你在做的事完全无关，却占掉四分之一的宽度**。
它还会误导：那个列表看起来像设置的一部分。

设置页自己有一套分区导航（模型 / 检索 / 抓取 / 插件 / 统计 / 数据 / 外观 / 账号），
那才是它需要的那一栏；它是**横向**排在内容上方的——早期版本把它做成内容列里
的左侧竖栏，于是一页之内有了两条左栏（`docs/DECISIONS.md` D-025）。

「外观」是其中一个分区，也是唯一**不写进设置键表**的一项：它是纯客户端的
渲染偏好，存 `localStorage` 而不是数据库（`DESIGN.md` §11 的同一判断）。
代价是换设备要重选一次，这一点直接写在那个分区里，不假装它跟着账号走。

### 为什么删掉了对话模式的中栏

原型里它显示「本次引用」（一张张来源卡片）。当时的设计意图是
**「它读了什么」应该和「我有什么」一样可见**。这个意图是对的，但**放错了位置**：

1. **它与回答下方的引用块重复。** 每条 AI 回答下面已经是一列引用块，带类型徽标、
   标题、原文片段与命中通道。中栏那几张是它的副本，而且更差——少了与
   具体回答的对应关系，看不出「这个来源支撑的是哪句话」
2. **它有一半时间显示的是别的东西。** 新对话时中栏按 §5.10 显示待整理收件箱；
   有会话时显示引用。同一栏位承担两种语义，用户每次都要重新判断「现在是什么」
3. **它是静态的。** 打开一个旧会话时显示的是那个会话的历史引用，
   而用户此刻想做的往往是「继续问」或「去看那篇文档」——两者都不需要这一栏

删掉换来的是：对话列更宽（问答是主场景，值得更多横向空间）、少一个要学的模式、
以及不再有「看起来像本次引用、实际是收件箱」这种误导（那正是删掉前的实际状态）。

**代价与补偿**：失去了「一次看到这次对话的全部来源」。这个需求由回答下的引用块
满足（滚动即可看到），并且引用块比中栏卡片多了「支撑哪句话」这层信息。
§5.10 那条「新对话的中栏不空着」改成在**对话空态里**列出待整理内容——
动机（「我刚收了几篇东西，想问问」）没有丢，只是换了承载它的地方。

### 5.3 树与标签并存，分工明确

- **目录树**：一个文档只能在一个位置，管**归属**
- **标签**：一个文档可挂多个，管**横切**

两者走同一套过滤逻辑，只是筛选条件不同，避免变成两套代码。

### 5.4 编辑器：所见即所得，无源码模式

**已知性质：Tiptap 不是无损的，但是幂等的。**

```
输入      | 1 | 2 |
首次保存  | 1   | 2   |     会被整理成编辑器的规范形
之后每次  | 1   | 2   |     不再变化
```

正文、标题、列表、嵌套列表、代码块、引用、链接、行内代码往返逐字节一致；表格是唯一会被重排的结构。

**边界**：可以作为唯一编辑器（不会逐次劣化）；**不要**用 Obsidian / VS Code 改同一批文件（两边规范形不同，来回改产生大量无意义 diff）。

### 5.5 AI 只有一个入口：主视图对话

**删掉了 AI 侧栏。** 理由是它被两头夹掉了：

- 问某一段 → 内联工具条的「就这段提问」，锚定选中内容，更精确
- 问整篇 → 主视图对话 + 范围选「当前文档」

侧栏的范围比内联宽、比主视图窄，两边都不如。留着的代价是 392px 屏幕和一个要维护的面。

删除后补了三处，否则「问当前文档」会变难：

1. 文档工具条「问 AI」→ 带这篇的上下文进主视图，范围自动锁定
2. 内联「就这段提问」→ 同上，并把选中的话作为引用预填进输入框
3. **「返回对话」** → 从对话点引用跳去文档后，文档顶部出现返回入口

### 5.6 检索过程可见，默认折叠

借自 WeKnora。AI 回答上方是一条 `思考 2 轮 · 调用 3 次工具 · 耗时 1.0s`，展开后是逐步记录，每步带具体数字：

```
✻ 我先在知识库里找与「组件性能」相关的内容
⌕ 用 jieba 切分查询词  组件 / 性能
  词级召回 3 段 · 子串兜底 1 段
▤ 读取命中的文档并合并相邻分块
  来自 2 个文档，共 4 个分块
✓ 确认没有遗漏，生成回答
```

**这条对个人知识库比对企业的更重要**：AI 说「没找到」时，你能立刻分辨是**确实没存过**、还是**存了但分词没匹配上**、还是**检索范围设错了**。没有它，你只能怀疑自己记错了。

### 5.7 对话沉淀成笔记

AI 回答下方有动作条（存成笔记 / 复制）。存下来的笔记**保留引用来源**，不是孤零零一段话。

这是闭环的最后一环。没有它，知识库只是「能问」，不会「越用越厚」。

### 5.8 失败路径：每类给不同的出路

| 失败 | 出路 | 说明里必须回答 |
|---|---|---|
| 额度用尽 | 改用别的模型 · 去充值 · 只看检索结果 | 这次花钱了吗 |
| 请求超时 | 重试 · 缩小到当前文档 · 拆成小问题 | 内容丢了吗 |
| 回答被截断 | 继续生成 · 只要结论 · 输出到笔记里继续写 | 能接着做吗 |
| 网络不可达 | 只用检索不调模型 · 重试 · 改用本地模型 | 还能做什么 |

统一给一个「重试」按钮等于把判断推回给用户，而用户此刻恰恰最缺判断依据。

「网络不可达」这条尤其重要：**离线不是全盘瘫痪**，检索在本地 Postgres、笔记在本地文件。明确告诉用户还能做什么。

### 5.9 保存状态与未保存保护

工具条常驻「正在保存… / 已保存 / 保存失败 · 点此重试」。

离开未保存内容时给**三个**选项：继续编辑 / 丢弃改动 / 保存并离开。两选项（留下 / 丢弃）把这个场景变成二选一的拷问，用户真正想要的往往是第三种。

**「保存并离开」在保存失败时不会放行**——放行了用户以为存上了，实际丢了，比不拦截更糟。

### 5.10 其他

- **文档大纲**：右侧锚点导航，滚动联动高亮。**标题数 ≥ 2 才出现**——两段话的笔记不需要目录，常驻只是白占 200px
- **新对话的空态不空着**：直接列待整理收件箱。启动新对话最典型的动机就是「我刚收了几篇东西，想问问」
- **整理条把 AI 已算好的标签建议直接摆出来**：后端早就在算高频词，界面上没地方显示等于白算
- **归档不是黑洞**：导航有「已归档」入口，归档的文档仍可浏览、可恢复
- **双链**：文档底部列出「来源」和「被引用」，让双向链接是双向的

### 5.12 文件：两层可看，格式不是类型

上传的文件可以是任意格式，但它们共享同一条记录、同一套整理动作、同一次检索。
界面要回答的是「这个东西现在能看到多少」。

**预览分两层，正文优先**：

| 层 | 是什么 | 回答的问题 |
|---|---|---|
| 正文 | 从原件提取出的文本（与笔记共用排版） | 「它讲了什么」 |
| 原件 | 上传的原始文件 | 「它原样长什么样」 |

`正文 | 原件` 的切换**只在两层都成立时才出现**。这比「永远显示两个页签」好：
一个点了没反应的页签是假的选择（`DESIGN.md` §7.4 的同一条判断），
而多数文件只有一层——PDF 只有原件，txt 只有正文，图片只有原件。

**正文为空时必须说明原因，不能留白。** 四种原因给用户的下一步完全不同：

```
这个格式还没有提取实现（PDF）  → 「该格式的正文提取将在后续版本支持」
试过但失败了（编码不对/文件损坏） → 「提取失败：{具体原因}」
文件里没有文字（空文件/纯图片）  → 「文件里没有可提取的文字」
未知格式                      → 「原件已保存，可下载查看」
```

留白等于说「这篇没有内容」，而它其实有内容、只是还没提取——
与热力图把「用量未上报」画成斜纹而不是空底是同一条规矩。

**格式显示成中性文字，不是彩色徽标**：「PDF · 2.4 MB」写在元信息行里。
彩色徽标是**来源**的语义（笔记 / 网页 / 文件…），而格式是**属性**。
按「一格式一色」走下去，每加一种格式就要多一组色对——而格式是开放集合。

**筛选只按来源，不按格式**：胶囊固定六个（全部 / 笔记 / 网页 / 公众号 /
GitHub / 文件）。要按格式找用搜索或标签，不让筛选器随支持格式增长。

**编辑按格式分先后**（用户的判断：**上传 / 列表 / 预览现在就要，
「其他类型后面支持」说的是编辑**）：

| 格式 | 现在 | 之后 |
|---|---|---|
| `.md` | **可编辑**（上传即导入为笔记） | — |
| 文本 / HTML | 只读（正文提取） | 视需求 |
| .docx | **可编辑**（浏览器内，vendored GenOffice；D-049） | 补分页视图与工具栏 |
| .xlsx / .pptx | 只读（正文提取） | 未评估（xlsx 走的是另一条路） |
| PDF | 只读 + 原件预览 | M2 批注（划线与注释的一部分） |

**「替换原件」是编辑的现实路径**：下载 → 用外部工具改 → 传回。
没有它，用户只能删了重传——**而标签、目录、整理状态会全丢**。
替换时这些整理结果保留，正文与大小重算。

### 5.11 统计：热力图量的是 token，不是次数

格子记录的是**每次调用消耗的 token**（输入 + 输出），不是调用次数。

理由是这两件事不成比例：一次深度推理可能抵二十次摘要，而「我这个月花了多少」
比「我点了多少次」更常被问起。**代价必须写在明处**：它因此不再能回答
「我还在不在用」——那正是 §7 的成功判据。补法很便宜，tooltip 里同时给两个数：

```
9 月 23 日 · 12.3 万 token · 8 次调用
```

**颜色按 token，密度按次数。** 两个问题一次答完，不需要第二张图。

**格子有四个状态，不是一个色阶**：

| 状态 | 表现 | 为什么不能合并 |
|---|---|---|
| 无调用 | 空底 | — |
| 有调用、用量未上报 | 斜纹（**不是**空底） | 兼容端点不一定回传 usage。画成空等于说「我那天没用」，那是**静默的谎**——图在否认发生过的事 |
| 有用量 | 按分位着色 | — |
| 今天 | 进行中，图例注明「到今天此刻为止」 | 半天的数据看着像用量骤降 |

**分档按这一年的分位数，图例给出最深一档的真实区间**（如「最深一档 ≥ 12.3 万」）。
固定阈值在忙的月份全是最深色、闲的月份全是浅色，图就没信息了。
tooltip 里的真实数字才是可行动的那个——颜色只负责给出形状。

**范围固定一年，不做切换。** 第一版有 30 天 / 90 天 / 一年三档，
去掉了：概览那排（今日 / 本周 / 本月）已经回答了「最近怎么样」，
而这张图回答的是「这一年我在持续用吗」——它需要的正是一整年的形状。
顺带解决了一处解释成本：分位数是按范围算的，切范围会让同一个颜色
代表不同的数字，得在图例里额外声明一句。固定下来之后一档就是一个
确定的区间。

**补嵌入那天的尖峰不剔除。** 它比日常高一两个数量级，剔除能让曲线好看，
但会让「图表说 50 万、表格说 210 万」——这个项目最不能忍的就是两处各说各话。
尖峰照画，靠 tooltip 拆解来源（对话 / 摘要 / 嵌入）解释它。

**时区必须显式指定。** 容器默认跑 UTC，「昨晚 11 点」的消耗会算到前一天，
图整体左移一格且不报错。聚合按 `stats.timezone`（默认 `Asia/Shanghai`），
并在图旁标出当前时区。`at` 是 `timestamptz`，所以换时区只是换聚合方式，
历史数据自动跟着重算，不需要迁移。

## 7. 成功判据

不自欺的判据只有一条：

> **连续用三个月，且第三个月打开的次数不低于第一个月。**

如果第一个月每天开、第三个月一周开一次，说明它退化成了收藏夹。届时要问的不是「怎么加功能」，而是「哪一环断了」。
