  1. /**
  2.  * PDF 的**页面模型**：一页是什么、改了哪些属性、怎么变成字节。
  3.  *
  4.  * ## 为什么从 PdfEditor 里搬出来
  5.  *
  6.  * 这个文件里没有一行 JSX。它是「PDF 的页面结构与几何」，而页面几何是这个
  7.  * 格式里最容易算错、又最难靠肉眼发现的那部分（裁 20pt 到底裁在哪、换纸型
  8.  * 时内容会不会跑偏、导入的页在第二次保存时还在不在）。搬出来才**测得动**
  9.  * ——`pdf-pages.test.ts` 拿 pdf-lib 读回产出的字节逐页断言，再用 pdf.js 读
  10.  * 回文字位置验证几何。
  11.  *
  12.  * ## 一页由四样东西决定（`PdfPageRef`）
  13.  *
  14.  * ```
  15.  * origin   这一页是从哪来的：原件第 N 页 / 空白页 / 别处导入的第 N 页
  16.  * rotation 目标旋转（绝对值，不是增量——见 buildPdfBytes 的说明）
  17.  * crop     裁剪：四边各内缩多少 pt（相对**原件可视区**，不是相对纸边）
  18.  * paper    纸型：目标尺寸。非 null 时内容按 k 缩放（与 resize 配对）
  19.  * ```
  20.  *
  21.  * **为什么用一个 `base` 尺寸而不是「当前尺寸」**：裁剪与纸型都要一个不变的
  22.  * 参照。用「当前尺寸」的话，裁一次之后再换纸型，k 会相对裁剪后的尺寸算，
  23.  * 而裁剪并不改变内容的实际比例——那会得到「裁 20pt 顺带把内容缩小 3%」。
  24.  * 所以 `base` 是**打开文件那一刻**这一页的可视区尺寸，之后不再变。
  25.  *
  26.  * ## 旋转是绝对值、且不改盒子的宽高
  27.  *
  28.  * PDF 的 `/Rotate` 是「显示时把页面转多少度」，它不改变 MediaBox。所以盒子
  29.  * 尺寸（`base`/`crop`/`paper`）**始终是未旋转的那一套**，界面要的显示尺寸由
  30.  * `displaySize()` 现算（90/270 度交换宽高）。上一版在 ref 里存的是交换后的
  31.  * 宽高，于是「旋转两次回到原样」要靠两次交换抵消——那种表示一旦有一处忘了
  32.  * 交换，页面的长宽比就是错的，而画布只会画得不对、不会报错。
  33.  */
